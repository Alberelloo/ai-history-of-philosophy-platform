# Design

Третье изменение стека (ТЗ, п. 2.3). Опирается на `add-reference-catalog` (снимок `snapshot.py`, правило `epochs.py`) и `add-epochs` (страница `/epochs/<id>`, `GET /v1/epochs`, QID эпох в `sources/epochs.yaml`). Контракт `GET /v1/context` — для `add-geo-timeline` (2.4).

## Контекст

- Реестр (`registry_data.py`):
  - `stimulated` — «стимулировало» / обратная «возникло в контексте»; субъект — `event`, `phenomenon`, `idea_event`; объект — идеи, агенты, труды; семейство `context`; уточнитель `mechanism` (political, economic, social, religious, scientific, institutional).
  - `happened_in` (событие → `place`), `participated` (агент → событие), `belongs_to_epoch`, `circumstance` (идейное событие → событие).
  - `event_kind` — political, scientific, religious, intellectual, biographical (нет economic и social).
  - Рецепт `context` — все типы, семейство `context`, «в обе стороны», глубина 2, порядок по времени.
- Извлечение (`filling.py`, файл Lead'а): схема вывода из `registry.output_schema()` — `stimulated` в списке типов (v0, без значения); `qualifiers` — свободный объект, проверка — `Statements._check` → `registry.check_qualifiers` (механизм вне списка → `RegistryError` → утверждение отбрасывается событием `knowledge.extraction.dropped`, фрагмент продолжается). В блоке `relations` (данные промпта) уточнителей нет — модель о механизме не знает, но если укажет, он проверится. Правка кода извлечения для 2.3 **не нужна**; подсказка механизма — отдельный пункт на согласование.
- Достройка (`graph.py`): промпт `graph.extend`, допустимые типы — из семейств рецепта, `_proposal` разрешает только существующие сущности с однозначным названием, `check_proposal` — проверки записи; связь должна касаться узлов графа; сохранение через очередь со статусом `generated`; порог `min_edges=5`.
- Карточка (`cards.py`): у события раздел «На что повлияло» (`stimulated`, out); у персоны «Контекст эпохи» (`belongs_to_epoch`); обратной стороны `stimulated` нет ни у кого.
- Карта: у событий есть `kind`; выбор события выделяет живших в год события и их труды ±10 лет (`model.ts`).

## Решения

### `GET /api/knowledge/v1/context`

| Параметр | Правило |
|---|---|
| `epoch` | id эпохи; либо `from` + `to` (годы, астрономический счёт), не оба и не ни одного; `from < to` |
| `kinds` | коды `event_kind`, через запятую; `none` — события без вида |
| `verified` | `true` — без `generated` |
| `textbook` | id источника — пометка `in_textbook` |
| `lang` | `ru` \| `en` |

```json
{
  "mode": "epoch",
  "epoch": {"id": "e_ep01", "label": "Просвещение", "from": 1680, "to": 1800},
  "window": null,
  "events": [
    {
      "id": "e_ev01",
      "label": "Славная революция",
      "type": "event",
      "kind": "political",
      "dates": {"from": 1688, "to": 1689, "precision": "year", "original": "1688–1689"},
      "places": [{"id": "e_pl01", "label": "Лондон", "wikidata": "Q84"}],
      "basis": "dates",
      "stimulated": [
        {
          "statement_id": "st_0a1b2c",
          "target": {"id": "e_po05", "label": "Политическая философия Локка", "type": "doctrine"},
          "mechanism": "political",
          "status": "sourced",
          "generated": false,
          "in_textbook": true,
          "attributed_to": ["Учебник N"],
          "evidence": [{"paragraph_id": "p_123", "link": "/p/p_123"}]
        }
      ]
    }
  ],
  "counts": {"political": 1, "intellectual": 1, "none": 0},
  "truncated": false
}
```

- QID в примерах этого документа — иллюстрация формы; верные идентификаторы подтверждает Lead после `suggest`/`harvest`.
- `epoch` — только в режиме эпохи; `window: {"from", "to"}` — только в режиме окна.
- `basis` — `explicit` | `dates` (режим эпохи); в режиме окна — `null`.
- `places[].wikidata` — внешний идентификатор места, если есть (для 2.4: по нему 2.4 берёт координаты).
- Подтверждения — без цитат (цитата показывается в карточке, здесь только ссылка на абзац); подтверждения и атрибуции источников, закрытых для региона, снимаются (`closed_sources`, как `without_closed`).
- Порядок, пределы (200 событий по значимости, 30 связей на событие), `truncated` — как в требовании.
- Код: `knowledge/context.py:Context(snapshots, registry, membership)` — сборка из снимка, без обращений к базе на событие; маршрут в `app.py`; не платная операция.

### Карточка

`cards.py:SECTIONS` — раздел `("context", "Исторический контекст", ["stimulated"], "in")` добавляется к `concept`, `person`, `work` и общему набору учений (`doctrine` и производные). Строка — общий `_row` (механизм — в `qualifiers`; клиент показывает его подписью `t.onto.values.mechanism`).

### Карта

`map.py`: у `events[]` — `stimulated: [{"id": <объект>, "generated": bool}]` (действующие, объект на карте); клиент: `model.ts` при выборе события добавляет эти id к участникам; при `filter.verified` — только `generated=false`. Линий нет.

### Модуль `knowledge/epoch_context.py`

```
python -m philograph.knowledge.epoch_context harvest [--epochs sources/epochs.yaml] [--manifest sources/epoch_context.yaml]
python -m philograph.knowledge.epoch_context apply   [--manifest sources/epoch_context.yaml] [--dry-run]
```

- `harvest`: для эпох с подтверждённым QID (из `sources/epochs.yaml` или внешнего идентификатора) — `fetch_entity(qid)` → P793 → для каждого события `fetch_entity` → дата (`epoch_dates.wikidata_time` + `dates.interval`; P585 или P580/P582), вид по `EVENT_CLASSES` (таблица P31 → `event_kind`, данные модуля, как `WIKIDATA_ROLES`; не найдено — вид не пишется), место P276 (первое). Без даты — не предлагается. Уже принятые и отклонённые в манифесте не перезаписываются.
- Манифест:

```yaml
epochs:
  - epoch: Просвещение          # ru-название из sources/epochs.yaml
    qid: Q12539                  # подтверждённый QID эпохи (берётся оттуда же)
    candidates:
      - qid: Q6534
        label: {ru: Французская революция, en: French Revolution}
        dates: {start: "+1789-00-00T00:00:00Z", start_precision: 9, end: "+1799-00-00T00:00:00Z", end_precision: 9}
        classes: [Q10931]
        kind: political
        place: {qid: Q90, label: {ru: Париж}}
        decision: pending        # pending | accepted | rejected — решает человек
```

- `apply`: только `accepted`; событие — по внешнему идентификатору или новое (`entities.create("event", names, external={"wikidata": qid})`); утверждения `dating`, `event_kind` (если есть), `belongs_to_epoch` (уточнитель `membership_basis=historians`), `happened_in` (место — по QID или новое `place`); все — `status="sourced"`, атрибуция `wikidata:<qid события>` со ссылкой, `Provenance("imported", extra={"wikidata": qid, "from": "P793", "epoch": epoch_qid})`. `stimulated` не пишется никогда.
- Сеть — только `epoch_dates.http_fetch` (общая функция из 2.2); тесты — фикстуры.

### Достройка с страницы эпохи

- Кнопка «Достроить контекст» у события → `POST /api/knowledge/v1/graph/build {"entity_id": <событие>, "recipe": "context", "generation": <настройка>, "textbook", "only_textbook"}` — поток NDJSON читается общим `web/src/map/stream.ts`; рёбра `stimulated` из потока добавляются в блок с пометкой «не проверено»; после `done` блок перезапрашивает `/v1/context` (сохранение идёт через очередь, поэтому до перезапроса строки помечены `pending`).
- Лимиты — платная операция `graph` шлюза (без изменений); уведомления (`notice`) — те же тексты, что на карте.

### Извлечение из текста

Проверяется тестами на фейковой модели (`tests/knowledge/test_filling.py`): `stimulated` с корректным механизмом сохраняется, с неверным — отбрасывается, фрагмент продолжается. Код `filling.py` и `prompts/__init__.py` не меняется.

## Выбор решения

### 1. Форма API контекста

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Без нового API: страница эпохи собирает контекст из справочника (`type=event&epoch=`) и карточек событий | Ноль нового кода сервера; N+1 запросов карточек на странице | Правило «что такое контекст» (порядок, статусы, пределы, закрытые источники) уходит в клиент | 2.4 повторяет ту же сборку; 50 событий — 51 запрос |
| Б. `GET /v1/epochs/{id}/context` | Один запрос | Привязан к эпохе; окно времени для 2.4 — второй маршрут | Два маршрута с одним правилом |
| В. `GET /v1/context` с режимами «эпоха» и «окно» | Один запрос, один маршрут | Правило в `context.py`, принадлежность — `epochs.py`, закрытые источники — общий фильтр | 2.4 берёт тот же контракт; пределы защищают от 10× |

Выбрано: **В**. Чем платим: проверка «ровно один режим» на сервере (отказ 400). Костыли, которых избегаем: N+1 запросов и копия правил в клиенте.

### 2. Контекст из Wikidata

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Не брать из Wikidata | Ноль кода | Контекст только из текста и модели — у Lead'а событий мало | ТЗ просит Wikidata |
| Б. Заводить все P793 эпохи сразу | Быстро | Внешний источник без человека заводит сущности в онтологию Lead'а; Wikidata у эпох перечисляет и спорное | Чистить — дольше, чем проверять |
| В. Кандидаты в манифест, в базу — принятые человеком | Один ручной шаг | Как портреты: внешнее предлагает, человек решает, код проверяет (дата, класс, тип концов) | Повторный запуск идемпотентен; манифест — в git, видно, кто что принял |
| Г. Брать из Wikidata и связи «стимулировало» | — | Такого свойства нет; P737 запрещён спецификацией `ontology-extraction` | — |

Выбрано: **В**. Чем платим: Lead размечает манифест вручную. Костыли, которых избегаем: «временное» массовое заведение без проверки.

### 3. Генерация связей моделью

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Новый промпт «контекст эпохи» с механизмом и новыми событиями | Богаче результат | Нужна правка `prompts/__init__.py` (файл Lead'а); новые сущности от модели требуют своей проверки | Новый поток, новые лимиты |
| Б. Существующая достройка графа по рецепту `context` от события | Ноль новых промптов, вызов модели — только по кнопке, под лимитом `graph` | Все проверки модели уже есть (типы рецепта, существующие сущности, отклонённые, сохранение `generated`) | Механизма нет; модель не может предложить отсутствующее событие |

Выбрано: **Б**. Чем платим: сгенерированные связи без механизма; механизм и новые события — пункт «требует согласования Lead'а». Костыли, которых избегаем: правка чужого файла, применение ответа модели без проверки.

### 4. Контекст на карте

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Линии от события к стимулированным | Наглядно | Противоречит решению владельца «линии только между людьми, между стратами — нет» (synchro-map) | Шум на плотной карте |
| Б. Подсветка стимулированных при выборе события | Одно поле в ответе | Соответствует «Выбор на карте» | Без новых элементов раскладки |

Выбрано: **Б**.

### 5. Вид события

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Оставить пять видов, экономику показывать по механизму | Ноль правок реестра | Группировка блока по механизму связи, а не по виду события: у события может быть несколько механизмов — оно попадает в несколько групп | Путано |
| Б. Добавить `economic` и `social` в `EVENT_KINDS` | Две строки данных и названия | Дозагрузка значений списка уже поддержана (`_add_missing_defaults`) | Фильтр карты «вид события» получает два значения |

Выбрано: **Б**. Чем платим: тип `EventKind` клиента и `ontology.*.json` правятся (тест-сверка с реестром уже есть).

### Клавиатура и доступность

- Блок — `<section aria-labelledby>`; виды — `role="group"` с `aria-pressed`; «Только проверенные» — `<input type=checkbox>` с подписью.
- События — `<h4>` с годом; связи — список; порядок Tab: вид → событие → связи → «Достроить».
- Пометка «не проверено» — текст, а не только пунктир; живая область объявляет «Добавлено N связей» после достройки.

## Функциональные сценарии

1. **Почему наукоучение.** Читатель в карточке «наукоучения» видит «Исторический контекст: Французская революция · политический» → нажимает событие → карточка революции → «На что повлияло».
2. **Обстановка эпохи.** `/epochs/<Просвещение>` → «Контекст эпохи» → «Экономика» → «Южноморский пузырь», связей нет → «Достроить контекст» → поток графа → новая связь с пометкой «не проверено» → оператор позже подтверждает её на странице проверки → пометка исчезает.
3. **На карте.** На карте выбирает «Французскую революцию» → выделены Фихте и его «Основа общего наукоучения», линий от события нет.
4. **Lead пополняет события.** `epoch_context harvest` → в `sources/epoch_context.yaml` кандидаты по эпохам → Lead ставит `accepted`/`rejected` → `apply --dry-run` → `apply` → события появились в справочнике (тип «События»), на карте (страта событий) и в контексте эпохи; связей «стимулировало» у них нет, пока их не найдёт извлечение, модель или оператор.

## Контракты для 2.4 (гео-таймлайн)

- `GET /v1/context?from=&to=` — события окна времени с датами, видом, местами (`places[].id/label/wikidata`) и связями «стимулировало». Это основной поток «что происходило где и когда» для 2.4.
- `GET /v1/context?epoch=` — то же в рамке эпохи.
- Места персон (`lived_in`) этим изменением не отдаются: 2.4 берёт их из карточки персоны или добавляет своё поле в `/v1/map` в своём изменении. Координат мест в онтологии нет — 2.4 получает их по `wikidata` места своим обогащением.
- Поля контракта только дописываются; удаление или переименование — через изменение OpenSpec с упоминанием 2.4.

## Риски

- **Мало связей у Lead'а.** Извлечение без подсказки механизма будет давать `stimulated` редко и без механизма. Митигирует пункт «на согласование» (уточнители в `x-relations`) и достройка; до согласования — честное «механизм не указан».
- **Порог достройки** (`min_edges=5`) может не запустить модель у «богатого» события — это существующее правило графа; на странице поясняется уведомлением из потока.
- **Совпадение названий при достройке:** `_proposal` отбрасывает неоднозначные названия (`ambiguous_entity`) — часть предложений модели пропадёт; это осознанная строгость.
- **Таблица классов P31** неполна — события без вида попадают в «Прочее»; таблица — данные, пополняется без кода.
- **Регрессия карты:** выбор события меняет подсветку — проверки `tests/web/test_map.py`; эталоны снимков — Lead/CI.
- Машина агента не тянет e2e и Docker — их прогоняют CI и Lead.

## Безопасность

- Модель: только через существующий поток графа (проверки сервера, лимиты, сохранение со статусом `generated`); механизм от модели не принимается.
- Wikidata: сеть только в команде оператора; адреса строит код из QID (`^Q\d+$`); из ответа берутся только даты, классы, метки и QID места; заведение — только по решению человека в манифесте.
- Закрытые источники: в ответе контекста нет подтверждений и атрибуций закрытых источников; цитаты не отдаются вообще.
- Журнал без личных данных и без текста запросов.
