## MODIFIED Requirements

### Requirement: Структурированный вывод по реестру

Модель SHALL возвращать сущности и утверждения по схеме, собранной из реестра: только допустимые типы, концы и уточнители. При неуверенности в частном типе SHALL выбираться общий тип по иерархии. Ответ не по схеме SHALL отбрасываться после повторов с записью в журнал.

**Массив `entities`.** Схема SHALL содержать необязательный массив `entities` — упомянутые сущности. У каждого элемента:
- `name` — название, как в утверждениях;
- `type` — тип из реестра;
- написания `ru`, `en`, `original`;
- необязательная датировка `dating`: текст, абзац, цитата.

Ответ без `entities` SHALL обрабатываться как прежде. Промпт SHALL получать язык фрагмента (по языку его абзацев) и содержать правила:
- язык названий;
- что не считается названием (номера, фразы, местоимения, роли);
- «извлекай годы, если они названы».

**Инвариант:** для любого ответа модели в онтологию попадают только типы, концы и уточнители из реестра. Поля `entities` никогда не создают утверждений других типов, кроме `lifespan` и `dating`.

#### Scenario: Неуверенность в типе

- **WHEN** модель не уверена, развивает автор чужую идею или переосмысляет её
- **THEN** утверждение записывается с типом «испытал влияние»

#### Scenario: Схема с сущностями и датировкой

- **WHEN** запускается извлечение фрагмента
- **THEN** в запросе к шлюзу `json_schema` содержит необязательный массив `entities` с полями `name`, `type`, `ru`, `en`, `original`, `dating`; в `required` корня только `statements`; в данных запроса поле `language` равно преобладающему `lang` абзацев фрагмента
- **AND** в журнале `knowledge.extraction.fragment` с `run_id`

#### Scenario: Тип вне реестра в сущностях

- **WHEN** ответ модели прошёл шлюз, но элемент `entities` имеет тип `deity`, которого нет в реестре (проверка сервера не полагается на проверку схемы шлюзом)
- **THEN** элемент не используется: по нему не создана сущность и не записана датировка; прочие элементы и утверждения записаны
- **AND** в журнале `knowledge.extraction.dropped` с `reason="entity:type"`

#### Scenario: Ответ без сущностей

- **WHEN** модель возвращает только `statements`, без `entities`
- **THEN** утверждения записываются как прежде, новые сущности созданы с языком названия по письменности
- **AND** в журнале `knowledge.extraction.fragment` с `created`, равным числу записанных утверждений

### Requirement: Нормализация сущностей

Упомянутые моделью сущности SHALL привязываться к существующим по названиям, вариантам, типу и датам. **Привязка по всем написаниям.** Если модель дала элемент `entities`, кандидаты SHALL искаться по всем его написаниям: `name`, `ru`, `en`, `original`.

Новая сущность SHALL создаваться, только если подходящей нет, выполнен критерий дробности из реестра и название прошло проверку названия. Неоднозначная привязка SHALL уходить на проверку, а не выбираться наугад.

**Инвариант:** для любого ответа модели сущность, найденная хотя бы по одному написанию элемента, не дублируется новой сущностью. Неоднозначная привязка всегда даёт пункт очереди проверки, а не выбор.

#### Scenario: Привязка

- **WHEN** модель упоминает «Хьюма»
- **THEN** утверждение привязывается к существующей персоне «Юм»

#### Scenario: Неоднозначность

- **WHEN** модель упоминает «Бэкона» в главе без явного контекста
- **THEN** привязка уходит в очередь проверки

#### Scenario: Привязка по английскому написанию

- **GIVEN** персона «Locke» без русского названия
- **WHEN** модель упоминает «Локк» и даёт элемент `{name: "Локк", type: "person", ru: "Локк", en: "Locke"}`
- **THEN** утверждение привязано к существующей персоне, новой персоны нет
- **AND** в журнале `knowledge.entity.renamed` с её `entity_id` и нет `knowledge.entity.created` с `type="person"`
