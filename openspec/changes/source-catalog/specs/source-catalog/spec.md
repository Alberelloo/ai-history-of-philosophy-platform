## ADDED Requirements

### Requirement: Каталог источников в репозитории

Список источников SHALL храниться в репозитории в файле `sources/catalog.yaml` вместе с JSON Schema. Запись описывает одно издание: постоянный идентификатор, ссылку на страницу источника, адаптер, вид, метаданные с сайта, правки человека, лицензию с доказательством, статус одобрения и правило публикации. Тексты источников в репозитории MUST NOT храниться. Проверка каталога SHALL находить нарушения схемы, повторы идентификаторов и ссылок, а также одобренные записи без лицензии.

#### Scenario: Каталог проходит проверку
- **WHEN** в каталоге записи без нарушений
- **THEN** проверка завершается успешно и сообщает число записей по статусам

#### Scenario: Повтор идентификатора
- **WHEN** у двух записей один идентификатор
- **THEN** проверка падает и называет идентификатор

#### Scenario: Одобренная запись без основания лицензии
- **WHEN** запись одобрена, а основание лицензии не указано
- **THEN** проверка падает и называет запись и поле

### Requirement: Добавление источника по ссылке

Команда `add` SHALL по ссылке на страницу источника выбрать адаптер сайта и собрать метаданные: название, авторов, язык, год, переводчика. Ещё она собирает прямые ссылки на файлы по порядку и подсказку о лицензии с сайта. Годы смерти авторов адаптер SHALL брать из данных сайта или Wikidata. Новая запись SHALL получать статус черновика. Если ссылка уже есть в каталоге, команда MUST NOT добавлять повтор.

#### Scenario: Книга с Project Gutenberg
- **WHEN** оператор добавляет ссылку на книгу Project Gutenberg
- **THEN** в каталоге появляется черновик с названием, автором, годами его смерти, языком и ссылкой на EPUB

#### Scenario: Ссылка уже в каталоге
- **WHEN** оператор добавляет ссылку, которая уже есть в каталоге
- **THEN** команда сообщает идентификатор существующей записи и ничего не меняет

#### Scenario: Сайт без адаптера
- **WHEN** ссылка ведёт на сайт, для которого нет адаптера
- **THEN** создаётся запись с адаптером прямой ссылки, а метаданные ждут ручного заполнения

### Requirement: Метаданные с сайта и правки человека

Метаданные, собранные адаптером, и правки человека SHALL храниться в записи раздельно. Итоговое значение каждого поля — правка человека, если она есть, иначе значение с сайта. Повторный сбор метаданных SHALL перезаписывать только данные с сайта и показывать, что изменилось. Изменение метаданных MUST NOT создавать новую версию текста.

#### Scenario: Правка человека важнее сайта
- **WHEN** у записи в правках указано другое название, а сайт отдаёт прежнее
- **THEN** в библиотеке источник называется так, как указано в правках

#### Scenario: Сайт изменил метаданные
- **WHEN** после повторного сбора у источника изменился год издания
- **THEN** команда показывает старое и новое значение, а после синхронизации меняется описание источника без новой версии текста

### Requirement: Синхронизация каталога с библиотекой

Команда `sync` SHALL обрабатывать только одобренные записи. Новую запись она регистрирует в учёте источников и связывает с идентификатором каталога. У связанной записи обновляет описание и, если изменились ссылки, файлы. Затем запускает обработку и применяет правило публикации. Повторный запуск без изменений MUST NOT создавать источники и версии. Итог SHALL выводиться таблицей: запись, состояние, версия, проблема.

#### Scenario: Первая синхронизация
- **WHEN** в каталоге одобренная запись, которой нет в библиотеке
- **THEN** источник регистрируется, обрабатывается и связывается с идентификатором записи

#### Scenario: Повторная синхронизация
- **WHEN** синхронизацию запускают второй раз без изменений
- **THEN** новых источников и версий нет, у записи итог «изменений нет»

#### Scenario: Черновик не обрабатывается
- **WHEN** запись в статусе черновика
- **THEN** синхронизация её пропускает и отмечает «ждёт одобрения»

### Requirement: Правило публикации обновлений

Новая версия источника SHALL публиковаться автоматически только при всех условиях:
- в записи указано правило «автоматически»;
- все проверки пройдены и решение по качеству распознавания не нужно;
- удалено не больше 2% абзацев опубликованной версии.

Версия с тем же текстом, что у опубликованной, SHALL публиковаться автоматически при любом правиле. Остальные версии ждут решения оператора, и система SHALL сообщать о них предупреждением. Первая версия источника с правилом «автоматически» публикуется по тем же условиям.

#### Scenario: Мелкая правка текста
- **WHEN** на сайте исправили опечатку и запись публикуется автоматически
- **THEN** новая версия публикуется сама, ссылки на абзацы продолжают работать

#### Scenario: Крупное изменение
- **WHEN** в новой версии удалено больше 2% абзацев
- **THEN** опубликованная версия остаётся, новая ждёт решения, выдаётся предупреждение

#### Scenario: Изменилась только служебная часть файла
- **WHEN** файл изменился, а текст абзацев тот же
- **THEN** версия публикуется без участия оператора

### Requirement: Снятие источника через каталог

Источник SHALL сниматься с публикации, если его запись помечена как отозванная. Если запись удалили из каталога без такой пометки, проверка каталога SHALL падать: по списку выданных идентификаторов видно, что запись исчезла.

#### Scenario: Запись отозвана
- **WHEN** запись помечена как отозванная и запущена синхронизация
- **THEN** источник снимается с публикации, а ссылки на его абзацы сообщают, что источник недоступен; если запись снова одобрить, прежняя публикация возвращается

#### Scenario: Запись удалили
- **WHEN** запись удалили из каталога
- **THEN** проверка падает и предлагает пометить запись отозванной

### Requirement: Бережная загрузка с сайтов

Загрузчик SHALL представляться User-Agent с названием и адресом проекта. Он SHALL делать не больше одного запроса в секунду на сайт, соблюдать robots.txt и повторять временные ошибки с растущей паузой. Загрузка больше заданного размера SHALL прерываться. Адрес почты пользователя MUST NOT передаваться сайтам.

#### Scenario: Запрет в robots.txt
- **WHEN** robots.txt сайта запрещает путь к файлу
- **THEN** файл не загружается, а итог записи называет причину

#### Scenario: Временная ошибка
- **WHEN** сайт один раз отвечает 503, а затем 200
- **THEN** файл загружается со второй попытки

### Requirement: Проверка обновлений без лишней загрузки

Плановая проверка SHALL запрашивать файлы условно, передавая ETag и Last-Modified прошлого ответа. На ответ «не изменилось» используется сохранённый снимок, и новая версия не создаётся. Если файл изменился, решение принимается по хешу содержимого. Перед хешированием адаптер SHALL убирать из файла служебные части сайта, которые меняются без изменения текста.

#### Scenario: Сайт ответил «не изменилось»
- **WHEN** сайт отвечает 304 на условный запрос
- **THEN** файл не скачивается заново и версия не создаётся

#### Scenario: Изменилась служебная шапка Gutenberg
- **WHEN** у файла Project Gutenberg изменилась только дата в служебной шапке
- **THEN** хеш очищенного файла прежний и версия не создаётся

### Requirement: Недоступный или переехавший источник

Если файл не загружается (ошибка сети, 404 или 5xx после повторов), опубликованная версия SHALL оставаться: снимок хранится у нас. Система SHALL считать неудачи подряд и после трёх выдавать предупреждение. Автоматически снимать источник с публикации она MUST NOT. При постоянном перенаправлении система SHALL запоминать конечный адрес и выдавать предупреждение «обновите ссылку в каталоге».

#### Scenario: Сайт пропал
- **WHEN** ссылка на файл три проверки подряд отвечает 404
- **THEN** источник остаётся опубликованным, выдано предупреждение, в итоге записи указано число неудач

#### Scenario: Сайт переехал
- **WHEN** ссылка отвечает постоянным перенаправлением на новый адрес
- **THEN** файл загружается по новому адресу, конечный адрес сохраняется, выдано предупреждение
