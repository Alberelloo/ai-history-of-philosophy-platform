## ADDED Requirements

### Requirement: Качество персон

Сущность типа «персона» SHALL создаваться только для лица, названного по имени. MUST NOT становиться персонами:
- местоимения и служебные слова (`some`);
- обращения (`your Lordship`);
- роли и описания (`поэт`, `мальчик`, `blind mathematician`, `the author of …`);
- группы (`children`, `logicians`);
- неодушевлённые предметы;
- склейки двух имён (`Kepler and Des Cartes`).

Сервер SHALL отклонять такие названия правилом проверки названий (`entity-naming`, правила `sentence`, `not_a_name`, `stopword`) с событием `knowledge.entity.rejected` и `type="person"`. Утверждения с отклонённой персоной отбрасываются с событием `knowledge.extraction.dropped`. Промпт извлечения SHALL определять, кто считается персоной, и приводить отрицательные примеры.

**Инвариант:** для любого ответа модели ни у одной персоны, созданной запуском, основное название не даёт причины отказа правила названий. Каждое отклонённое предложение персоны даёт ровно одно событие `knowledge.entity.rejected` с `type="person"`. Персоны, созданные до этого изменения, приводит миграция (`ontology-migration`).

#### Scenario: Мусорная персона

- **WHEN** модель предлагает персону «children» в утверждении
- **THEN** сущность не создаётся, утверждение отброшено
- **AND** в журнале `knowledge.entity.rejected` ровно с полями `{type: "person", label: "children", reason: "not_a_name"}` и `knowledge.extraction.dropped`

#### Scenario: Склейка

- **WHEN** модель предлагает персону «Kepler and Des Cartes»
- **THEN** сущность не создаётся
- **AND** в журнале `knowledge.entity.rejected` с `reason="not_a_name"`

#### Scenario: Определение персоны в промпте

- **WHEN** запускается извлечение фрагмента
- **THEN** текст шаблона `ontology.extract` в перехваченном запросе к шлюзу содержит определение персоны и отрицательные примеры «your Lordship», «blind mathematician», «children»
- **AND** в журнале `knowledge.extraction.fragment`

#### Scenario: Инвариант качества персон

- **WHEN** на произвольных предложениях персон выполняется извлечение. Генератор возвращает пары «название, ожидаемый исход», собранные из частей:
  - имена с частицами и без;
  - роли, обращения, группы, местоимения;
  - склейки;
  - строчные описания в любом регистре
- **THEN** создана ровно та персона, для которой ожидался успех; на каждое отклонённое предложение — одно `knowledge.entity.rejected` с `type="person"` и ожидаемой причиной; число созданных персон равно числу `knowledge.entity.created` с `type="person"`

### Requirement: Слияние вариантов персоны

Одно лицо в разных написаниях (английском, русском, транслитерации) SHALL становиться одной сущностью. У двух сущностей не бывает одного QID: внешний идентификатор уникален. Поэтому правило сравнивает пару персон `a`, `b` так.

**Определения.**
- *Нормализованное название* — по `entity-naming`.
- *Даты противоречат*, если у обеих есть основная дата и при допуске 2 года не пересекаются интервалы начала `[earliest_start − 2, latest_start + 2]` или интервалы конца `[earliest_end − 2, latest_end + 2]`. Если хотя бы у одной даты нет, противоречия нет.

**Правило `same_person`** — проверки по порядку, первая сработавшая даёт вердикт:

1. не обе — персоны → `apart:type`;
2. у обеих есть QID (значит, разные) → `apart:qid`;
3. человек закрыл пункт `duplicate` по этой паре решением «разные» → `apart:decided`;
4. даты противоречат → `review:dates`;
5. QID одной подтверждён человеком для другой (запись манифеста QID, `qid_taken`) → `merge:qid_confirmed`;
6. нормализованное основное название одной совпадает с нормализованным основным названием другой (на любом языке), в том числе однословное («Hume»×2, «Сократ»×3) → `merge:name`;
7. один элемент ответа модели дал оба написания, и каждое нашло ровно одну из двух сущностей → `merge:model_pair`;
8. нормализованное основное название одной совпадает с нормализованным вариантом другой: название из одного слова → `review:single_name`, иначе → `review:variant`;
9. иначе → `apart:none`.

**Компоненты.** При обходе многих персон строится граф: ребро — пара с вердиктом `merge:*`. Для каждой связной компоненты:
- если в ней два и больше разных QID или у какой-либо её пары вердикт `apart:qid`, `apart:decided` или `review:dates`, то ни одно слияние в компоненте MUST NOT выполняться. Каждое её ребро уходит в очередь проверки `duplicate` с `reason="review:qid_cluster"` или `"review:dates"`, кроме пар с решением «разные»;
- иначе вся компонента сливается в одну сущность. Пара с вердиктом `review:*`, обе стороны которой оказались в одной сливаемой компоненте, в очередь не ставится.

Пара, по которой человек уже закрыл пункт `duplicate` решением «разные», повторно в очередь MUST NOT ставиться.

Разбиение на компоненты и итог MUST NOT зависеть от порядка входа.

**Оставшаяся сущность** — та, у которой есть QID. Иначе та, на которую больше ссылок: субъект и объект утверждений плюс атрибуции-автор. Иначе с меньшим идентификатором. При этом:
- QID SHALL сохраняться;
- после слияния у сущности SHALL быть ровно одно основное название: русское, если оно есть у любой из сторон (правило языка `entity-naming`), иначе основное оставшейся. Все прочие бывшие основные обеих сторон становятся вариантами. Виды названий обеих сторон пишутся в запись слияния, чтобы отмена вернула их полностью;
- утверждения и атрибуции переносятся по правилу слияния с перенаправлением.

**Журнал.** Поле `reason` событий слияния — единый перечень с префиксом, тот же, что вердикт правила (О11); значений без префикса нет ни в одном событии.
- Слияние пишет `knowledge.entity.merged` с `reason` ∈ {`merge:qid_confirmed`, `merge:name`, `merge:model_pair`, `merge:review`}. `merge:review` — человек закрыл пункт очереди решением «слить».
- Пара в очереди пишет `knowledge.entity.merge_proposed` с полями `kept`, `removed`, `reason` ∈ {`review:dates`, `review:variant`, `review:single_name`, `review:qid_cluster`, `review:qid_candidate`, `review:qid_taken`}. Две последние причины ставит команда QID (`entity-dating`, «Подтверждение QID персон и произведений»).

**Транслитерации** без общего написания («Гомер»/«Омир», «Горгий»/«Горгиас») SHALL сливаться через решение человека в манифесте QID. Человек подтверждает (`accepted`) для одной персоны QID, который уже стоит у другой. Это доказательство `merge:qid_confirmed`. Пока решения нет, пара SHALL стоять в очереди `duplicate`.

**Инвариант:** для любого набора персон и любого порядка обхода:
- слиты ровно компоненты, допустимые по правилу;
- ни одна пара с разными QID не оказалась в одной сущности;
- у каждой оставшейся не больше одного QID и ровно одно основное название — русское, если русское основное было у любой стороны компоненты;
- результат (разбиение, оставшиеся, очередь) одинаков при любой перестановке входа.

#### Scenario: Слияние вариантов

- **GIVEN** персона «Locke» с QID Q9353 и утверждением «Locke — автор „An Essay Concerning Human Understanding“» и персона «Локк» без QID с утверждением «Локк — член группы „Эмпиризм“»
- **WHEN** модель в одном элементе называет `{name: "Локк", type: "person", ru: "Локк", en: "Locke"}`
- **THEN** остаётся одна сущность — бывшая «Locke» (с QID): основное `ru` «Локк», вариант `en` «Locke», внешний QID Q9353; оба утверждения при ней; запрос по идентификатору «Локк» отдаёт её
- **AND** в журнале `knowledge.entity.merged` с `reason="merge:model_pair"`, `statements=1`

#### Scenario: Общее основное название

- **GIVEN** три персоны «Berkeley» без QID и без дат (однословное основное название сливается, О13)
- **WHEN** запускается слияние вариантов
- **THEN** одна персона «Berkeley» со всеми утверждениями трёх
- **AND** в журнале два `knowledge.entity.merged` с `reason="merge:name"`

#### Scenario: QID подтверждён человеком для другой

- **GIVEN** персона «Hume» с QID Q41568 и персона «Юм» без QID; манифест QID подтверждает Q41568 для «Юм», запуск дат дал `qid_taken`
- **WHEN** запускается слияние вариантов с этим подтверждением
- **THEN** одна персона: основное «Юм», вариант «Hume», QID Q41568
- **AND** в журнале `knowledge.entity.merged` с `reason="merge:qid_confirmed"`

#### Scenario: Транслитерация

- **GIVEN** персона «Гомер» с QID Q6691 и утверждением «Гомер — автор „Илиады“», персона «Омир» без QID с утверждением «Омир упомянут Платоном»; в манифесте QID для «Омир» `wikidata: Q6691`, `decision: accepted`
- **WHEN** запущен `apply` команды QID, затем слияние вариантов с подтверждениями
- **THEN** одна сущность — бывшая «Гомер»: основное «Гомер», вариант «Омир», QID Q6691, оба утверждения при ней; запрос по идентификатору «Омир» отдаёт её
- **AND** в журнале `knowledge.life_dates.skipped` с `reason="qid_taken"` и `knowledge.entity.merged` с `reason="merge:qid_confirmed"`

#### Scenario: Транслитерация без решения человека

- **GIVEN** те же «Гомер» (Q6691) и «Омир»; `suggest` нашёл для «Омир» кандидата Q6691, решения нет (`pending`)
- **WHEN** запущены `suggest` и слияние вариантов
- **THEN** обе сущности остаются; в очереди проверки пункт `duplicate` с парой «Гомер»/«Омир»
- **AND** в журнале `knowledge.entity.merge_proposed` с `reason="review:qid_candidate"` и нет `knowledge.entity.merged`

#### Scenario: Тёзки

- **GIVEN** две персоны с основным названием «Бэкон» без QID и без дат: у одной вариант «Роджер Бэкон», у другой «Фрэнсис Бэкон»; пункт `duplicate` по их паре человек закрыл решением «разные»
- **WHEN** запускается слияние вариантов
- **THEN** обе остаются, нового пункта очереди нет
- **AND** в журнале нет `knowledge.entity.merged` и `knowledge.entity.merge_proposed`

#### Scenario: Разные QID

- **GIVEN** персоны «Бэкон» с QID Q37388 и «Бэкон» с QID Q192010
- **WHEN** запускается слияние вариантов
- **THEN** обе остаются, слияния нет, пункта очереди нет
- **AND** в журнале нет `knowledge.entity.merged`

#### Scenario: Транзитивная компонента с двумя QID

- **GIVEN** персоны «Hume» (Q1), «Hume» (без QID) и «Hume» (Q2)
- **WHEN** запускается слияние вариантов, в любом порядке перечисления
- **THEN** все три остаются; в очереди проверки два пункта `duplicate` (пары с сущностью без QID)
- **AND** в журнале два `knowledge.entity.merge_proposed` с `reason="review:qid_cluster"` и нет `knowledge.entity.merged`

#### Scenario: Противоречащие даты

- **GIVEN** персоны «Berkeley» (1685–1753) и «Беркли» (1885–1953), модель назвала их одним элементом
- **WHEN** выполняется извлечение
- **THEN** слияния нет, в очереди проверки пункт `duplicate` с этой парой
- **AND** в журнале `knowledge.entity.merge_proposed` с `reason="review:dates"`

#### Scenario: Даты у одной стороны

- **GIVEN** «Berkeley» (1685–1753) и «Berkeley» без дат
- **WHEN** запускается слияние вариантов
- **THEN** одна персона с датами 1685–1753
- **AND** в журнале `knowledge.entity.merged` с `reason="merge:name"`

#### Scenario: Совпал только вариант

- **GIVEN** персоны «Фрэнсис Бэкон» с вариантом «Бэкон» и «Бэкон» (основное), без QID и дат; персоны «Thomas Reid» с вариантом «Томас Рид» и «Томас Рид» (основное)
- **WHEN** запускается слияние вариантов
- **THEN** слияний нет, два пункта `duplicate` в очереди
- **AND** в журнале `knowledge.entity.merge_proposed` с `reason="review:single_name"` (однословное «Бэкон») и с `reason="review:variant"` (двусловное «Томас Рид»)

#### Scenario: Инвариант слияния

- **WHEN** на произвольных кластерах персон запускается слияние вариантов, вход перечисляется в двух случайных перестановках. Генератор возвращает персоны и ожидаемое разбиение, построенное по правилу из известных частей:
  - написания ru/en/транслит;
  - QID: нет, один, разные;
  - даты: равные, в пределах допуска, противоречащие, у одной стороны;
  - транзитивные цепочки через сущность без QID;
  - подтверждения человека (`qid_confirmed`) для пар без общего написания
- **THEN**
  - разбиение равно ожидаемому и одинаково в обеих перестановках;
  - ни одна пара с разными QID не слита;
  - у каждой оставшейся не больше одного QID и одного основного названия на язык;
  - на каждое слияние — одно `knowledge.entity.merged`, на каждую пару очереди — одно `knowledge.entity.merge_proposed`
