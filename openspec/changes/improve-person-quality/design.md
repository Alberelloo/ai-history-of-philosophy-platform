# Design

## Контекст (факт кода)

- `Entities.merge(kept, removed)` переносит такие данные:
  - `names`;
  - `statements.subject` и `statements.object`;
  - `external_ids`;
  - `mentions`.

  Затем ставит `redirect_to` и пишет `merges.moved` (id перенесённого) для `undo_merge`. Чего она не делает:
  - **не трогает** `attributions.who` (`who_kind="entity"`), то есть атрибуции «так считает Кант»;
  - **не пересчитывает** `statements.key`. Ключ включает id концов (`Statements._key`), поэтому повтор после слияния не объединяется, а новое утверждение с оставшейся сущностью не найдёт старое;
  - **оставляет** два основных названия на одном языке;
  - **не пересчитывает** `primary` (`Statements._update_primary` живёт в `Statements`);
  - **не переносит** портреты (`portraits.entity_id`, `UniqueConstraint(entity_id, phash)`).
- `Entities.duplicate_candidates` — пары одного типа, у которых совпадает последнее слово нормализованного названия и равны `primary.dates`. Сравнение всех со всеми: O(n²), при 1889 сущностях около 1,8 млн пар. После изменения пары перебираются внутри групп «тип + последнее слово». Группа больше `entities.MAX_LAST_WORD_GROUP = 200` не перебирается: пишется `knowledge.entity.duplicate_group_capped` (`type`, `size`, `limit`, без названий), и потеря видна в журнале (О18). Совпадения полных названий ищутся по индексу и для неё.
- `ReviewQueue.resolve_duplicate` вызывает `entities.merge`.
- Из `improve-extraction-naming` берутся:
  - `naming.check_name` (`not_a_name`, стоп-список), действует при создании;
  - `EntityItems.resolve`, где кандидаты ищутся по всем написаниям элемента.

## Контракты

### `knowledge/dedupe.py` (новый)

```python
@dataclass(frozen=True)
class Verdict:  kind: Literal["merge", "review", "apart"]; reason: str
def same_person(a: Entity, b: Entity, *, paired_by_model=False, qid_confirmed=False, decided_apart=False) -> Verdict
def choose_kept(component: list[Entity], counts: Mapping[str, int]) -> str
def plan(entities: Iterable[Entity], pairs_by_model=(), confirmed=(), distinct=()) -> Plan   # чистая функция; distinct — пары, закрытые «разные»
@dataclass(frozen=True)
class Plan: merges: list[tuple[str, list[str], str]]; review: list[tuple[str, str, str]]   # (kept, removed[], reason), (a, b, reason)
```

`Entity` — `{id, type, names, primary, externals}`. Правило `same_person` по шагам 1–9 и правило компонент заданы в спецификации `person-quality` и здесь не повторяются. Изменения после ревью (О9):
- **`merge:qid` убран.** Первичный ключ `external_ids (system, value)` не допускает один QID у двух сущностей. Его место заняло `merge:qid_confirmed`: человек подтвердил в манифесте QID для сущности, у которой его нет, а QID уже у другой (`qid_taken` в `add-wikidata-life-dates`);
- **компоненты.** `plan` строит граф по рёбрам `merge:*` (индекс по нормализованным основным названиям, плюс пары от модели и подтверждения) и находит связные компоненты объединением множеств. Компонента с ≥ 2 QID или с парой `apart:qid`/`review:dates` целиком уходит в очередь. Это закрывает обход запрета QID по транзитивности: «Hume»(Q1)~«Hume»~«Hume»(Q2). Итог зависит только от множества входа: компоненты, `choose_kept` по компоненте и сортировка вывода по id;
- **даты у одной стороны** — не противоречие;
- **однословные дубли** (О13, отменяет «однословные → review» из О12): совпавшее нормализованное основное название сливается `merge:name` и при одном слове, если нет разных QID, даты не противоречат и человек не решил «разные». На стенде почти все дубли однословные без дат (Hume, Newton, Reid, Descartes, Сократ, Теэтет), спека владельца считает их дублями и требует А4 = 0. Ложное слияние тёзок обратимо (`undo_merge`), видно в `plan` до записи и предотвращается решением «разные» (`apart:decided`) или разными QID. Однословное основное, совпавшее лишь с вариантом другой, даёт `review:single_name`;
- **`reason` событий** равен строке вердикта (`merge:name`, `review:dates`): один перечень во всех spec и design (О11).

`choose_kept` выбирает оставшуюся по порядку:
- сущность с QID;
- иначе ту, у которой больше ссылок (утверждения как субъект и объект плюс атрибуции `who`);
- иначе меньший id.

Сложность `plan` — O(n · названий) по индексу, без перебора всех пар.

`Dedupe(statements, review).run(*, dry_run=False, run_id=None, confirmed=()) -> {merged, proposed, apart}`. Здесь `confirmed` — пары `(entity, holder)` из `qid_taken`. Метод — — «запуск слияния вариантов» из сценариев. Он обходит персон по индексу и сливает пары с вердиктом `merge` через `merge_entities`, а пары `review` ставит в очередь. Сухой прогон только считает. Своего CLI у него нет: оператор запускает его шагом миграции (`migrate-ontology-quality`) или из юнит-кода. Слияния запуска записываются в `merges` с `run_id` в `moved.run_id`, чтобы миграция могла откатить их по запуску.

### `Statements.merge_entities(kept, removed, reason) -> merge_id` (новый, `statements.py`)

`Entities.merge` остаётся низкоуровневым переносом строк. Он дополняется переносом `attributions.who`, `portraits` и правилом основного названия. Свёртка и пересчёт живут в `Statements`, потому что ключ, согласие и `primary` принадлежат ему.

1. `Entities.merge` переносит:
   - названия (О12): после переноса у оставшейся ровно одно основное. Выбирается русское основное любой из сторон (при двух русских — оставшейся), иначе основное оставшейся. Все прочие бывшие основные обеих сторон становятся `variant`. Прежний вид каждой изменённой строки обеих сторон пишется в `moved.kinds` (`{name_id: kind}`), отмена возвращает их все. Точные повторы названий `(lang, normalized)` не дублируются: строка удалённой переносится, но получает вид `variant`;
   - `statements.subject` и `statements.object`;
   - `external_ids` — перенесённые пишутся в `moved.externals` (исправление: сейчас `undo_merge` их не возвращает, ревью п. 3);
   - `mentions`;
   - `attributions.who`, где `who_kind="entity"` и `who=removed` (`moved.attributions_who`);
   - `portraits`. При конфликте уникальности (одинаковый `phash`) портрет удалённой остаётся за ней, это записывается в `moved.portraits_kept`.

   Кэш `graph_extensions` удалённой удаляется.
2. Для каждого перенесённого утверждения ключ пересчитывается (`_key`). Старый ключ пишется в `moved.keys`.
3. Если новый ключ совпал с ключом другого действующего утверждения (`survivor`), выполняется **свёртка**:
   - атрибуции и подтверждения повтора переносятся на `survivor`; точные повторы атрибуции `(who_kind, who, stance)` не дублируются, а помечаются в `moved.folded[].skipped`;
   - полная строка повтора сохраняется в `moved.folded[].row`, сама строка удаляется;
   - согласие `survivor` пересчитывается, в журнал утверждения (`journal`) пишется запись «свёрнуто при слиянии».
4. `_update_primary(kept, "lifespan" | "dating" | "description")`.
5. **Петли.** Утверждение, у которого после переноса `subject == object`, остаётся в базе как есть. Снимок не показывает утверждения-связи с `subject == object`. Число петель пишется в `moved.loops`, `integrity` (миграция) считает их отдельно от потерь.
6. Событие `knowledge.entity.merged` с полями `kept`, `removed`, `reason`, `statements`, `attributions`, `folded`, `loops`.

`Statements.undo_merge(merge_id)` выполняет шаги в обратном порядке:
- восстанавливает строки свёрнутых утверждений;
- возвращает атрибуции и подтверждения на них;
- возвращает ключи, виды названий, `attributions.who`, портреты, `external_ids` (`moved.externals`);
- восстанавливает свёрнутые утверждения с прежними id;
- вызывает `Entities.undo_merge`;
- пересчитывает `primary` обеих сущностей.

`ReviewQueue.resolve_duplicate` вызывает `Statements.merge_entities` вместо `entities.merge`. Отдельной копии правила нет.

### Точка в извлечении

В `EntityItems.resolve` (из `improve-extraction-naming`) разбирается случай, когда написания элемента нашли больше одного кандидата-персоны:
- для каждой пары вызывается `same_person(..., paired_by_model=True)`, но только для пар, где разные написания элемента нашли разные сущности;
- все пары дали `merge` → `merge_entities` по `choose_kept`, привязка — к оставшейся;
- есть `review` → пункт очереди `duplicate` (`payload.pair`, `payload.reason`), событие `knowledge.entity.merge_proposed`, утверждение уходит по прежней логике неоднозначности;
- `apart` → прежняя логика неоднозначности.

`filling.py` для этого не меняется: точка вызова уже в `EntityItems`.

### Промпт (файл Lead'а, О3)

`ontology.extract` получает абзац: «Персона (`person`) — только названное по имени лицо. Не персона: местоимения, обращения (your Lordship), роли и описания (поэт, blind mathematician, the author of …), группы (children, logicians), неодушевлённое. Два лица — два элемента, не одно». Правку промпта согласует Lead (5.1).

## События журнала

| Событие | Уровень | Поля | Когда |
|---|---|---|---|
| `knowledge.entity.merged` (есть, поля расширены) | info | `kept`, `removed`; новые — `reason` (`merge:qid_confirmed`, `merge:name`, `merge:model_pair`, `merge:review`; единый перечень с префиксом, О11), `statements` (перенесено), `attributions` (перенесено `who` + атрибуций свёрнутых), `folded` (свёрнуто утверждений) | слияние |
| `knowledge.entity.merge_undone` (есть) | info | `kept`, `removed`; новые — `restored` (восстановлено свёрнутых) | отмена |
| `knowledge.entity.merge_proposed` (новое) | info | `kept`, `removed`, `reason` (`review:dates`, `review:variant`, `review:single_name`, `review:qid_cluster`, `review:decided_conflict`, `review:qid_candidate`, `review:qid_taken`) | пара в очередь проверки |
| `knowledge.entity.rejected` (из `improve-extraction-naming`) | warning | `type`, `label`, `reason` | мусорная персона |
| `knowledge.entity.duplicate_group_capped` (новое, О18) | warning | `type`, `size`, `limit` (без названий) | группа «тип + последнее слово» больше предела в `duplicate_candidates` |

Новые поля `knowledge.entity.merged` добавляются в `optional`, `required` прежний: старые вызовы `Entities.merge` событие не ломают.

## Выбор решения

### Слияние вариантов

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Только очередь проверки: каждая пара — человеку | Ноль автоматики, человек на ~15 пар | Правильно, но А4 = 0 зависит от ручной работы | При 10× источников — сотни пар вручную |
| Б. Слияние по совпадению последнего слова (как `duplicate_candidates`) | Просто | Ложные слияния: Бэконы, Миллы | Ошибки тихие, откат ручной |
| В. Правило `same_person` (QID, основные названия, пара от модели, даты) + очередь для сомнительного (выбрано) | Индекс по названиям и QID, O(n) | Одно правило в `dedupe.py` для извлечения и миграции; модель предлагает пару, код проверяет QID и даты | Порог дат и виды доказательств — константы правила; любое слияние откатывается |

**Выбрано В.** Платим тем, что «Гомер»/«Омир» без общего QID остаются в очереди. Костыли, которых избегаем: слияние по подстроке, второе правило тождества в миграции, тихое слияние без события.

### Где свёртка утверждений

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Не сворачивать, скрывать повторы в снимке по содержимому | Без записи в базу | Правило объединения повторов размазано по снимку, карточкам и графу | Каждый новый потребитель должен помнить про повторы |
| Б. Свёртка в `Statements.merge_entities` с архивом строки в `merges.moved` (выбрано) | Одна транзакция на слияние | Ключ, согласие и `primary` у их владельца (`Statements`); `Entities.merge` остаётся переносом строк | Отмена полная по архиву; формат `moved` расширяется ключами, старые записи отменяются как прежде (`get` с умолчаниями) |

## Стратегии для property-тестов (О7, О9)

Инфраструктура (профили, «вход + ожидание», `dump.py`, `mutation_check.py`, запрет сети) — общая, из `improve-extraction-naming`. Стратегии этого изменения — в `tests/knowledge/strategies.py`. Оракул не импортирует `dedupe`.

- `persons_with_variants()` — персоны и **ожидаемое разбиение**. Стратегия сначала выбирает «лица», затем раздаёт каждому 1–4 записи. Из каждого лица в разбиение попадает один блок, если в блоке нет двух QID и противоречащих дат. Иначе ожидается очередь. Части:
  - написания ru/en/транслит, регистр;
  - QID: нет, один на лицо, два на лицо (цепочка через запись без QID);
  - даты: равные, в допуске, противоречащие, у одной стороны.

  Тест прогоняет `Dedupe.run` на двух перестановках входа.
- `ontology_with_duplicates()` — 5–30 сущностей и 0–60 утверждений и **ожидаемое множество содержания** после слияния. В нём:
  - атрибуции `source`, `entity` (в том числе на удаляемую), `common`;
  - подтверждения;
  - повторы, которые совпадут после слияния;
  - петли;
  - упоминания;
  - портреты с одинаковым `phash`;
  - QID у одной стороны.
- `not_persons()` — переиспользует `not_names` с ожидаемой причиной.
- Явные `@example`:
  - «Hume»(Q1) / «Hume» / «Hume»(Q2);
  - разные QID «Бэкон»;
  - даты на границе допуска ±2;
  - петля;
  - повтор с одинаковой атрибуцией.

**Инварианты** (формулировки — в спецификации):
- **Сохранение.** Множество `(resolve(subject), type, resolve(object), value, qualifiers)` после слияния равно ожидаемому без петель. Мультимножество атрибуций `(тройка, who_kind, resolve(who), stance)` не теряет элементов, кроме точных повторов. Подтверждения сохраняются.
- **Отмена.** `dump.dump()` после `undo_merge` равен дампу до слияния.
- **QID.** Ни одна сущность после слияния не содержит записей двух разных QID.
- **Независимость от порядка.** Итог `Dedupe.run` одинаков на перестановках.

## Риски

- Свёртка удаляет строку утверждения, и ссылки на её id снаружи (`statement_views`, `review_samples`, `journal`) повиснут. Поэтому при свёртке выполняется перенаправление: в `merges.moved.folded[].into` хранится `survivor`, а `Statements.get` по свёрнутому id отдаёт `survivor`. Так же устроены перенаправления сущностей: старая ссылка работает.
- Допуск дат 2 года на краях интервалов неопределённости — константа правила. Слишком строгий допуск отправит в очередь персону с годами «1632–1704» и «1632–1705» из разных учебников. Поэтому допуск ненулевой.
