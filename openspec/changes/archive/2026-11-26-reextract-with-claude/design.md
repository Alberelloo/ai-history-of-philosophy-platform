# Design

## Контекст (факт кода на 63a07cc)

- `Filling._extract_fragment` шлёт шлюзу `Filling._schema()` — схему реестра с перечнями (`type`, `subject_type`, `object_type`, `stance`, типы `entities`), шлюз проверяет ответ целиком (`jsonschema`) и после `schema_retries` отдаёт 502. Клиент знаний ждёт 120 с (`knowledge/main.py`), шлюз — до 3 × 3 × 120 с.
- `_store` проверяет абзац, затем `_resolve` создаёт сущности, затем `Statements.add` сверяет цитату (`_norm_quote`: пробелы, `ё`, регистр).
- `start_run` пишет `model="main"`; `finish_run` вызывается только при успехе; `_drop` пишет событие, но в ветке «ответ не 200» не считает.
- `Filling.fragments` режет главу окнами по `fragment_size` абзацев (4).
- Ключ утверждения (`Statements._key`) не даёт двух утверждений, но `_attach` всегда вставляет атрибуции и подтверждения: повтор той же записи удваивает их.

## Контракты

### `knowledge/quotes.py` (новый)

- `normalize(text) -> str` — правило из дельты («Цитата у каждого утверждения»).
- `parts(quote) -> list[str]` — нормализация, снятие обрамляющих кавычек (повторно, пока цитата начинается и кончается `"`/`'`), деление по многоточию (`[...]`, `(...)`, `...`), пустые части отбрасываются.
- `check(quote, text) -> str | None` — `None`, если найдена; иначе код `quote_not_found` или `quote_too_short`. Поиск частей — `str.find` с позиции конца предыдущей части.
- `found(quote, text) -> bool`.
- **Минимум значимого текста.** Цитата целиком принимается, только если в ней есть хотя бы одна буква или цифра (`MIN_WHOLE = 1`); иначе `quote_too_short`. Минимум 10 символов, как у части при многоточии, для цельной цитаты не взят: прежнее правило принимало любую подстроку, и подтверждения боевой базы из одного короткого слова («Бог», «априори», «tabula rasa» — 3–11 символов) при перепроверке изменённого абзаца стали бы потерянными, а потеря существующих должна быть 0 (критерий R6). Порог 1 отсекает ровно то, что ничего не подтверждает: многоточие, тире, знаки препинания и пробелы.

Используют: `Statements._check`, `Statements` при событии библиотеки (перепроверка изменённых абзацев), `Filling` (проверка до сущностей), `dating.check` (цитата датировки). `_norm_quote` и `dating._quote_key` удаляются — правило в одном месте.

### `knowledge/extraction_codes.py` (новый)

Закрытый перечень `CODES` (таблица дельты) и `code_for(reason) -> str`: `entity:type` → `entity_type`, `entity:no_type` → `entity_no_type`, `entity:ambiguous` → `entity_ambiguous`, `entity:<naming.REASONS>` → `entity_invalid`, `dating:<x>` → `dating_<x>`, код из перечня → он же. `Skip` получает необязательный `code`; без него код выводится из `reason`.

### Проверка элемента: `Filling._item`

Чистая функция над элементом ответа и фрагментом (без базы, кроме реестра): возвращает приведённый элемент или бросает `Skip(reason, code)`. Порядок — дельта, «Проверка ответа по утверждениям», шаги 1–7. Абзац и цитата сверяются с текстом окна (тот же текст, что отдаст `internal/paragraphs/{id}`: оба — из библиотеки по одной версии), до `_resolve`. `Statements.add` сверяет ещё раз — защита записи для всех путей.

Код связи вне реестра: `proposed_type` = этот код, тип записи — `influenced_by`, дальше `_fit` (прежнее поведение `proposed_type`).

### Общий путь ответа: `Filling.apply_reply(window, data, source, run_id, reply)`

Одна функция для шлюза и внешнего извлекателя: проверка вида ответа (`reply_invalid`), `EntityItems.index` (элементы `entities`, отказы — через тот же `_drop`), утверждения, датировки, счёт, событие `knowledge.extraction.fragment`. `_extract_fragment` = вызов шлюза + `apply_reply`; `external_extraction.ingest` = чтение файла + `apply_reply`. Валидация не дублируется.

### Учёт отбраковки

`Filling._drop(run_id, reason, code)` — единственное место: событие и счётчик запуска (`dropped`, `drop_reasons`) в памяти; в базу — в конце фрагмента одной записью (`_count`). Нормативное равенство `dropped = Σ drop_reasons = число событий` держится тем, что других мест нет. `EntityItems.index` получает обратный вызов `on_drop` вместо прямого `events.emit`.

`dropped` во фрагменте и запуске теперь включает и отказ элемента `entities` (`entity:type`) — раньше он был только событием. Это следствие «каждая отбраковка считается».

### Жизненный цикл запуска

`start_run(kind, target, *, extractor=None, source_id=None, model=None)`; `finish_run(run_id, *, metrics=None)` пишет `done`, `finished_at`, `fragments`, `duration_seconds`, токены, `cost_usd`, `drop_reasons`; `fail_run(run_id, exc)` пишет `failed`, `failure`, `finished_at`, `drop_reasons`, событие `knowledge.run.failed`. `extract_version` — `try/except BaseException: fail_run; raise`.

Для шлюза: модель — `GET roles/strong` в начале запуска (`model`, `call_budget_seconds`); токены и стоимость — `GET spend?group_by=run_id` в конце (строка запуска, суммы `input_tokens`, `output_tokens`, `cost_usd`).

### Миграция `knowledge:10`

`ALTER TABLE knowledge.filling_runs ADD COLUMN …` для `extractor VARCHAR(20)`, `source_id VARCHAR(100)`, `fragments INTEGER`, `duration_seconds FLOAT`, `input_tokens INTEGER`, `output_tokens INTEGER`, `drop_reasons JSON` (`JSON` в SQLite и Postgres — тип `JSON` есть в обоих; в SQLite хранится текстом), `failure TEXT`. Существующие столбцы пропускаются (свежая база получает их из метаданных в `knowledge:2`) — как `knowledge:9`.

### Фрагмент по объёму (П12)

`Filling(…, fragment_size=30, fragment_chars=3000)`. Окно от `start`: добавлять абзацы, пока длина < `fragment_chars` и абзацев < `fragment_size`. Следующее начало — последний абзац окна (перекрытие) или следующий, если окно из одного абзаца. При коротких текстах и малом `fragment_size` (тесты: `fragment_size=2`) поведение совпадает с прежним делением по числу абзацев, `changed` — прежний.

Почему 3000: у Трубецкого (737 знаков в абзаце) это 4–5 абзацев, как было; у «Заратустры» (130) — 24 абзаца вместо 4, вызовов в ~8 раз меньше (1218 → ~160), ответ — в пределах 8000 токенов вывода.

### Внешний извлекатель: `knowledge/external_extraction.py`

Сборка без сервиса знаний: `PHILOGRAPH_DATABASE_URL` (база знаний, миграции применяются), `PHILOGRAPH_LIBRARY_URL` (обязательна, как в `main.py`; можно `--library-url`), реестр по умолчанию, `Statements` с текстом абзаца из библиотеки (кэш абзацев версии, заполненный тем же ответом `internal/versions/{id}/paragraphs`), `Filling(llm=None)`.

Формат задания и ответов — дельта, «Внешний извлекатель». Файл ответов — тот же JSON, что шлюз отдал бы в `value`.

Тариф — `knowledge/extraction_prices.yaml` (package data): `claude-opus-5-5: {input: 4.0, output: 20.0, cache_read: 0.20}` за 1M токенов. Аргументы `--price-*` важнее.

Повтор `ingest`: без `--replace` — отказ, с `--replace` — `Filling.rollback` прежних `done`-запусков `extractor=external` этой версии, затем новая запись.

### Отчёт

`report(engine, since, until) -> str` — Markdown; источник — название сущности-источника по `source_id` (`Entities.by_external("library", …)`), иначе `source_id`, иначе `target`.

### Шлюз моделей

- `LLMGateway.role_info(role) -> {role, model, call_budget_seconds}`, маршрут `GET /v1/roles/{role}` (404 `unknown_role`).
- `Store.spend_summary` — суммы `input_tokens`, `output_tokens`.

### Промпт

`ontology.extract`: правила художественного текста и атрибуции автору; формулировка «не включай вместо null» усилена.

## Выбор решения

### 1. Где проверять ответ модели

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость и масштабируемость |
|---|---|---|---|
| А. Оставить строгую схему шлюза, поднять `schema_retries` (самый простой) | Плохо: каждый повтор — деньги, одно поле по-прежнему бракует весь ответ | Шлюз решает за сервис знаний, что допустимо в онтологии | Правило реестра дублируется в двух местах (схема шлюза и проверка сервера) |
| Б. Мягкая схема шлюзу, поштучная проверка сервером знаний | Хорошо: плохой элемент теряется один, повторов нет | Владелец правила — сервис знаний («модель предлагает, код проверяет») | Одна функция `_item` для шлюза и внешнего извлекателя; новый тип реестра — без правки схемы шлюза |
| В. Шлюз принимает частично валидный ответ (фильтрует элементы по схеме сам) | Средне | Шлюз узнаёт о структуре ответа извлечения — общий компонент тянет предметную логику | Коды причин пришлось бы передавать из шлюза |

**Выбрано Б.** Платим: схема реестра больше не защищает вход шлюза, поэтому вся проверка — на сервере, и она обязана быть полной (дельта, шаги 1–8). Избегаем костыля «увеличить повторы до зелёного».

### 2. Доступ внешнего извлекателя к абзацам

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость и масштабируемость |
|---|---|---|---|
| А. Клиент библиотеки `internal/versions/{id}/paragraphs` (как `Filling`) | Нужен поднятый сервис библиотеки | Контракт сервиса, знания не знают таблиц библиотеки | Деление и тексты — ровно те же, что у `Filling`; сверка цитаты в `Statements` идёт тем же `internal/paragraphs/{id}` |
| Б. `--library-db URL`: чтение таблиц `library` напрямую | Работает без сервиса | Нарушает границу сервисов (`lint-imports` ловит импорт, но не SQL к чужой схеме): знания завязаны на схему библиотеки | Любая миграция библиотеки ломает команду; сверку цитат в `Statements` тоже пришлось бы переключать на SQL |

**Выбрано А.** Платим: на машине ведущего должен быть поднят сервис библиотеки (он и так нужен — данные там). Режим Б не делаем.

### 3. Где хранить тариф внешних моделей

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость и масштабируемость |
|---|---|---|---|
| А. Только аргументы CLI | Просто | Цена размазана по командам ведущего | Ошибка в одной команде — неверный отчёт |
| Б. Данные `knowledge/extraction_prices.yaml` + переопределение аргументами | Один файл | Тариф внешних моделей — данные сервиса знаний (шлюз о них не знает, в `config/llm.yaml` им не место: там модели, которые шлюз вызывает) | Новая модель — строка в YAML |
| В. Секция в `config/llm.yaml` | — | Конфиг шлюза начинает описывать модели, которые шлюз не вызывает | Знания должны читать конфиг чужого сервиса |

**Выбрано Б.**

### 4. Таймаут вызова шлюза (П1)

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость и масштабируемость |
|---|---|---|---|
| А. Переменная окружения знаний с большим значением | Просто | Знания угадывают бюджет шлюза | Правка `llm.yaml` молча ломает соответствие |
| Б. Шлюз сообщает бюджет роли (`GET roles/{role}`), знания берут бюджет + запас; переменная — запасной вариант | Один запрос на запуск | Формула бюджета — у владельца (шлюз), знания её не повторяют | Меняется `llm.yaml` — таймаут следует сам; тот же запрос даёт модель роли для `filling_runs.model` |
| В. Асинхронное извлечение без ожидания | Лучше всего | Правильно | Большая переделка очереди и обработчика — вне запроса |

**Выбрано Б** (В — «Открытые вопросы»).

### 5. Повторная запись ответов

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость и масштабируемость |
|---|---|---|---|
| А. Дедуп подтверждений и атрибуций в `Statements._attach` | Тонко | Меняет поведение записи для всех путей (перекрытие фрагментов, второй учебник) — вне запроса | Затрагивает согласие и повышение статуса |
| Б. Отказ без `--replace`, с `--replace` — откат прежнего внешнего запуска версии (`rollback_run`) и новая запись | Один откат | Использует существующий откат запуска | Поведение записи не меняется; повтор явно виден в `filling_runs` (`rolled_back`) |

**Выбрано Б.** Проверено чтением: ключ утверждения удвоения утверждения не даёт, но `_attach` удвоил бы подтверждения и атрибуции — поэтому простой «повтор безопасен» неверен.

### 6. Размер фрагмента

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость |
|---|---|---|---|
| А. Оставить 4 абзаца | — | — | П12 остаётся |
| Б. Цель по символам с пределом числа абзацев | Ровная нагрузка на вызов | Одна функция `fragments`, параметры — у `Filling` | Прежние тесты с `fragment_size` действуют без правки |
| В. По токенам модели | Точнее | Нужен токенизатор модели в знаниях | Зависит от модели |

**Выбрано Б.**

## Открытые вопросы

1. **Возобновление запуска.** Повтор задания очереди после сбоя начинает новый запуск с начала: прежний — `failed`, но фрагменты извлекаются заново (ключ утверждения не даёт дублей утверждений, подтверждения удвоятся). Возобновление «с фрагмента» — отдельное изменение.
2. **Асинхронное извлечение** вместо синхронного в обработчике события — отдельное изменение.
3. **Неизвестная `stance`** (`neutral`) — отказ `stance_invalid`, а не замена на `asserts`: замена молча меняет смысл атрибуции. Если доля таких отказов велика — пересмотреть.
4. **Цель 3000 символов** — оценка по двум книгам; после первых 10 источников переизвлечения стоит сверить долю отбраковки и длину ответов.
5. **Тесты прежнего контракта** (`progress.md`): сценарий «Схема с сущностями и датировкой» проверял перечни в схеме шлюза и `required` у `dating`; юнит `test_new_entity_without_type_dropped_by_code` — точное множество ключей события без `code`. Новая дельта это меняет; тесты правит тестировщик.
6. **Архив.** Дельта `improve-extraction-naming` (MODIFIED «Структурированный вывод по реестру») ещё не перенесена в основную спецификацию; новое правило схемы вынесено в ADDED «Проверка ответа по утверждениям», чтобы не конфликтовать. При архиве — сначала перенести `improve-extraction-naming`.

7. **Сирота при отказе датировки** (ревью, п. 3). `EntityItems.date_item` привязывает или создаёт сущность элемента `entities` до `dating.check`; отказ `dating_*` оставляет созданную сущность без утверждений. «Сирот нет» дельты относится к утверждениям; для датировок П7 не закрыт. Исправление — проверять датировку (абзац, цитату, формат) до `resolve`, отдельным пунктом.
8. **Повтор задания очереди после `failed` на шлюзовом пути** (ревью, п. 8) удваивает подтверждения и атрибуции утверждений, записанных прерванным запуском (`_attach` вставляет всегда). Случай частый (П1 давал сотни прерванных запусков). Задача ведущему — отдельное изменение: продолжение прерванного запуска того же `run_id` с первого необработанного фрагмента или откат прерванного запуска перед повтором. Для внешнего пути закрыто здесь: повтор без `--replace` запрещён, с `--replace` откатываются все неоткатанные запуски версии.
9. **`--replace` откатывает до новой записи.** Если новая запись затем упадёт, у версии не останется утверждений внешнего извлечения до следующего `ingest --replace` (повтор безопасен: прерванный запуск тоже откатится). Порядок «сначала откат» нужен, иначе новые подтверждения слились бы со старыми. Риск и порядок действий — в runbook, «Извлечение связей».

## Риски

- Мягкая схема пропускает больше мусора к серверу: защита — поштучная проверка, инвариант «только типы реестра» (тестировщик).
- Нормализация цитаты терпимее: пересказ не должен проходить — инвариант дельты и мутация «части в любом порядке».
- `GET spend` за 3650 дней на каждый запуск — как было (`_run_cost`); при 208 запусках приемлемо.
