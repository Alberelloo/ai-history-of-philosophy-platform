# Design

## Context

Мотивация в [proposal.md](proposal.md), требования в `evaluation-datasets` и `quality-evaluation`, метрики по компонентам — блок 7 [system-design.md](../../../docs/product/system-design.md).

## Decisions

### 1. Наборы с версиями по диапазонам

Элемент набора живёт в диапазоне версий `[added, removed)`. Добавление, правка и решение человека поднимают версию набора. Правка закрывает старую запись и открывает новую с тем же `item_id`. Снимок любой версии — запрос по диапазону, поэтому старые прогоны воспроизводимы.

### 2. Черновики не участвуют в метриках

Черновик модели получает статус `draft`. Прогон берёт только подтверждённое и записывает, сколько черновиков осталось без решения.

### 3. Компоненты — через HTTP

Оценка — офлайн-задача и сосед, как любой другой сервис: поиск, ассистент (`/v1/ask`, `/v1/internal/route`) и сервис LLM (оценщик) вызываются по своим интерфейсам. Поэтому оценка меряет то, что видит пользователь, а не внутренности. Расход оценщика и черновой разметки идёт в бюджет «наполнение».

### 4. Метрики — чистые функции

`search_metrics`, `router_metrics`, `assistant_metrics`, `ocr_metrics`, `ontology_metrics` получают пары «элемент — результат» и ничего не знают о сервисах. Метрики онтологии принимают выборку утверждений с решениями человека: страница проверки (этап 4) будет их источником.

### 5. Сравнение по элементам

Метрика `per_item` у каждого прогона позволяет сравнить два прогона не только средними, но и списками вопросов, где стало лучше и хуже. Сравнение на разных версиях набора даёт предупреждение.

## Risks / Trade-offs

- [Оценщик ошибается] → его метрики показываются с долей согласия с человеком (`agreement`), калибровка на выборке.
- [Задержка в прогоне не похожа на работу сайта] → время берётся из события `done` ассистента; нагрузочный прогон — этап 6.
