# Design

## Context

Мотивация в [proposal.md](proposal.md), требования в `paragraph-indexing` и `paragraph-search`. Абзацы и события даёт библиотека, эмбеддинги — сервис LLM. Стек — [ADR-0001](../../../../docs/architecture/adr/0001-stack.md), провайдер эмбеддингов — [ADR-0002](../../../../docs/architecture/adr/0002-embeddings.md).

## Goals / Non-Goals

**Goals:** находить абзацы по смыслу и по словам, не тратить бюджет на неизменённое, соблюдать разрешения лицензий, не ломаться без векторной базы.

**Non-Goals:** выбор конкретной модели эмбеддингов, расширение запроса онтологией (это [add-ontology-aware-assistant](../2026-11-05-add-ontology-aware-assistant/proposal.md); здесь только точка расширения).

## Decisions

### 1. Индексы — производные данные

Поиск хранит свою копию нужного: текст абзаца, главу, язык, видимость. Он никогда не читает таблицы библиотеки, а получает абзацы через внутренний интерфейс библиотеки (`/api/v1/internal/...`). Индексы можно пересобрать из библиотеки в любой момент, поэтому их нет в резервных копиях.

### 2. Подписчики событий

Передача исходящих событий раскладывает каждое событие по подписчикам: `search:source.published`, позже `ontology:source.published`. У каждого своя задача в очереди и свой учёт обработанных событий. Подписчик не мешает другому, а повтор события ничего не дублирует.

### 3. Поиск по словам — свой обратный индекс

Леммы считает код (pymorphy3 для русского, Snowball для остальных), индекс «лемма → абзац» лежит в реляционной базе, ранжирование — BM25. Так одинаково работают PostgreSQL и SQLite в тестах, и полностью контролируется нормализация дореформенной орфографии. Служебные слова не участвуют, иначе «тема, которой нет» находилась бы по предлогам.

### 4. Смысловой индекс — Qdrant, коллекция на модель

Точка — фрагмент абзаца с полями `paragraph_id`, `source_id`, `lang`, `scope`, `active`, `text_hash`. Снятый источник помечается `active=false`, а не удаляется, поэтому повторная публикация не пересчитывает эмбеддинги. Тот же текст у другого абзаца копирует готовые векторы. Новая модель строит свою коллекцию, переключение идёт в самом конце.

### 5. Слияние результатов по рангам (RRF)

Оценки BM25 и косинусной близости несравнимы, поэтому списки сливаются по рангам: `1 / (k + rank)`. Расширение запроса — отдельный список, поэтому видно, какие результаты пришли через него. Приоритетные абзацы получают добавку.

### 6. Эмбеддинги пачками

Индексация считает эмбеддинги пачками и сохраняет каждую сразу. При исчерпании лимита запуска готовое остаётся, а абзацы уже находятся по словам.

## Risks / Trade-offs

- [Тестовая модель понятий проверяет механику, а не качество] → качество настоящей модели меряет оценка (`add-evaluation-harness`), ADR-0002.
- [Свой обратный индекс медленнее специализированных систем] → на десятках тысяч абзацев BM25 по нескольким леммам — миллисекунды; время каждой части пишется в журнал.
- [Внутренний интерфейс библиотеки не должен быть доступен снаружи] → в продакшене наружу смотрит только шлюз (`deployment`, этап 6).
