# Design

## Context

Мотивация в [proposal.md](proposal.md), стек в [ADR-0001](../../../../docs/architecture/adr/0001-stack.md). Требования в спецификациях `llm-gateway`, `observability`, `operator-access`, `service-runtime`. На машине разработчика нет Docker и PostgreSQL, поэтому всё, что касается данных, должно запускаться в тестах на SQLite, а в CI — ещё и на PostgreSQL.

## Goals / Non-Goals

**Goals:**
- общий каркас, на который ложатся все сервисы: настройки, журнал событий, контекст запроса, доступ к базе, очередь;
- сервис LLM целиком, кроме выбора провайдера эмбеддингов;
- проверка поведения тестами по результату и по журналу; прослеживаемость «требование → тест» в CI.

**Non-Goals:**
- конкретный провайдер эмбеддингов (изменение поиска);
- веб-клиент (появится с библиотекой и чтением);
- оповещения и копии (этап 6).

## Decisions

### 1. Пакет `philograph` с подпакетами по сервисам

```
src/philograph/
  platform/   общее: настройки, события, контекст, база, очередь, часы, интерфейсы между сервисами
  llm/        сервис LLM
  operator/   доступ оператора (библиотека, используется сервисами с внутренними страницами)
  library/ search/ assistant/ knowledge/ gateway/   следующие изменения
```

Сервис зависит только от `platform` и от интерфейсов других сервисов, не от их внутренностей. Правило проверяет import-linter: контракт «сервисы независимы» на уровне подпакетов.

Альтернатива — отдельный репозиторий или пакет на сервис. Отклонена: для одного разработчика это кратно больше работы с версиями и CI без выигрыша на нашем объёме.

### 2. Журнал как поток событий с каталогом

Код пишет не строки, а события: `emit("llm.call.completed", role=..., cost_usd=...)`. Каталог (`platform/events.py`) хранит имя, уровень и обязательные поля каждого события. `emit` проверяет событие по каталогу; в строгом режиме (тесты) нарушение — исключение, в работе — отдельное событие `observability.catalog.violation`. События уходят в приёмники: JSON через structlog в работе, список в памяти в тестах.

Контекст запроса (идентификатор запроса или запуска, сервис) хранится в `contextvars` и подставляется в каждое событие автоматически, поэтому его нельзя забыть.

Альтернатива — обычный журнал с текстовыми сообщениями и проверка тестами по подстрокам. Отклонена: такие тесты хрупкие, а каталог даёт контракт для оповещений.

### 3. Тест на каждое требование

Маркер `@pytest.mark.req("llm-gateway", "Дневной лимит бюджета сайта")` связывает тест с требованием. Скрипт `scripts/check_traceability.py` разбирает `### Requirement:` во всех спецификациях изменений, перечисленных в `openspec/traceability.yaml` как реализованные, и падает, если у требования нет теста или маркер ссылается на несуществующее требование. Фикстура `events` даёт тесту список событий и помощники для проверки последовательности.

### 4. Сервис LLM: ядро без сети, провайдеры за интерфейсом

`LLMGateway` — ядро без привязки к HTTP: роли, шаблоны, бюджеты, кэш, журнал, повторы. Провайдер реализует интерфейс `generate`, `stream`, `embed`. Есть `FakeProvider` с заданными ответами и ошибками для тестов и `OpenAICompatibleProvider` на httpx для DeepSeek. Поверх ядра — FastAPI-приложение. Тесты проверяют ядро напрямую и через приложение.

Дневной лимит с резервом: перед вызовом в учёте записывается резерв по оценке стоимости (верхняя граница по максимуму токенов ответа), после ответа резерв заменяется фактом. Проверка «хватает ли» и запись резерва выполняются под одной блокировкой: в процессе — `threading.Lock`, в PostgreSQL — блокировка строки дня. Поэтому одновременные запросы не переходят лимит больше чем на один вызов.

Цены и роли — настройка в YAML, путь к которой задаёт переменная окружения. Ночной тариф — интервал часов по UTC в настройке цен.

### 5. Доступ оператора

Пароль хранится хешем PBKDF2-SHA256 из стандартной библиотеки, сессия — случайный токен с временем бездействия; в токен входит «эпоха» пароля, поэтому смена пароля делает все сессии недействительными. Права проверяются по роли через `require(permission)`. Неавторизованный запрос получает 404.

### 6. Очередь на базе

Таблица задач со статусом, числом попыток, временем следующей попытки и ключом идемпотентности. Забор задачи — `FOR UPDATE SKIP LOCKED` в PostgreSQL и обычная транзакция в SQLite (в тестах один исполнитель). После N неудач задача получает статус «не удалась» с причиной.

### 7. Часы как зависимость

Время берётся из объекта часов, а не из `datetime.now()`. Тесты подставляют управляемые часы: так проверяются сутки лимита, ночной тариф, срок хранения журнала и сессий.

## Risks / Trade-offs

- [SQLite и PostgreSQL ведут себя по-разному в блокировках] → блокировки за интерфейсом; CI гоняет тесты и на PostgreSQL.
- [Каталог событий разрастётся] → он разбит по сервисам, у события есть описание; тест проверяет, что каждое событие каталога кто-то пишет.
- [Резерв по максимуму токенов занижает доступный лимит] → резерв живёт только время вызова.
