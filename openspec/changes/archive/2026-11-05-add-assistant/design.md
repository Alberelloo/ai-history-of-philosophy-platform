# Design

## Context

Мотивация в [proposal.md](proposal.md), требования в `assistant-dialog`, `question-routing`, `answer-grounding`. Ассистент вызывает поиск ([add-paragraph-search](../add-paragraph-search/design.md)) и сервис LLM ([add-platform-foundation](../add-platform-foundation/design.md)) только по HTTP.

## Goals / Non-Goals

**Goals:** ответ потоком с первым фрагментом как можно раньше, проверка опоры кодом, предсказуемое число вызовов модели, понятные сообщения при любом сбое.

**Non-Goals:** онтология в цепочках (точки `hooks` для [add-ontology-aware-assistant](../add-ontology-aware-assistant/proposal.md)), настройки читателя в отдельном экране (этап 6; пока флаги в запросе).

## Decisions

### 1. Маршрутизация и цепочки как данные

Маршрутизатор — структурированный вывод роли `fast` по JSON Schema через `/v1/structured` сервиса LLM. Цепочки (`CHAINS`) описывают поиски данными: область (`current`, `all`, `others`, `toggle`), лимит, соседей, дополнительные термины. Новый тип вопроса — новая запись, а не новый обработчик. Агента с циклами нет: вызовов модели на вопрос не больше `max_llm_calls` (маршрутизатор и ответ).

### 2. Опора проверяется кодом по фрагментам

Модель получает абзацы под номерами и ставит `[n]` после предложений. `FragmentStream` режет поток на предложения: предложение отдаётся, только когда началось следующее, чтобы его ссылки успели прийти. Каждый фрагмент проверяется до отправки: номера переводятся в абзацы, выдуманные удаляются, цитаты сверяются с абзацем, длинные цитаты из источников без права цитирования убираются. Пометка `grounded` — решение кода. Инструкции в вопросе на это не влияют, потому что правила не в модели.

### 3. Шаблоны — общий каталог данных

Тексты шаблонов лежат в `philograph.prompts`: их импортируют и сервис LLM (регистрирует при старте), и тесты. Потребитель передаёт только имя шаблона и данные. Версия шаблона — отпечаток текста.

### 4. Поток событий NDJSON

Ответ ассистента — строки JSON: `fragment`, `notice`, `refused`, `unavailable`, `no_answer`, `error`, `done`. Клиент рисует фрагменты по мере прихода. Остановка — отмена запроса: сервер закрывает поток, шлюз закрывает резерв в бюджете стоимостью полученной части.

### 5. Память диалога в браузере

Клиент хранит диалог и передаёт историю. Сервер берёт последние обмены целиком, а более ранние — списком вопросов.

## Risks / Trade-offs

- [Модель не ставит ссылки или ставит их не после предложения] → такие фрагменты помечаются как без опоры; качество ссылок меряет оценка.
- [Буферизация потока на любом звене убивает «первое слово быстро»] → регрессионный тест на HTTP-поток сервиса LLM и тест остановки в браузере через настоящий HTTP.
- [Лимит посетителя в памяти процесса сбрасывается при перезапуске] → до этапа 6, где лимиты переходят в шлюз (`abuse-protection`).
