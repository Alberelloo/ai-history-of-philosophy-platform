# Design

Второе изменение стека (ТЗ, п. 2.2). Опирается на `add-reference-catalog`: общий снимок `knowledge/snapshot.py`, правило `knowledge/epochs.py:EpochMembership`, справочник `GET /v1/catalog?epoch=`. Его использует `add-epoch-context` (2.3) и `add-geo-timeline` (2.4) — импортом `knowledge/wikidata.py`, `dates.span/middle` и клиентской `eraOf`.

## Контекст

- Реестр: тип `epoch`; `dating` разрешена для `epoch` (synchro-map); `belongs_to_epoch` (любая → `epoch`, уточнитель `membership_basis`: self | institutional | historians). Аналога «relates_to_epoch» не нужно.
- `Statements._update_primary` копирует основную датировку в `entities.primary.dates` (предпочтённая, иначе первая); `SectionMap` берёт пролёт эпохи из `primary.dates` по серединам. Это правило не меняется: спецификация «Датировка эпохи» описывает его как есть; «самая сильная по статусу» — вне объёма (отдельное изменение `Statements`). После дефекта Д1 правило применяется последовательно: копия пересчитывается и при смене статуса (`_set_status`), без действующих значений — `None`; порядок «первое записанное» — явный (`_raw`, по первой записи журнала, коррелированный подзапрос).
- `filling.import_wikidata(qid, fetch)` (файл Lead'а, не трогаем) — персоны и труды; год берёт срезом `claims[...][0][1:5]`, то есть теряет знак эры и точность. Для эпох не подходит.
- `knowledge/portraits_source.py` — образец сетевого модуля: CLI `python -m …`, `fetch`/`download` внедряются, сеть только в нём, манифест в `sources/portraits.yaml` проверяет человек.
- Клиент карты: `web/src/map/model.ts` считает участников эпохи по `midLife` и подсветку эпохи по `eraOf` — без явных связей; это вторая копия правила, которую 2.1 вынесла на сервер.
- Карточка (`cards.py:SECTIONS`) для `epoch` разделов не имеет — показывает только описание и «где читать».
- В данных Lead'а эпохи появляются из извлечения (концы `belongs_to_epoch`) с датировкой редко; QID у них нет.

## Решения

### Модуль `knowledge/epoch_dates.py`

```
python -m philograph.knowledge.epoch_dates suggest [--manifest sources/epochs.yaml]
python -m philograph.knowledge.epoch_dates apply   [--manifest sources/epochs.yaml] [--linked] [--dry-run]
                                                   (база — PHILOGRAPH_DATABASE_URL, как у сервиса знаний)
```

- Команда опирается на общий модуль `knowledge/wikidata.py` (ниже); своего httpx и разбора времени у неё нет. Свои функции: `epoch_dating(record: WikidataRecord) -> tuple[FuzzyDate, list[str]] | None` (датировка и использованные свойства), `EpochDates(statements, entities).apply(manifest, fetch, *, dry_run=False, linked=False) -> Report`, `suggest(manifest, fetch) -> Manifest`.
- Интервал: `dates.interval(start: FuzzyDate, end: FuzzyDate) -> FuzzyDate` — новая функция в `dates.py` (рядом с `lifespan`): ранние и поздние начала — из `start`, концы — из `end`; точность — `year`, если обе год, иначе худшая (`century` > `decade` > `approx` по ширине); `original` строится детерминированно `wikidata.format_original(start, end)` — «1685–1815», «VIII в. до н. э. – 476».

### Общий модуль `knowledge/wikidata.py` (создаётся здесь; 2.3 и 2.4 переиспользуют)

```python
QID = re.compile(r"^Q\d+$")
USER_AGENT = "PhiloGraph/1.0 (+https://github.com/<репозиторий проекта>)"   # без сведений об операторе
ENTITY_URL = "https://www.wikidata.org/wiki/Special:EntityData/{qid}.json"
SEARCH_URL = "https://www.wikidata.org/w/api.php?action=wbsearchentities&format=json&type=item&limit=10&language={lang}&search={label}"
PAGE_URL = "https://www.wikidata.org/wiki/{qid}"

Fetch = Callable[[str], dict[str, Any]]            # URL → JSON; в тестах — фикстура

class WikidataError(Exception): ...                # неверный QID, сбой загрузки, ответ не по форме
def check_qid(qid: str) -> str                     # ^Q\d+$, иначе WikidataError; запросов не делает
def page_url(qid: str) -> str                      # ссылка «Wikidata ↗» и place атрибуции — только отсюда
def http_fetch(url: str, *, wait: Callable[[float], None] = time.sleep,
               transport: httpx.BaseTransport | None = None,
               timeout: float = 10.0, retries: int = 3, max_wait: float = 30.0) -> dict  # 429/503 → Retry-After
def fetch_entity(qid: str, fetch: Fetch) -> WikidataRecord
def search(label: str, lang: str, fetch: Fetch) -> list[dict]          # id, label, description

@dataclass(frozen=True)
class WikidataRecord:
    qid: str
    labels: dict[str, str]                         # язык → метка
    descriptions: dict[str, str]
    claims: dict[str, list[Claim]]                 # свойство → значения (как в ответе, с рангом)
    def best(self, prop: str) -> Claim | None      # preferred, иначе первый normal; deprecated — никогда
    def items(self, prop: str) -> list[str]        # QID-значения свойства (P31, P793, P276…), с проверкой check_qid

@dataclass(frozen=True)
class Claim:
    value: Any                                     # {"time","precision"} | {"id"} | {"latitude","longitude"} | str
    rank: str                                      # preferred | normal | deprecated
    qualifiers: dict[str, list[Any]]

def wikidata_time(value: str, precision: int) -> FuzzyDate | None   # эра, точность (11…6), +0000/мусор → None
def claim_date(claim: Claim | None) -> FuzzyDate | None             # обёртка над wikidata_time
def format_original(start: FuzzyDate, end: FuzzyDate | None = None) -> str
```

- **Формат уточнителя `time` и значений-дат.** Любая дата из Wikidata пишется в утверждение (значение `dating` или уточнитель `time`, как у `lived_in` в 2.4) ровно как `FuzzyDate.to_json()`: `{"earliest_start", "latest_start", "earliest_end", "latest_end", "precision", "original"}`, где `original` — из `format_original`, а интервал — из `dates.interval`. Одинаковые данные Wikidata дают одинаковый JSON, а значит одинаковый ключ утверждения (`Statements._key`) — повторный запуск сливается с прежним утверждением (идемпотентность).
- Сеть — только `http_fetch`; команды получают `fetch = partial(http_fetch, wait=time.sleep)`, тесты — словарь фикстур или `httpx.MockTransport`. Ожидание повторов — через внедряемую функцию `wait` (у `Clock` проекта нет `sleep`; в тестах `wait` записывает запрошенные секунды и сдвигает `ManualClock`, реального ожидания нет).
- Правило времени — в спецификации «Доступ к Wikidata»: знак — эра (`dates._astro`), точность 9+ — год, 8 — десятилетие, 7 — век ⌈|год|/100⌉ (обе записи XVIII века — `+1800` и `+1701`), 6 — тысячелетие (`approx`), ниже 6, `+0000` и не по формату — `None`.
- Ошибки ловятся по типу (`WikidataError`, `httpx.HTTPError`), не `except Exception`.

- Свойства: P580/P582; если нет обоих — P571/P576; если есть только начало или только конец — `no_dates`.
- Запись: `Statements.add(epoch, "dating", value=…, attributions=[Attribution("source", f"wikidata:{qid}", place=url)], provenance=Provenance("imported", extra={"wikidata": qid, "properties": ["P580","P582"]}), status="sourced")` — та же форма, что у `import_wikidata`; внешний идентификатор — новый `Entities.add_external(entity_id, "wikidata", qid)` (с `DuplicateEntity`, если QID уже у другой сущности → `result=duplicate_qid`, без записи).
- Существующая действующая датировка: сравнение четырёх границ; совпадает — `unchanged`; иначе `conflict` (обе датировки в отчёте, запись не делается).
- `--linked`: кроме манифеста — все эпохи базы с внешним идентификатором Wikidata.
- Отчёт — JSON в stdout: по эпохе `{epoch_id, label, qid, result, dating?, existing?}` и итог.

### Манифест `sources/epochs.yaml`

```yaml
# Эпохи раздела «Теория познания». wikidata — только подтверждённый человеком QID.
epochs:
  - ru: Античность
    en: Classical antiquity
    wikidata: null          # подтверждает Lead после suggest
    candidates: []          # заполняет suggest: [{qid, label, description, start, end}]
  - ru: Средние века
    en: Middle Ages
    wikidata: null
  - ru: Возрождение
    en: Renaissance
    wikidata: null
  - ru: Научная революция
    en: Scientific Revolution
    wikidata: null
  - ru: Просвещение
    en: Age of Enlightenment
    wikidata: null
  - ru: Немецкая классическая философия
    en: German classical philosophy
    wikidata: null
```

- QID в коммите не выдумываются: `suggest` записывает кандидатов, человек переносит выбранный в `wikidata`. Фикстуры тестов используют QID только как метки записей в фикстурах.
- Классы периода для отбора кандидатов — данные модуля `PERIOD_CLASSES` (исторический период, эпоха, эра, культурный период — QID список ведётся в модуле с комментариями и проверяется тестом на фикстуре, а не по сети).
- Проверка манифеста (`validate` внутри `apply`): уникальность `ru`, формат QID `^Q\d+$`, кандидаты только с датами.

### `GET /api/knowledge/v1/epochs`

```json
{
  "epochs": [
    {
      "id": "e_ep01",
      "label": "Просвещение",
      "from": 1685,
      "to": 1815,
      "fuzzy": {"from": [1685, 1685], "to": [1815, 1815]},
      "precision": "year",
      "original": "1685–1815",
      "dating": {"status": "sourced", "source": "wikidata", "wikidata": "Q12539"},
      "summary": {"text": "Интеллектуальное движение…", "generated": true},
      "counts": {"people": 17, "works": 9, "ideas": 2, "events": 4, "groups": 1}
    }
  ],
  "undated": [{"id": "e_ep07", "label": "Барокко", "counts": {"people": 1, "works": 0, "ideas": 0, "events": 0, "groups": 0}}]
}
```

- `dating.source`: атрибуция основной датировки — `wikidata` (источник `wikidata:Q…`), `source` (источник библиотеки; также атрибуция персоне — `who_kind=entity` — и подтверждающий абзац: это опора на источник, а не общее мнение), `common` (общее мнение), `manual` (оператор без атрибуции). Скрытые атрибуции не учитываются.
- `counts` — через `EpochMembership.members`, по категориям, как в карте (идеи — только явные).
- Из снимка (`max_stale` справочника), без модели; не платная операция. Событие `knowledge.epochs.listed`.

### Карта

- `SectionMap._build`: у `people[]`, `works[]` (и идей), `events[]` — `epochs: [id]` (порядок — по началу эпохи); у `eras[]` — `fuzzy: {from: [earliest_start, latest_start], to: [earliest_end, latest_end]}`. Поля только дописываются; прежние клиенты их игнорируют.
- Клиент: `types.ts` — новые поля и `Filter.epochs: string[]`, `parseState`/`writeState` — параметр `epochs`; `model.ts` — `visible` фильтрует по `epochs`, `related` для эпохи берёт `x.epochs.includes(id)` вместо `midLife`, `eraOf(eras, year)` остаётся для эпохи года (подпись года, подсветка эпохи выбранного) с правилом перекрытия «самое позднее начало, затем название»; удаляется только клиентская привязка сущности к эпохе (`midLife` в `related` для эпохи); `MapPanel.tsx` — раздел фильтра «Эпоха» со счётчиками (как прочие фасеты), только датированные эпохи; при выборе эпохи без явного окна — окно на общий пролёт; `MapCanvas.tsx`/`layout.ts` — растушёвка краёв пролёта (`linearGradient` на токенах `scene`, ширина — от `fuzzy`).
- `MapViews` (вид от ассистента) параметр `epochs` не принимает (вне объёма); `visible_counts` не меняется — ассистент фильтр не задаёт.

### Страница эпох

- `web/src/epochs/EpochsPage.tsx` — `/epochs`, `/epochs/<id>`; данные `GET /v1/epochs`; описание выбранной: счётчики из `counts`, ведущие персоны и труды — `GET /v1/catalog?epoch=<id>&type=person&sort=weight&limit=8` и `type=work`; события — `type=event&sort=date&limit=20`. Новых эндпоинтов «участники эпохи» нет: справочник уже это умеет.
- `epochs/Timeline.tsx` — SVG-лента: шкала (переиспользуются шаги шкалы `map/layout.ts`), упаковка пролётов по дорожкам (тот же алгоритм, что `packPeople`, вынесенный в общую функцию `packIntervals` в `map/layout.ts`), растушёвка краёв.
- Карточка эпохи — `OPEN_CARD_EVENT`; «На карте» — `/graph?epochs=<id>`; «В справочнике» — `/reference?epoch=<id>`.
- Пункт боковой панели: `LIVE.epochs = "/epochs"`, подпись `t.soon.sections.epochs.title` → «Эпохи» (EN «Epochs»), `/soon/epochs` → `replaceState("/epochs")`.

### Карточка эпохи

`cards.py:SECTIONS["epoch"] = [("dating", "Датировка", ["dating"], "out"), ("members", "Относятся к эпохе", ["belongs_to_epoch"], "in")]` — код `dating`, а не `when`: `when` уже занят разделом события «Дата и место», а тест каталогов сверяет «код → заголовок» однозначно — только утверждения; вывод по датам в карточку не попадает (О-8).

## События журнала

| Событие | Уровень | Поля | Когда |
|---|---|---|---|
| `knowledge.epochs.listed` | info | `epochs`, `undated`, `truncated`, `snapshot` | ответ `GET /v1/epochs` |
| `knowledge.epoch_dates.checked` | info | `epoch_id`, `qid` (может быть `null`), `result` (`added`\|`unchanged`\|`conflict`\|`no_dates`\|`no_qid`\|`fetch_failed`\|`ambiguous`\|`duplicate_qid`\|`created`) | каждая эпоха в `apply` |
| `knowledge.epoch_dates.run` | info | `mode` (`apply`\|`dry_run`), `checked`, `added`, `created`, `conflicts`, `skipped` | конец `apply` |
| `knowledge.epoch_dates.suggested` | info | `epochs`, `candidates` | конец `suggest` |
| `knowledge.map.built` | info | без изменений | — |

Сбой загрузки ловится по типу (`httpx.HTTPError`, `KeyError`/`ValueError` разбора), а не `except Exception`, и всегда оставляет событие `knowledge.epoch_dates.checked` с `result=fetch_failed`.

## Выбор решения

### 1. Как получать даты эпох из Wikidata

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Дописать эпохи в `filling.import_wikidata` | Меньше кода | Файл Lead'а (запрещено без согласования); тип сущности угадывается по P50 («work» иначе «person»); год без знака эры | Одна функция на все типы растёт ветвлениями |
| Б. Новый модуль-команда `knowledge/epoch_dates.py` поверх общего `knowledge/wikidata.py` (загрузка, время, QID), манифест в `sources/` | Сеть только при запуске оператором; ни одного вызова на пути читателя | Как `portraits_source`: правило времени Wikidata — в одном месте; запись — через `Statements` с проверками реестра | Тесты офлайн на фикстурах; 10× эпох — линейно, десятки запросов к Wikidata |
| В. Операторский HTTP-эндпоинт в сервисе знаний | Запуск из интерфейса оператора | Сервис ходит в сеть во время работы, держит долгий запрос; нужен фоновой запуск и права | Сложнее отладка и повторы; для разовой операции избыточно |

Выбрано: **Б**. Чем платим: правка общего `Statements` (пересчёт основной копии при смене статуса и явный порядок `_raw`, см. «Контекст» и proposal → Impact) и `graph.py` (подпись и ссылка атрибуции Wikidata); запуск — командой в окружении сервиса (Lead делает это у себя); команда пишет в базу сервиса знаний своим же кодом (`Statements`), как `seed_demo` и `portraits_source sync`. Костыли, которых избегаем: правка файла Lead'а, сеть на пути читателя, угадывание типа по свойству, копия разбора Wikidata в 2.3 и 2.4 (после обсуждения ролями загрузка и разбор вынесены в `wikidata.py`; в первой версии плана они были внутри `epoch_dates.py`).

### 2. Что делать с уже существующей датировкой

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Перезаписать (ранг «предпочтённое» у Wikidata) | Пролёты сразу «правильные» | Внешний источник молча побеждает учебник; меняет данные Lead'а без человека | Нельзя отличить решение от случайности |
| Б. Дописать вторую датировку «по источникам» | Сохраняет оба факта | Основной становится случайно одна из двух (порядок `_raw`) | Пролёты на карте «прыгают» |
| В. Дописывать только эпохам без датировки; расхождение — в отчёт | Ноль неожиданных изменений | Решение о конфликте — за человеком (страница проверки или ранг) | Повторный запуск идемпотентен (`unchanged`) |

Выбрано: **В**. Чем платим: эпохи с плохой датировкой из текста не исправятся сами — Lead видит их в отчёте `conflict`. QID манифеста, отличный от QID, уже записанного у эпохи, — тоже решение человека: `result=duplicate_qid`, второй QID не записывается. Костыли, которых избегаем: «временное» перезаписывание без проверки.

### 3. Принадлежность к эпохе на карте

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Оставить клиентский `midLife` | Ноль правок | Две копии правила (клиент и `epochs.py`), клиент не знает явных связей — карта и справочник расходятся | Каждое изменение правила — в двух языках |
| Б. Сервер отдаёт `epochs` у сущностей карты | +1 поле на запись (≈ 400 записей × 1–2 id) | Правило в одном месте, карта = справочник = страница эпох | Клиент проще |

Выбрано: **Б**. Чем платим: ответ карты чуть больше; проверка «Выбор на карте» для эпох меняется (тест на Локка). Костыли, которых избегаем: копия логики в двух местах без общего теста.

### 4. Смысл фильтра «Эпоха» на карте

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Только окно времени по пролёту эпохи | Тривиально | Явная принадлежность не учитывается — это не фильтр по эпохе, а пресет времени | Путает: Локк из Просвещения пропадает при окне Научной революции |
| Б. Фильтр по `epochs` + окно на пролёт, если читатель не задал своё | Немного кода в `visible` и панели | По общему правилу; окно — удобство, а не правило | Сочетается с остальными фасетами через «и» |

Выбрано: **Б**.

### 5. Страница эпох

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Без страницы: `/epochs` → `/graph` с линзой эпох | Ноль новой страницы | Раздел «Эпохи» превращается в ссылку на карту; негде показать датировку, источник и (в 2.3) контекст | 2.3 некуда класть |
| Б. Своя страница: лента эпох + описание выбранной на данных `/v1/epochs` и `/v1/catalog` | Один новый эндпоинт, остальное — справочник | Участники берутся тем же справочником, правило одно | 2.3 дописывает блок контекста; 2.4 получает тот же `/v1/epochs` |
| В. Своя страница с отдельным `/v1/epochs/{id}` (участники, события) | Один запрос на эпоху | Дублирует справочник (фильтр по эпохе и типу) | Два способа получить «участников эпохи» |

Выбрано: **Б**. Чем платим: описание эпохи — 3–4 запроса справочника (параллельно, каждый — фильтр в памяти). Костыли, которых избегаем: второй способ получить одно и то же.

### Клавиатура и доступность

- Лента — `role="listbox"` с `aria-label="Эпохи на оси времени"`, пролёт — `role="option"` с `aria-selected`; ←/→ — по времени, Home/End — первая/последняя, Enter — выбрать, Esc — снять выбор. После выбора фокус — на `<h2>` описания (`tabIndex=-1`).
- Растушёвка — не единственный признак нечёткости: в доступном имени и подписи «ок.»/«XVIII в.» из исходной записи.
- Цвета пролётов — токены; контраст подписи на пролёте ≥ 4.5:1 в обеих темах.

## Функциональные сценарии

1. **Lead обогащает даты.** `python -m philograph.knowledge.epoch_dates suggest` → в `sources/epochs.yaml` у каждой эпохи кандидаты → Lead переносит верные QID в `wikidata` → `apply --dry-run` → отчёт: `added` 4, `conflict` 1 («Научная революция»: в тексте 1543–1687, в Wikidata иное) → `apply` → на карте появились пролёты; конфликт Lead решает на странице проверки (ранг «предпочтённое»).
2. **Читатель смотрит эпохи.** Боковая панель → «Эпохи» → лента → «Просвещение» → датировка с источником, кто и что относится → «На карте» → карта отфильтрована по Просвещению.
3. **От справочника к эпохе.** В справочнике у записи Канта эпоха «Просвещение» — ссылка → `/epochs/<id>` (ссылка в записи справочника дописывается этим изменением в `ReferencePage`).
4. **Явная принадлежность.** Оператор подтверждает «Локк относится к Просвещению» → на карте при выборе Просвещения Локк выделен, в справочнике фильтр «Просвещение» его показывает, в карточке эпохи — строка «Локк».

## Контракты для 2.4 (гео-таймлайн)

- `GET /v1/epochs` — эпохи с пролётом, нечёткими границами, источником; стабильная форма, поля только дописываются.
- `GET /v1/map` — у персон, трудов и событий `epochs`.
- Состав эпохи — `GET /v1/catalog?epoch=<id>&type=…`.
- Места (`place`, `lived_in`, `happened_in`) этим изменением не меняются; контекстные события с местами — `GET /v1/context` из `add-epoch-context`.

## Риски

- **Неверный QID.** Защита — только подтверждённые человеком QID, фильтр кандидатов по классу и датам, `--dry-run` и отчёт.
- **Wikidata отвечает 429/таймаутом.** `http_fetch` соблюдает `Retry-After` (не дольше 30 с, не больше 3 повторов); эпоха получает `fetch_failed`, запуск идёт дальше.
- **Точность «век» в Wikidata неоднородна** (`+1800` и `+1701` для XVIII века) — правило ⌈|год|/100⌉ и тест на обе записи.
- **Конкурентная запись** во время фонового извлечения у Lead'а: команда пишет короткими транзакциями через `Statements`; блокировок очереди не берёт; `queue.py` не трогается.
- **Регрессия карты** (дизайн-якоря линий жизни, узлов, `anchorOn`): изменение выбора эпохи и растушёвка — проверка `tests/web/test_map.py` и визуальная по DOM; эталоны снимков — только Windows, их обновляет владелец; на машине агента e2e и `visual_check.py` не прогоняются — CI и Lead.

## Тестируемость

- Сервер: ожидание внедряется в `http_fetch` (`wait`), часы — в `Snapshots` (`ManualClock`); сеть в тестах запрещена ловушкой, загрузка — фикстуры `tests/knowledge/fixtures/wikidata/`.
- Клиент: таймеры ленты и карты — `setTimeout`/`requestAnimationFrame`/`performance.now`, тесты — `page.clock`.
- Браузерные тесты — на фикстуре `tests/web` с настоящим приложением знаний из `add-reference-catalog` (данные задаёт тест); `page.route` — только для 503 и задержки.
- Интерфейсные результаты (адрес, выбор, фокус) без клиентского журнала перечисляются в `verification.md` с серверным якорем.

## Безопасность

- Сеть — только в CLI оператора; домен один (`www.wikidata.org`), адреса строит код из QID по шаблону (`^Q\d+$`), а не из ответа.
- Ответы Wikidata — данные: из них берутся только время и точность; названия кандидатов в базу не пишутся, пока человек не перенёс QID.
- Ни секретов, ни личных данных: Wikidata без ключа, `User-Agent` проекта без сведений об операторе.
- Ссылка «Wikidata ↗» на странице эпох строится из `wikidata` ответа только после проверки `^Q\d+$` (сервер — `page_url`, клиент — та же проверка перед выводом).
- Названия и id из адреса выводятся текстом (React, без `dangerouslySetInnerHTML`); события `knowledge.epoch*` — только id, коды и числа.
