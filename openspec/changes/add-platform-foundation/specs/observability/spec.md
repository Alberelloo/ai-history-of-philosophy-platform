# Spec Delta

## Purpose

Позволяет восстановить, что произошло в системе: каждое значимое действие оставляет структурированное событие в журнале, события одного запроса связаны общим идентификатором, а набор событий описан каталогом и служит контрактом для тестов и оповещений.

## ADDED Requirements

### Requirement: Структурированный журнал событий

Каждый сервис и каждая офлайн-задача SHALL писать журнал как последовательность структурированных событий. У события SHALL быть: время, сервис, имя события из каталога, уровень, идентификатор запроса или запуска и поля, заданные каталогом для этого события.

#### Scenario: Запись события

- **WHEN** библиотека отдаёт главу
- **THEN** в журнале есть событие с именем из каталога, сервисом «библиотека», идентификатором запроса и идентификатором главы

### Requirement: Каталог событий

Имена событий и их обязательные поля SHALL быть описаны в каталоге событий. Событие, которого нет в каталоге, или событие без обязательного поля SHALL считаться ошибкой: в тестах — падением, в работе — отдельным событием о нарушении каталога. Каталог служит контрактом для тестов и оповещений.

#### Scenario: Событие не из каталога

- **WHEN** код пишет событие с именем, которого нет в каталоге
- **THEN** тест, в котором это произошло, падает

#### Scenario: Нет обязательного поля

- **WHEN** событие «llm.call.completed» записано без стоимости
- **THEN** это фиксируется как нарушение каталога

### Requirement: Сквозной идентификатор запроса

Запрос пользователя SHALL получать идентификатор на входе в систему, а офлайн-запуск — идентификатор запуска. Этот идентификатор SHALL передаваться во все вызовы между сервисами, в задачи очереди и в сервис LLM и записываться во все события, которые они порождают.

#### Scenario: Вопрос ассистенту

- **WHEN** пользователь задаёт вопрос, и ассистент обращается к поиску и к сервису LLM
- **THEN** события шлюза, ассистента, поиска и сервиса LLM несут один и тот же идентификатор запроса

#### Scenario: Задача из очереди

- **WHEN** публикация источника ставит задачу индексации в очередь
- **THEN** события индексации несут идентификатор запуска, породившего задачу

### Requirement: Без персональных данных

События MUST NOT содержать персональные данные посетителей: адреса, идентификаторы браузера в открытом виде, текст вопросов. Для подсчёта уникальных посетителей допускается только необратимый хеш с солью, которая меняется ежедневно. Текст вопросов хранится только в журнале вызовов LLM с его сроком хранения.

#### Scenario: Вопрос ассистенту

- **WHEN** пользователь задаёт вопрос
- **THEN** события ассистента содержат длину вопроса и тип, но не его текст

### Requirement: Уровни и ошибки

События SHALL иметь уровень: отладка, информация, предупреждение, ошибка. Каждая ошибка SHALL записываться с видом ошибки из каталога и без раскрытия секретов. Пользователь MUST NOT видеть внутренние сообщения об ошибках: он видит понятное сообщение и идентификатор запроса для обращения.

#### Scenario: Ошибка при чтении

- **WHEN** при открытии главы происходит внутренняя ошибка
- **THEN** пользователь видит сообщение «не удалось открыть главу» с идентификатором запроса, а в журнале событие уровня «ошибка» с подробностями

#### Scenario: Ключ в ошибке

- **WHEN** текст ошибки провайдера содержит ключ API
- **THEN** в журнале ключ скрыт

### Requirement: Метрики

Система SHALL считать метрики: число запросов и ошибок по операциям, задержку по операциям с перцентилями, время до первого фрагмента ответа ассистента, расходы на LLM по бюджетам, длину очереди задач и возраст самой старой задачи.

#### Scenario: Задержка ассистента

- **WHEN** оператор смотрит метрики за день
- **THEN** он видит медиану и 95-й перцентиль времени до первого фрагмента ответа ассистента

### Requirement: Проверки состояния

Каждый сервис SHALL отвечать на проверку состояния: жив ли он и готов ли обслуживать запросы. Готовность SHALL учитывать доступность того, без чего сервис не работает, например базы. Недоступность необязательной зависимости, например провайдера LLM для библиотеки, MUST NOT делать сервис неготовым.

#### Scenario: База недоступна

- **WHEN** у библиотеки нет связи с базой
- **THEN** проверка готовности библиотеки отвечает «не готов» с причиной

#### Scenario: Провайдер LLM недоступен

- **WHEN** провайдер LLM не отвечает
- **THEN** библиотека остаётся готовой, а сервис LLM сообщает о недоступности провайдера в своей проверке

### Requirement: Журнал как основа проверок поведения

Для каждого требования спецификаций, у которого есть наблюдаемый процесс, каталог SHALL содержать события, по которым процесс можно проверить: начало, ключевые решения, результат. Тесты SHALL проверять и итоговый результат, и последовательность событий.

#### Scenario: Публикация источника

- **WHEN** тест публикует версию источника
- **THEN** он проверяет и что источник виден в библиотеке, и что в журнале есть события начала публикации, переключения версии и отправки события следующим конвейерам в этом порядке
