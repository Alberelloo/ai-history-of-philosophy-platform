# Design

Первое изменение стека «справочник → эпохи → контекст» (ТЗ, п. 2.1). Следующие — `add-epochs` (2.2) и `add-epoch-context` (2.3) — опираются на `knowledge/snapshot.py` и `knowledge/epochs.py` отсюда. Параллельное изменение 2.4 (`add-geo-timeline`) берёт из этого стека только HTTP-контракты, описанные ниже и в дизайнах 2.2 и 2.3.

## Контекст

- `GET /v1/entities?name=` (`knowledge/app.py` → `Entities.find`) — точное совпадение нормализованного названия; возвращает список сущностей целиком (`id`, `type`, `primary`, `names`). Пользователи — тесты и ручные вызовы; клиент его не вызывает. Ассистент разрешает имена через `/internal/assistant/context`, граф — через `Entities.find` в процессе.
- Нормализация названий — `entities.normalize` (нижний регистр, «ё» → «е», знаки препинания → пробел). Колонка `names.normalized` уже есть.
- `SectionMap._load` (`knowledge/map.py`) уже читает «действующие» данные одним проходом: сущности без перенаправления, первое основное русское название, утверждения `scope=public`, не `rejected`, не `deprecated`, не только со снятых источников. `_fingerprint` — 12 счётчиков и максимумов таблиц; кэш карты пересобирается при любом изменении.
- Область учебника — `SectionMap._textbook_entities` (упоминания) плюс концы утверждений, для которых `Statements._attributed(s, textbook)`.
- Закрытые источники: `closed_sources(library, region)` в `app.py` (заголовок `X-Philograph-Region` от шлюза). Сырые маршруты снимают цитаты и атрибуции закрытых источников; «где читать» их не показывает.
- Шлюз проксирует `/api/knowledge/*` целиком; платные операции перечислены в `gateway/limits.py:PAID`, общий лимит частоты — корзина 20/с, всплеск 60.
- Клиент: пункт «Справочник» — `SOON` в `SoonPage.tsx`, `LIVE` в `Sidebar.tsx` содержит только `assistant` и `graph`; `App.tsx` заменяет `/soon/graph` и `/soon/assistant` через `replaceState`. Карточка открывается событием `OPEN_CARD_EVENT` в правую панель (`App.tsx`).
- Явная связь «относится к эпохе» (`belongs_to_epoch`, любая сущность → `epoch`, уточнитель `membership_basis`) есть в реестре; `relates_to_epoch` не нужен. Принадлежность по датам сейчас считает только клиент карты (`web/src/map/model.ts`: `eraOf`, `midLife`), и явную связь он не учитывает.

## Решения

### API справочника

`GET /api/knowledge/v1/catalog`

| Параметр | Тип | По умолчанию | Правило |
|---|---|---|---|
| `q` | строка | пусто | ≤ 200 знаков после обрезки пробелов, иначе 400 `bad_query` |
| `type` | код реестра; несколько — повтором параметра (`type=person&type=work`), запятая не разбирается | все | каждый — известный тип, иначе 400 `unknown_type`; включает подтипы (`is_a`); `source` всегда исключён |
| `epoch` | id сущности | нет | должен быть `epoch` (после перенаправления), иначе 400 `unknown_epoch` |
| `textbook` | id источника библиотеки | нет | «известный онтологии» источник: упомянут в нём (`mentions`), ему атрибутировано утверждение (`who_kind=source`), его абзац подтверждает утверждение (`evidence`) или есть сущность-источник (`external_ids`, система `library`); иначе 400 `unknown_textbook`. Закрытый для региона → пустой ответ, `textbook_closed=true` |
| `sort` | `label` \| `date` \| `weight` \| `relevance` | `relevance` при `q`, иначе `label` | иначе 400 `bad_query`; `relevance` без `q` выполняется как `label` |
| `page` | целое ≥ 1 | 1 | |
| `limit` | 1..60 | 24 | иначе 400 `bad_query` |
| `lang` | `ru` \| `en` | `ru` | язык основного названия; нет на этом языке — русское, затем любое. Прочее значение — как `ru` (не ошибка), без своей записи в кэше подписей индекса |

Ответ 200:

```json
{
  "items": [
    {
      "id": "e_1a2b3c4d5e6f",
      "type": "person",
      "label": "Иммануил Кант",
      "matched_name": null,
      "dates": {"from": 1724, "to": 1804, "precision": "year", "original": "1724–1804"},
      "epochs": [{"id": "e_ep01", "label": "Просвещение", "basis": "dates"}],
      "summary": {"text": "Немецкий философ, основатель критической философии…", "generated": false},
      "weight": 42
    }
  ],
  "total": 30,
  "page": 1,
  "limit": 24,
  "sort": "label",
  "facets": {
    "types": {"person": 12, "concept": 9, "work": 6, "epoch": 2, "event": 1},
    "epochs": [{"id": "e_ep01", "label": "Просвещение", "count": 17}]
  },
  "textbook_closed": false
}
```

- `dates.from`/`to` — середины нечётких границ (как `_start`/`_end` в `map.py`); `original` — исходная запись. У идей без датировки `dates=null`.
- `summary.text` — первые 200 знаков действующего описания (`description`), обрезка по слову с «…»; `generated` — статус описания `generated`. Описаний-цитат нет по построению: описание — значение, а не подтверждение.
- `facets.types` — по точному коду (клиент сам складывает коды в группы); `facets.epochs` — эпохи с ненулевым числом, по началу датировки, затем по названию; эпохи без датировки — в конце.
- Ошибки — общий формат `UserFacingError`: `{"error": "…", "kind": "bad_query" | "unknown_type" | "unknown_epoch" | "unknown_textbook"}`, 400; полный перечень `reason` события `knowledge.catalog.rejected` — таблица в требовании «Проверка параметров справочника». 503 `knowledge_unavailable`, если недоступна библиотека при фильтре `textbook`.
- Регион: заголовок `X-Philograph-Region` от шлюза, зависимость `region_closed` в `app.py`, как у `/entities/{id}/statements` и карточки; запрос к библиотеке (`/internal/access`) делается только при `textbook`.
- При `textbook_closed=true` — `items=[]`, `total=0`, `facets={"types":{},"epochs":[]}`.

`GET /v1/entities?name=` не меняется (требование «Прежний поиск по названию»).

### Снимок данных онтологии (`knowledge/snapshot.py`)

- `Snapshot` — неизменяемая структура: `entities` (id → тип, primary), `names` (id → список названий с `normalized`), `labels` (id → основное русское), `statements` (действующие, с атрибуциями и подтверждениями), `fingerprint`, `built_at`.
- `Snapshots(engine, clock).get(max_stale: float)`: считает отпечаток (перенесённый из `SectionMap._fingerprint` без изменений); если он совпадает с текущим снимком — `cached`; если не совпадает, но снимку меньше `max_stale` секунд — `stale` (возвращается прежний); иначе пересборка (`fresh`, событие `knowledge.snapshot.built`). Пересборка — под блокировкой процесса, параллельный запрос ждёт её, а не строит второй снимок.
- `SectionMap(statements, settings=None, snapshots=None)` — сигнатура совместима: без `snapshots` создаёт свой `Snapshots`; `main.py` передаёт общий экземпляр справочнику, карте и (в 2.4) слою мест. Карта берёт снимок с `max_stale=0` — поведение прежнее (тест `test_map.py` «новое утверждение меняет отпечаток» остаётся зелёным без правки), поля `knowledge.map.built` не меняются.
- Кэш ответов карты по учебнику (`SectionMap._cache`) ограничивается: LRU на 32 ключа (ключ — произвольный `textbook` из запроса, без предела рос бы). `CatalogIndex` и `EpochMembership` строятся один раз на отпечаток и хранятся только для текущего снимка.
- Часы: `Snapshots(engine, clock: Clock)` — `ManualClock` в тестах, `SystemClock` в сервисе.
- Справочник вызывает `get(max_stale=settings.catalog_max_stale_seconds)`, по умолчанию 15, переменная `PHILOGRAPH_CATALOG_MAX_STALE_SECONDS`.

### Индекс справочника (`knowledge/catalog.py`)

- `CatalogIndex` строится из снимка один раз на снимок (кэш по `fingerprint`): для каждой сущности — нормализованные названия, тип, датировка, значимость (число действующих утверждений, где она субъект или объект), описание, эпохи (через `EpochMembership`), множество источников раздела (упоминания + атрибуции/подтверждения утверждений).
- Правило «утверждение относится к учебнику» — одна функция `statements.attributed_sources(s, who_kinds=None)`: её используют `Statements._attributed` (пометка «в учебнике» карты, карточки, графа, ассистента) и раздел справочника. Параметр `who_kinds=("source",)` нужен только справочнику — для перечня «известных онтологии учебников», чтобы id персоны из атрибуции вида `entity` не считался учебником; для проверки принадлежности разделу ограничение не нужно (учебник к этому моменту уже проверен как известный).
- Запрос: фильтрация в памяти по типу, эпохе, разделу, затем поиск; счётчики — тем же проходом (тип — без фильтра типа, эпоха — без фильтра эпохи). Ранжирование: 0 — точное совпадение нормализованного названия, 1 — начало слова, 2 — внутри слова.
- `Catalog.list(params, closed)` → ответ и событие `knowledge.catalog.listed`.

### Принадлежность к эпохе (`knowledge/epochs.py`)

- Общая функция границ — `dates.span(d) -> (start, end)`: `round((earliest_start+latest_start)/2)`, `round((earliest_end+latest_end)/2)` — ровно прежние `map._start`/`map._end`, которые переходят на неё; `dates.middle(d) -> float` — `(start+end)/2` от `span`. Ей пользуются принадлежность к эпохе (2.1), пролёты карты и списка эпох (2.2), режим окна контекста (2.3), год глобуса (2.4).
- `EpochMembership(snapshot, registry)` — правило требования «Принадлежность к эпохе»: явное `belongs_to_epoch` из действующих утверждений, иначе по датам через `dates.middle` (персона, труд, событие, явление, идейное событие); пролёт эпохи — `dates.span`, `[from, to)`; идеи и группы — только явные.
- Методы: `of(entity_id) -> list[(epoch_id, basis)]`, `members(epoch_id) -> list[(entity_id, basis)]`. Изменение 2.2 добавляет сюда список эпох и отдаёт принадлежность карте.

### Клиент

- `web/src/reference/ReferencePage.tsx`: состояние из адреса (`q`, `group` — код группы из `TYPE_GROUPS`, раскрывается в повторяющиеся `type` запроса, `epoch`, `textbook`, `sort`); устаревший ответ отбрасывается по номеру запроса (последний отправленный побеждает), а не только `AbortController`, запросы через `reference/api.ts` с отменой устаревших (`AbortController`) и задержкой ввода 250 мс; «Показать ещё» добавляет страницу к списку.
- Группы типов — данные в `reference/types.ts` (`TYPE_GROUPS`: `person` → [person]; `ideas` → [concept, conception, doctrine, problem, position, argument]; `term` → [term]; `work` → [work]; `events` → [event, phenomenon] (idea_event — подтип event); `epoch` → [epoch]; `group` → [group]; `place` → [place]). Неизвестный серверу код в данных клиента — ошибка теста, а не тихий пропуск (тест сверяет `TYPE_GROUPS` с реестром, как `ontology.ru.json`).
- Карточка — тем же `OPEN_CARD_EVENT`, что в ответах ассистента; «Показать на карте» — `navigate("/graph/<id>")` для типов, которые есть на карте (person, work, идеи, события, epoch, group).
- `App.tsx`: маршрут `/reference`, замена `/soon/reference` на `/reference` через `replaceState`; `Sidebar.tsx`: `LIVE.reference = "/reference"`; `activeItem` отмечает «Справочник».

## Выбор решения

### 1. Форма API

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Расширить `GET /v1/entities`: без `name` — страница с фасетами | Ноль новых маршрутов | Одна точка — две формы ответа; ломает типизацию и смысл «точного разрешения имени»; старые тесты на форму списка оказываются под угрозой | Ветвление по наличию параметра; каждое расширение каталога трогает контракт разрешения имён |
| Б. Новый `GET /v1/catalog` рядом, `/v1/entities?name=` без изменений | Один маршрут | Контракты разделены по назначению: разрешение имени и каталог; правило фильтрации живёт в `catalog.py` | Каталог развивается независимо; 2.4 получает стабильный контракт |
| В. `GET /v1/entities/catalog` | Как Б | Пересекается с `/entities/{entity_id}` — зависит от порядка объявления маршрутов | Хрупко |

Выбрано: **Б**. Чем платим: два способа найти сущность по имени (точный и каталог) — это разные задачи, тест «Прежний поиск» фиксирует, что первый не менялся. Костыли, которых избегаем: особый случай по значению параметра, зависимость от порядка маршрутов.

### 2. Откуда справочник берёт данные

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. SQL на каждый запрос: `names.normalized LIKE '%q%'`, `GROUP BY type` для счётчиков | Без памяти; задержка — запрос к базе на каждую страницу и отдельные на каждый фасет | Фильтр по эпохе по датам в SQL не выразить переносимо (`primary` — JSON; SQLite и PostgreSQL расходятся), пришлось бы держать вторую копию правила принадлежности или хранить вывод (запрещено О-8) | `LIKE '%…%'` — полный просмотр `names`; при 10× (≈ 200 тыс. названий) — сотни мс на PostgreSQL без `pg_trgm`, на SQLite хуже |
| Б. Снимок в памяти (общий с картой) и индекс справочника на снимок, фильтры в Python | Один проход базы на снимок; запрос — фильтрация списка (сейчас ≈ 700 записей — доли мс; при 10× ≈ 7 тыс. — единицы мс) | Правило «действующее утверждение» и отпечаток — в одном месте (`snapshot.py`), карта и справочник читают одно; принадлежность к эпохе — в `epochs.py` | Пересборка O(сущности + утверждения); окно устарелости гасит пересборки при фоновом извлечении; путь при 100× — вынести поиск в PostgreSQL (`pg_trgm`) за тем же интерфейсом `CatalogIndex.query` |
| В. Отдельный поисковый индекс (сервис поиска, Qdrant или PG FTS) | Новая инфраструктура, синхронизация через события | Знания о сущностях уходят в чужой сервис; нарушение «данные через сервис-владелец» в обратную сторону | Избыточно для тысяч записей |

Выбрано: **Б**. Чем платим: отпечаток базы (`snapshot.fingerprint`, 12 подзапросов, из них 7 `count(*)`) считается на каждом запросе справочника и карты, в том числе при `cached`; на PostgreSQL `count(*)` — полный просмотр таблиц, при 10× (≈ 20 тыс. названий, ≈ 4 тыс. утверждений) — единицы мс, это основная цена запроса, а не фильтрация. Если станет заметно — проверять отпечаток внутри окна устарелости не чаще раза в N секунд (только справочник; карта — без окна). Также платим памятью процесса (оценка при 10× ≈ 7 тыс. сущностей: 5–10 МБ на снимок, пик при пересборке — два снимка одновременно; замер tracemalloc — задача 4.8); справочник до 15 с может не видеть новую запись (настраивается; карта — без окна). Костыли, которых избегаем: вторая копия правила принадлежности в SQL, хранение выведенного, `sleep`-подобные задержки (окно — явный параметр с часами `Clock`, тестируется без ожидания).

### 3. Лимиты шлюза

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Только общий лимит частоты | Ноль кода в шлюзе | Требование «Бесплатное без ограничений платных» соблюдается буквально; цена запроса ограничена сервером (≤ 60 записей, ≤ 200 знаков) | При злоупотреблении — тот же общий лимит, что у чтения |
| Б. Квота в `PAID`, как у карты (`map`: 300/2000) | Строка в `limits.py` | Справочник становится «платным» без модели — противоречит смыслу квот (защита бюджета модели) | Читатель, листающий справочник, упирается в квоту и получает 429 вместо страницы |

Выбрано: **А**. Чем платим: от сканирования справочника защищает только общий лимит частоты (20/с на адрес). Костыли, которых избегаем: квота «на всякий случай» без бюджета за ней.

### 4. Где правило принадлежности к эпохе

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. В справочнике (`catalog.py`), карта считает сама на клиенте | Меньше файлов | Две копии правила (сервер и `model.ts`), клиентская не знает явной связи | Расхождения справочника и карты |
| Б. Отдельный модуль `knowledge/epochs.py`, требование в возможности `epochs`; справочник — первый потребитель, карта и контекст переходят на него в 2.2–2.3 | Небольшой модуль | Правило в одном месте сервиса-владельца | 2.2 удаляет клиентскую копию |
| В. Отложить фильтр по эпохе до 2.2 | Меньше в 2.1 | Без копий | Справочник 2.1 без фильтра, который просили в ТЗ |

Выбрано: **Б**. Чем платим: возможность `epochs` появляется в 2.1 с одним требованием, остальное в 2.2. Костыли, которых избегаем: копия логики в двух местах без общего теста (клиентская копия на карте снимается в 2.2, задача там).

### 5. Пагинация

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. `page`/`limit` по снимку | Просто; `total` и счётчики есть всегда | Устойчивость порядка — по `(ключ, id)` | При смене снимка между страницами запись может сдвинуться на соседнюю страницу — для справочника приемлемо |
| Б. Курсор (последний ключ) | Устойчивее при изменениях | Сложнее клиент («Показать ещё» и адрес) | Нет прямого перехода на страницу N |

Выбрано: **А**; клиент при «Показать ещё» убирает повторы по `id`. Чем платим: редкий пропуск записи при пересборке снимка между страницами.

## Концепт интерфейса

Страница — обычная страница продукта (`page`), не сцена стола. Сетка: боковая панель слева (свёрнута по умолчанию), содержимое, при открытой карточке — правая панель `SidePanel`. Токены и компоненты — из дизайн-системы (`pg-btn`, `badge`, `pg-notice`, `section-title`).

### Клавиатура и доступность

- «/» — фокус в поиск (не перехватывается, если фокус в поле ввода); Esc в поиске — очистить; ↓ из поиска — на первую запись; ↑/↓ по записям (roving tabindex в списке); Enter — карточка; Shift+Enter или кнопка — «На карте».
- Переключатели типов — `role="group"` с подписью «Тип», кнопки с `aria-pressed`; выбор эпохи и раздела — нативные `<select>` с подписями.
- Список — `<ul aria-label="Результаты">`, запись — ссылка-кнопка с доступным именем «Иммануил Кант, персона, 1724–1804».
- «Найдено: N» — `aria-live="polite"`, объявляется после загрузки, не на каждый ввод.
- Контраст и фокус-кольцо — токены дизайн-системы; при `prefers-reduced-motion` без анимации заполнителей.

## Функциональные сценарии

1. **Найти философа.** Читатель открывает «Справочник» в боковой панели → `/reference`, видит весь список по названию и счётчики → вводит «юм» → через 250 мс список сужается до «Дэвид Юм», «Юмор»(если есть) → Enter → справа карточка Юма. Адрес `/reference?q=юм`; ссылку можно отправить.
2. **Что было в эпоху.** Выбирает «Эпоха: Просвещение» → счётчики типов пересчитаны для эпохи → «События» → список событий Просвещения по названию → «По времени» → по годам.
3. **Что в моём учебнике.** «Раздел: Учебник N» → только сущности, о которых говорит учебник; переключатель «Понятия и учения» → понятия учебника. Если учебник закрыт в регионе — сообщение и «Все источники».
4. **Перейти к карте.** У «Критики чистого разума» — «На карте» → `/graph/<id>`, труд выбран.
5. **Старая закладка.** `/soon/reference` → адрес заменён на `/reference`, «Назад» уводит туда, где читатель был до закладки.
6. **Ошибка.** Сервис знаний перезапускается → сообщение и «Повторить»; после восстановления — список.

## Контракты для 2.4 (гео-таймлайн)

2.4 может брать из справочника списки сущностей по типу и эпохе: `GET /v1/catalog?type=place&limit=60&page=N` — все места; `type=person&epoch=<id>` — персоны эпохи. Координат мест в онтологии нет (это предмет 2.4). Форма записи (`id`, `type`, `label`, `dates`, `epochs`) — стабильная; новые поля добавляются только дописыванием.

## Риски

- **Память и пересборка при 10×.** Пересборка снимка при ≈ 7 тыс. сущностей и ≈ 4 тыс. утверждений — ожидаемо сотни мс на SQLite; пик памяти — два снимка одновременно (старый отдаётся, новый строится). Окно устарелости 15 с и блокировка от параллельных пересборок ограничивают ущерб; карта пересобирается без окна, как сейчас. Замер — задача тестировщика на синтетических 10× данных (без сети, в памяти SQLite), результат в `verification.md`.
- **Рефакторинг карты.** Вынос `_load`/`_fingerprint` может незаметно поменять карту. Защита — существующие `tests/knowledge/test_map.py`, `test_map_view.py` без правок и сравнение ответа `/v1/map` до и после на демо-данных.
- **Нормализация и латиница.** `normalize` не транслитерирует: «kant» найдёт только при варианте «Kant». Это осознанно (вне объёма).
- **Lead'овский прогон.** Справочник только читает базу; извлечение, очередь и реестр не меняются.
- **e2e и визуальная проверка** на машине агента (1 ГБ RAM, 1 CPU) не прогоняются: их прогоняют CI и Lead. Здесь — `tests/knowledge`, `tests/web` по одному файлу.

## Тестируемость

- **Время.** Сервер: окно устарелости и `built_at` — только через внедряемые часы (`ManualClock` в тестах), без `sleep`. Клиент: задержка ввода — `setTimeout`, отметки времени — `performance.now()`, не `Date`; тесты управляют временем через `page.clock`.
- **Серверные события в браузерных тестах.** `tests/web` получает фикстуру, поднимающую настоящее приложение знаний в процессе (SQLite, данные задаёт тест, шлюз проксирует `/api/knowledge` к нему); события `knowledge.*` наблюдаемы фикстурой `events` по `request_id`. Тесты задают данные сами; `?fixture=dense`, `seed_demo` и продуктовые фикстуры источником ожиданий не служат; `page.route` — только для крайних случаев (ошибка 503, задержка ответа, гонка). Эту фикстуру переиспользуют `add-epochs`, `add-epoch-context` и `add-geo-timeline`.
- **Интерфейсные результаты** (адрес, фокус, открытая карточка) клиентского журнала не имеют; их серверный якорь — событие загрузки данных с `request_id`; перечень таких THEN — в `verification.md`.

## Безопасность

- Параметры проверяются сервером (длина, коды типов, предел страницы); идентификатор эпохи проверяется через реестр типов, а не по строке.
- Вывод на странице — только текстовыми узлами React (без `dangerouslySetInnerHTML`); названия, описания, `q` и id из адреса — данные (требование «Безопасный вывод справочника»).
- События `knowledge.catalog.*` и `knowledge.snapshot.built` — только id, коды и числа.
- Вне объёма, отдельной задачей (`regional-access`): существующий `/v1/map?only_textbook=true` по закрытому учебнику раскрывает его охват; здесь не чинится, но и не повторяется в справочнике (`textbook_closed`).
- Текст поиска не пишется в журнал (только длина); регион не пишется.
- Закрытые источники: фильтр по закрытому учебнику не раскрывает упоминаний; описание — не цитата.
- Внутренних адресов не добавляется; маршрут публичный и только читает.
