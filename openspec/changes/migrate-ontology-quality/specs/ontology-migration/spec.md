## ADDED Requirements

### Requirement: Миграция существующей онтологии

Команда оператора SHALL приводить существующую онтологию к правилам языка, названий и качества персон. Шаги выполняются по порядку:

1. **QID из манифеста** (`manifest_qids`) — если задан манифест QID (`--manifest`), применяются его решения по правилам команды QID: подтверждённые QID записываются, пары `qid_taken` с решением человека передаются слиянию (`merge:qid_confirmed`), записи без решения (`pending`), у кандидата которых есть держатель (`holder`), ставятся в очередь `duplicate` с `reason="review:qid_candidate"`, если открытого пункта по паре нет.
2. **Язык по письменности** (`lang_fix`) — у каждого названия язык приводится к правилу `entity-naming`.
3. **Снятие мусора** (`retire`) — снимается действующая сущность, кроме источников библиотеки, если её основное название не проходит правило названий.
4. **Русские названия из Wikidata** (`wikidata_labels`) — для сущностей с QID и нерусским основным названием подпись `ru` записи становится основным названием, если она русская и проходит правило названий.
5. **Перевод моделью** (`translate`) — остальные нерусские основные названия, только по явному флагу.
6. **Слияние дублей персон** (`dedupe`) — по правилу слияния вариантов (`person-quality`). Совпадения основных названий у не-персон одного типа уходят в очередь проверки.
7. **Проверка сохранности** (`verify`).

Порядок шагов один и тот же в спецификации, в `STEPS` и в отчёте.

Каждое действие SHALL записываться в журнал действий запуска. Переименование MUST NOT менять идентификатор сущности. Утверждения, атрибуции и подтверждения MUST NOT удаляться, кроме свёртки повторов при слиянии.

**Учёт утверждений при проверке сохранности.** Утверждение *потеряно*, если до запуска оно было действующим, а после запуска:
- его нет (с учётом свёртки) или оно не действующее;
- и ни один его конец не снят;
- и оно не стало петлёй при слиянии.

Атрибуция *потеряна*, если её `(вид, автор с учётом перенаправлений, позиция)` нет у утверждения, в которое попало исходное. Точный повтор после свёртки потерей не считается, атрибуция с автором — снятой сущностью тоже.

**Аварийный откат.** Если потеряно хотя бы одно утверждение или одна атрибуция, запуск SHALL сам откатиться и завершиться с кодом 1 событием `knowledge.migration.aborted`.

**Сухой прогон** (`plan`) SHALL считать тот же отчёт без записи в базу и без вызова модели. Он выводит список снимаемых сущностей (`id`, `type`, `label`, `reason`) и список переименований (`id`, старое и новое название, источник).

**Отчёт** — JSON оператора. В нём:
- число действий по шагам и причинам;
- переименования по источникам (`wikidata`, `model`);
- непереведённые по причинам;
- слияния, свёртки, петли, пункты очереди;
- утверждения и атрибуции до и после, `lost`;
- А1 до и после.

**Журнал.**
- Каждый шаг пишет `knowledge.migration.step` ровно с полями `run_id`, `step`, `actions`, `dry_run`.
- Запуск пишет `knowledge.migration.run`.
- Ни в одном событии миграции MUST NOT быть названий сущностей и других текстов, только идентификаторы, коды и числа.

**Инвариант:** для любой онтологии после запуска нет потерянных утверждений и атрибуций. Ни одна действующая сущность (кроме источников) не даёт причины отказа правила названий. Сухой прогон не меняет дамп базы. Действия сухого прогона совпадают с действиями, которые записал запуск без перевода: тот же вид, та же сущность, те же значения.

#### Scenario: Синтетическая онтология стенда

- **GIVEN** онтология с симптомами П1–П4:
  - понятия «causality», «substance» с языком `ru`;
  - понятие «20.1», термин «Every», пустой термин;
  - персоны «your Lordship», «children», «blind mathematician», «Kepler and Des Cartes»;
  - «Berkeley»×3 без QID, у одной годы жизни 1685–1753 (однословным тёзкам без QID и дат слияние по названию не положено, `person-quality`);
  - «Hume» с QID Q41568 и «Юм» без QID; запись Q41568 в фикстуре Wikidata с подписью `ru` «Юм»;
  - «Гомер» с QID Q6691 и «Омир» без QID; в манифесте QID для «Омир» `wikidata: Q6691`, `decision: accepted`;
  - 40 утверждений с атрибуциями, из них 3 с концом-мусором и одно с атрибуцией-автором «your Lordship»
- **WHEN** запущен `run --translate model --manifest <манифест>`, фейковая модель переводит «causality» → «Причинность», «substance» → «Субстанция»
- **THEN**
  - снято 7 сущностей: `number`×1, `stopword`×1, `empty`×1, `not_a_name`×4;
  - «Berkeley» — одна персона;
  - «Hume» получил основное «Юм» из Wikidata и слит с «Юм» по общему основному названию: одна персона с QID Q41568, основное «Юм», вариант «Hume»;
  - у понятий основные «Причинность» и «Субстанция», варианты `en` прежние;
  - «Омир» слит в «Гомер» по подтверждению человека: одна персона «Гомер» с QID Q6691, вариант «Омир»;
  - в отчёте `statements.lost=0`, `attributions.lost=0`, `dropped_garbage=3`, `a1.after > a1.before`
- **AND** в журнале:
  - по одному `knowledge.migration.step` на каждый из семи шагов;
  - семь `knowledge.entity.retired`;
  - четыре `knowledge.entity.merged` (два с `reason="merge:name"` у «Berkeley», один `merge:name` у «Юм», один `merge:qid_confirmed` у «Гомер»);
  - `knowledge.migration.run` с `lost=0`

#### Scenario: Транслитерация без решения человека

- **GIVEN** синтетическая онтология, но в манифесте у «Омир» кандидат Q6691 с `decision: pending`
- **WHEN** запущен `run --translate model --manifest <манифест>`, затем замер
- **THEN** «Гомер» и «Омир» не слиты; в очереди проверки открыт пункт `duplicate` с этой парой; А4 = 1, итог замера «не выполнен»
- **AND** в журнале `knowledge.entity.merge_proposed` с `reason="review:qid_candidate"` и `knowledge.quality.measured` с `a4=1`

#### Scenario: Сухой прогон

- **WHEN** оператор запускает `plan`, затем `run --translate off`
- **THEN**
  - `plan` не изменил нормализованный дамп базы, модель не вызвана;
  - список снимаемых (`id`, `type`, `label`, `reason`) и действия `plan` совпадают с записанными `run` в журнале действий запуска;
  - числа отчёта `plan` равны числам отчёта `run`, кроме `run_id` и `dry_run`;
  - в `plan` `to_translate` и `batches` показывают объём перевода
- **AND** в журнале `knowledge.migration.run` с `dry_run=true`, затем с `dry_run=false`

#### Scenario: Потеря — аварийный откат

- **GIVEN** сбой, при котором шаг слияния теряет атрибуцию (подмена шага в тесте)
- **WHEN** запущен `run`
- **THEN** код выхода 1, нормализованный дамп базы равен исходному
- **AND** в журнале `knowledge.migration.aborted` с `lost_attributions ≥ 1` и `knowledge.migration.rolled_back` с тем же `run_id`

#### Scenario: Проверенное человеком не трогается

- **GIVEN** утверждение со статусом «проверено» у одной из персон «Berkeley»
- **WHEN** запущен `run`
- **THEN** утверждение со статусом «проверено» у оставшейся персоны
- **AND** в отчёте `statements.lost=0`

#### Scenario: В журнале нет названий

- **GIVEN** онтология, у всех названий которой есть уникальная метка-маркер (например, «Zq7Marker»)
- **WHEN** выполняются `plan`, `run --translate model` и `rollback`
- **THEN** ни одна строка сериализованного журнала событий всех трёх запусков не содержит маркера
- **AND** в журнале по `knowledge.migration.run` на `plan` и на `run`, затем `knowledge.migration.rolled_back`

#### Scenario: Инвариант миграции

- **WHEN** на произвольных онтологиях с симптомами П1–П4 и произвольных ответах фейковой модели выполняются `plan` и `run`. Генератор: кластеры дублей с QID у одной стороны, атрибуции на дубль и на мусор, проверенные утверждения, упоминания, портреты
- **THEN**
  - после `run` нет потерь;
  - ни одна действующая сущность (кроме источников) не даёт причины правила названий;
  - `plan` не изменил дамп;
  - действия `plan` совпадают с действиями `run --translate off`

### Requirement: Снятие мусорных сущностей

Снятая сущность MUST NOT показываться:
- в справочнике;
- в поиске по названию;
- на карте раздела и на глобусе;
- в упоминаниях;
- в карточках;
- в контексте ассистента;
- в кандидатах привязки при извлечении.

Её карточка SHALL отвечать 404, как для неизвестной сущности.

**Утверждения и атрибуции.** Утверждение, у которого хотя бы один конец снят, SHALL оставаться в базе и MUST NOT показываться нигде: снимок, справочник (в том числе вес), карта, карточки, граф, контекст ассистента. Атрибуция, автор которой — снятая сущность, MUST NOT показываться. Утверждение, у которого все атрибуции скрыты, не показывается.

**Учёт и возврат.** Снятие SHALL записывать номер запуска и причину. Возврат при откате восстанавливает показ.

**Журнал.**
- Снятие пишет `knowledge.entity.retired` ровно с полями `entity_id`, `type`, `reason`, `run_id`.
- Возврат пишет `knowledge.entity.restored` ровно с полями `entity_id`, `run_id`.

**Инвариант:** для любой онтологии и любого подмножества снятых сущностей:
- ни одна снятая сущность не встречается в ответах справочника, карты, карточек, графа и контекста ассистента;
- ни одно показанное утверждение не имеет снятого конца;
- ни одна показанная атрибуция не имеет снятого автора;
- число строк в таблицах утверждений и атрибуций не меняется.

#### Scenario: Номер раздела снят

- **GIVEN** понятие «20.1» с одним утверждением «Кант → 20.1»
- **WHEN** миграция снимает «20.1»
- **THEN**
  - справочник (`GET /api/knowledge/v1/catalog?q=20.1`) его не возвращает;
  - карточка `/api/knowledge/v1/entities/<id>/card` отвечает 404;
  - в `/api/knowledge/v1/entities/<Кант>/statements` и на карте нет утверждения «Кант → 20.1»;
  - строка утверждения в базе есть
- **AND** в журнале `knowledge.entity.retired` ровно с полями `{entity_id, type: "concept", reason: "number", run_id}`

#### Scenario: Ассистент не видит снятое

- **GIVEN** утверждение «Кант → your Lordship», персона «your Lordship» снята
- **WHEN** ассистент запрашивает контекст сущности «Кант» (`POST /api/knowledge/v1/internal/assistant/context`)
- **THEN** ответ успешен, утверждения со снятым концом в нём нет
- **AND** в журнале нет событий ошибки сервиса знаний

#### Scenario: Возврат при откате

- **WHEN** запуск, снявший «20.1», откатывается
- **THEN** «20.1» снова в справочнике, и утверждение «Кант → 20.1» снова показывается
- **AND** в журнале `knowledge.entity.restored` с тем же `run_id`

#### Scenario: Инвариант снятия

- **WHEN** на произвольных онтологиях снимается произвольное подмножество сущностей
- **THEN**
  - ни одна снятая не в справочнике, не на карте, не в карточках и контексте ассистента;
  - ни одно показанное утверждение не имеет снятого конца, ни одна показанная атрибуция — снятого автора;
  - число строк в таблицах утверждений и атрибуций не изменилось

### Requirement: Перевод названий

Нерусские основные названия SHALL получать русское основное название в таком порядке:
1. подпись `ru` записи Wikidata — для сущностей с QID;
2. перевод моделью — только по явному флагу `--translate model`.

*Русское название* — по `entity-naming`: есть кириллическая буква, нет латинских вне слов из римских цифр (`^[IVXLCDM]+$`).

**Пакеты.** Модель SHALL получать пакеты не больше заданного размера (по умолчанию 50). В пакете — номер `n` с 1, тип и название, без идентификаторов сущностей.

**Проверка ответа.** Для каждого предложения проверки идут по порядку, первая сработавшая даёт причину:
1. `unknown_item` — номера `n` нет в пакете;
2. `duplicate_item` — номер `n` встречается в ответе больше одного раза. Отклоняются **все** предложения с этим номером;
3. `not_russian` — название не русское;
4. `invalid:<причина>` — название не проходит правило названий для типа элемента.

Элемент пакета без предложений считается `missing`. Отклонённое MUST NOT записываться. Сбой шлюза пропускает пакет (`failed_batches`) и не прерывает запуск.

**Запись.** Принятое название SHALL становиться основным `ru`. Прежнее основное становится вариантом со своим языком, идентификатор сущности не меняется.

**Оценка стоимости.** `plan --estimate` SHALL делать один вызов модели на одном пакете без записи и показывать оценку полного перевода: стоимость пробы × число пакетов.

**Журнал.** Каждый пакет пишет `knowledge.migration.translated` ровно с полями `run_id`, `batch`, `accepted`, `rejected`.

**Инвариант:** для любого ответа модели:
- каждое записанное моделью название русское, проходит правило названий и относится к элементу своего пакета, номер которого встретился в ответе один раз;
- число записанных равно сумме `accepted`;
- без флага `--translate model` модель не вызывается ни разу.

#### Scenario: Пакет с ошибками модели

- **GIVEN** пакет: 1 «causality», 2 «substance», 3 «idea», 4 «mind» (понятия)
- **WHEN** фейковая модель отвечает `[{n:1, ru:"Причинность"}, {n:2, ru:"Substanz"}, {n:2, ru:"Субстанция"}, {n:7, ru:"Ум"}, {n:3, ru:"some"}]`
- **THEN**
  - записано только «Причинность»;
  - у «substance», «idea», «mind» основные названия прежние;
  - в отчёте `untranslated`: `duplicate_item=2`, `unknown_item=1`, `not_russian=1`, `missing=1`
- **AND** в журнале `knowledge.migration.translated` с `accepted=1`, `rejected=4`

#### Scenario: Русское стоп-слово от модели

- **WHEN** модель переводит понятие «every» в «Всякий» (в данных стоп-список дополнен «всякий»)
- **THEN** название не записано
- **AND** в отчёте `untranslated` `invalid:stopword=1`

#### Scenario: Подпись из Wikidata раньше модели

- **GIVEN** персона «Hume» с QID, в записи Wikidata подпись `ru` «Юм»
- **WHEN** запущен `run --translate model`
- **THEN** основное «Юм» из Wikidata, в перехваченных запросах к модели нет «Hume»
- **AND** в отчёте `renamed.wikidata=1`

#### Scenario: Без флага модель не вызывается

- **WHEN** запущен `run` без `--translate model`
- **THEN** фейковый провайдер не получил ни одного запроса с шаблоном `ontology.translate_names`; в отчёте `to_translate` — число нерусских основных названий
- **AND** в журнале нет `knowledge.migration.translated`

#### Scenario: Оценка стоимости

- **WHEN** оператор запускает `plan --estimate` при 120 названиях к переводу и размере пакета 50
- **THEN** модель вызвана один раз, дамп базы не изменился; в отчёте `batches=3` и `estimate_usd`, равная стоимости пробы × 3
- **AND** в журнале одно событие `knowledge.migration.translated`

#### Scenario: Инвариант перевода

- **WHEN** на произвольных ответах фейковой модели выполняется перевод. Генератор возвращает ответ и ожидаемые принятые и причины. Варианты ответов: верные, латиница, стоп-слова, чужие и повторные номера, пропуски, сбои шлюза
- **THEN**
  - записаны ровно ожидаемые названия;
  - причины отказов равны ожидаемым;
  - число записанных равно сумме `accepted`;
  - без флага запросов к модели нет

### Requirement: Откат миграции

Запуск миграции SHALL можно откатить по номеру запуска. Откат выполняет действия запуска в обратном порядке:
- отменяет слияния запуска, включая свёрнутые утверждения и QID удалённых;
- отменяет шаг QID из манифеста: удаляет QID, записанные запуском, и утверждения запуска команды QID (годы жизни, датировки, роли), кроме проверенных человеком;
- восстанавливает названия: тексты, виды, языки;
- возвращает снятые сущности;
- возвращает языки названий;
- закрывает пункты очереди проверки, созданные запуском, со статусом `rolled_back`.

**Чужие изменения.** Откат MUST NOT трогать изменения, сделанные после запуска другими запусками и людьми. Сущность, которую запуск переименовал, а потом переименовали снова, пропускается и считается в `kept`.

**Журнал.** Откат пишет `knowledge.migration.rolled_back` ровно с полями `run_id`, `actions`, `merges_undone`, `restored`, `kept`.

**Инвариант:** для любой онтологии, любого манифеста QID (или без него) и любого запуска без последующих изменений откат возвращает нормализованный дамп таблиц данных (сущности, названия, внешние идентификаторы, утверждения, атрибуции, подтверждения, упоминания, портреты) к состоянию до запуска.

#### Scenario: Полный откат

- **GIVEN** запуск из сценария «Синтетическая онтология стенда»
- **WHEN** оператор запускает `rollback <run_id>`
- **THEN** нормализованный дамп таблиц данных равен дампу до запуска. Это значит:
  - «Berkeley»×3, «Hume» (с QID) и «Юм», «Гомер» (с QID) и «Омир» (без QID) раздельно;
  - «20.1» и мусорные персоны снова видны;
  - у «causality» основное «causality» с языком `ru`, как до запуска;
  - QID и годы жизни, записанные шагом QID из манифеста, удалены
- **AND** в журнале `knowledge.migration.rolled_back` с `merges_undone=4`, `restored=7`

#### Scenario: Последующее изменение сохраняется

- **GIVEN** после запуска оператор сменил основное название «Причинность» на «Каузальность»
- **WHEN** запуск откатывается
- **THEN** «Каузальность» остаётся основным названием
- **AND** в журнале `knowledge.migration.rolled_back` с `kept=1`

#### Scenario: Инвариант отката

- **WHEN** на произвольных онтологиях, манифестах QID (решения `accepted`, `auto`, `pending`, с держателем и без) и ответах фейковой модели выполняется `run --manifest`, затем `rollback`
- **THEN** нормализованный дамп таблиц данных равен дампу до `run`

### Requirement: Замер качества онтологии

Команда только на чтение SHALL считать приёмочные критерии А1–А8 и печатать таблицу «критерий | значение | порог | итог». С флагом `--json` она выдаёт тот же результат в JSON.

**Обозначения.**
- *Действующая* сущность — не перенаправлена слиянием и не снята.
- *Название* сущности — основное русское, иначе первое основное, иначе первое любое.
- *Русское*, *нормализованное* и *правило названий* — по `entity-naming`.
- `P` — действующие персоны.

**Формулы и пороги.**

| # | Формула | Порог |
|---|---|---|
| А1 | доля действующих сущностей, кроме источников библиотеки, с русским названием | ≥ 0,90 |
| А2 | число действующих сущностей, кроме источников, у которых название даёт причину `number` | = 0 |
| А3 | число персон `P`, у которых название даёт любую причину правила названий для персоны | = 0 |
| А4 | число различных неупорядоченных пар `{a, b} ⊂ P` в объединении двух множеств: (1) пары, где нормализованное основное название одной совпадает с каким-либо нормализованным названием другой (основным или вариантом); (2) пары открытых пунктов очереди `duplicate` любой причины (в том числе `review:qid_candidate` и `review:qid_taken`). Пара считается один раз, даже если попала в оба множества. Пары, по которым человек закрыл пункт `duplicate` решением «разные» (`resolution.merge = false`), не считаются | = 0 |
| А5 | число персон `P` с основной датой | ≥ 20 |
| А6 | число записей раздела `people` ответа карты раздела по всей библиотеке (`GET /api/knowledge/v1/map` без учебника), у которых в `roles` есть `philosopher` | ≥ 10 |
| А7 | число элементов справочника (`GET /api/knowledge/v1/catalog`, все страницы, `lang=ru`, без фильтров), у которых название не проходит правило названий своего типа | = 0 |
| А8 | число потерянных утверждений и атрибуций (определения из «Миграции существующей онтологии») относительно базы сравнения: `--save` до миграции, `--baseline` после | = 0 |

Без базы сравнения А8 — «не измерено», итог «не выполнен». Команда считает А6 и А7 теми же объектами сервиса знаний, что отвечают на эти адреса.

**Только чтение.** Команда MUST NOT записывать в базу:
- соединение только на чтение;
- миграции схемы не выполняются;
- она SHALL работать и на схеме до снятия сущностей, чтобы сохранить базу сравнения до миграции.

**Код выхода:** 0 — все пороги выполнены, 1 — нет, 2 — ошибка.

**Журнал.** Событие `knowledge.quality.measured` ровно с полями `a1`…`a8`, `passed`, `failed`.

**Инвариант:** для любой онтологии:
- замер не меняет дамп базы;
- каждое из А1–А8 равно своей формуле, посчитанной независимо по дампу и по ответам API;
- итог «выполнен» тогда и только тогда, когда все восемь порогов выполнены, а код выхода соответствует итогу.

#### Scenario: Синтетическая онтология до и после

- **GIVEN** онтология из сценария «Синтетическая онтология стенда» и база сравнения, сохранённая `--save` до миграции
- **WHEN** замер запускается до миграции и после `run --translate model --manifest <манифест>` с `--baseline`
- **THEN**
  - до: А2 = 1, А3 = 4, А4 = 3 (три пары «Berkeley»; «Гомер»/«Омир» не в очереди и без общего написания), итог «не выполнен», код 1;
  - после: А2 = А3 = А4 = А7 = 0, А8 = 0, А1 равна доле, посчитанной в тесте по дампу;
  - вывод — таблица из восьми строк с порогами
- **AND** в журнале два события `knowledge.quality.measured`, второе с `a8=0`

#### Scenario: А4 — объединение и решение «разные»

- **GIVEN** персоны «Бэкон» (основное) и «Фрэнсис Бэкон» с вариантом «Бэкон», по паре открыт пункт `duplicate` (`review:variant`); персоны «Роджер Бэкон» с вариантом «Бэкон» и «Бэкон» — второй экземпляр, пункт по их паре закрыт решением «разные»
- **WHEN** запущен замер
- **THEN** пара «Бэкон»/«Фрэнсис Бэкон» посчитана один раз, хотя попала и по названию, и через очередь; пара с решением «разные» не посчитана
- **AND** в журнале `knowledge.quality.measured` с `a4` равным числу различных оставшихся пар, посчитанному в тесте по дампу

#### Scenario: А6 и А7 совпадают с API

- **WHEN** замер запускается на онтологии с тремя философами с датами (роль `philosopher`), одним учёным с датами и одним философом без дат
- **THEN** А6 = 3 и равно числу записей `people` с `philosopher` в ответе `GET /api/knowledge/v1/map`; А7 равно числу элементов ответа `GET /api/knowledge/v1/catalog` (все страницы), не проходящих правило названий
- **AND** в журнале `knowledge.quality.measured` с `a6=3`

#### Scenario: Без базы сравнения

- **WHEN** замер запускается без `--baseline`
- **THEN** строка А8 «не измерено», итог «не выполнен», код 1
- **AND** в журнале `knowledge.quality.measured` с `a8=null`, `passed=false`, `failed` содержит `8`

#### Scenario: Только чтение

- **WHEN** замер запускается на базе SQLite
- **THEN** дамп базы и время изменения файла не изменились; попытка записи через соединение замера отклонена базой
- **AND** в журнале `knowledge.quality.measured`

#### Scenario: Старая схема

- **GIVEN** база на схеме до снятия сущностей
- **WHEN** запускается замер с `--save before.json`
- **THEN** замер выполнен, файл базы сравнения записан, номер схемы базы не изменился
- **AND** в журнале `knowledge.quality.measured`

#### Scenario: Инвариант замера

- **WHEN** на произвольных онтологиях (генератор миграции) выполняется замер
- **THEN**
  - дамп базы не изменился;
  - каждое из А1–А8 равно значению, посчитанному в тесте независимо по дампу и ответам API по формулам требования (без вызова кода замера и `naming`);
  - итог «выполнен» ⇔ все пороги выполнены;
  - код выхода соответствует итогу
