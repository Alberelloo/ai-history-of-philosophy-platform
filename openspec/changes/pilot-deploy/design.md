# Design

## Выбор решения

### Плановый запуск `check-updates`

ADR-0003 обещает проверку обновлений раз в неделю. Команда `python -m philograph.library.catalog check-updates` проверяет файлы условными запросами и применяет правило публикации. По расписанию её сейчас никто не запускает.

| Вариант | Оптимальность | Архитектурная правильность | Поддерживаемость и масштабируемость |
|---|---|---|---|
| А. Cron или таймер systemd на хосте, команда из `source-ingestion.md` | Самый быстрый: строка в crontab и абзац в runbook | Расписание живёт вне репозитория и вне compose. Сбой не виден оповещениям: правила `ops` о нём не знают | Теряется при переезде на новый сервер. Раздел runbook «Восстановление после потери сервера» пришлось бы дополнять вручную. Тестами не проверяется |
| Б. Планировщик сервиса `ops`: раз в неделю ставит задачу `library.check_updates` в очередь, у сбоя есть правило оповещения | Немного кода: в `ops` уже есть `Scheduler` для ночных копий | Расписание там же, где расписание копий, и в той же версии образа. Задачу исполняет `worker` библиотеки | Переживает пересборку сервера, проверяется тестами, сбой приходит оповещением |
| В. Отдельный сервис-планировщик (cron-контейнер) в `compose.prod.yaml` | Новый образ и сервис ради одной задачи | Дублирует `Scheduler` из `ops` | Ещё один сервис, за которым нужно следить |

**Выбрано Б.** Платим отдельным изменением со спецификацией: расписание и оповещение о сбое — новое наблюдаемое поведение (дельта `source-catalog`, при необходимости `operational-alerts`). Поэтому в этом изменении, где `skip_specs: true`, остаётся только задача его завести (2.1). Чего избегаем: правила, которое живёт вне репозитория и молча пропадает при восстановлении сервера.

Одно расхождение нужно разобрать в той спецификации. Правило публикации («новая версия публикуется сама, только если изменения малы») применяет команда каталога, а не задача очереди: так написано в `source-ingestion.md`, раздел «Плановый запуск». Либо задача очереди должна применять то же правило, либо `ops` должен звать команду. Решение принимается в новом изменении.

### Раскладка `pilot-launch` на три изменения

Простейший вариант — обновить `pilot-launch` на месте. Он отвергнут: в одном изменении оказались бы задачи с разными зависимостями (данные, замеры, инфраструктура), и его нельзя было бы закрыть по частям. Три изменения закрываются независимо, у каждого свой `progress.md`.
