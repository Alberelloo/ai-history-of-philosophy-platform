# Design

Изменение закрывает пункты аудита 1.1–1.5, 1.8, 1.12–1.15 и «Критично» 7. Каждый пункт — отдельное решение. Варианты оцениваются по трём критериям из `docs/process/working-principles.md`, раздел 5.

## Выбор решения

### 1. Секрет посетителя и настройки сервисов (1.1, 1.5)

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Убрать только `"dev-secret"`: `os.environ["PHILOGRAPH_VISITOR_SECRET"]` | Две строки | Падение `KeyError` при импорте, без события и без имени в понятном виде; остальные 18 мест как были | Правило «проверить при старте» по-прежнему в каждом модуле своё |
| Б. Класс настроек на сервис (`ServiceSettings`), фабрика `create(env)` читает его при старте; `uvicorn --factory` | Новых зависимостей нет (pydantic-settings уже есть). Цена — правка команд запуска | Одно правило в `platform.settings`: чтение, проверка, событие `service.settings.invalid`, событие о необязательной зависимости. Приложение не собирается при импорте модуля, поэтому импорт в тестах не зависит от окружения | Новая настройка — поле класса. Необязательные зависимости описаны данными (`optional = {поле: что не работает}`), а не ветками кода |
| В. Один общий класс настроек на всю систему | Меньше классов | Сервис узнаёт о чужих настройках; при старте падает из-за настройки, которая ему не нужна | Плохо: любая новая настройка трогает всех |

Выбрано: Б. `platform.settings.load(cls, env)` читает поля класса из окружения (по умолчанию `os.environ`, в тестах — словарь). Пустая строка считается отсутствием значения, поэтому пустой секрет — тоже ошибка. Для полей из `optional` со значением `None` пишется `service.settings.optional_absent` (`settings`, `setting`, `effect`). Ошибки разбора, которые возникают вне pydantic (квоты лимитов, ключи провайдеров), идут через тот же `settings.fail`, чтобы событие и исключение были одинаковыми.

Секрет посетителя — обязательное поле `visitor_secret: SecretStr` у `AssistantSettings` и `GatewaySettings`. Значение регистрируется в `events.register_secret`, чтобы не попасть в журнал. `assistant.app.build_app` получает секрет параметром, без значения по умолчанию.

Точки входа: `philograph.<сервис>.main:create` с `uvicorn --factory`. Флаг `PHILOGRAPH_KNOWLEDGE_SERVICE`, который нужен был только как условие сборки при импорте, больше не нужен. Шлюз получает свой `gateway/main.py`. Команды (исполнитель, `ops`, миграции, CLI каталога и портретов) читают свои классы настроек так же.

Чем платим: команды запуска в `compose.yaml` и `scripts/dev_stack.py` меняются (`--factory`); тесты, которые собирают ассистента через `build_app`, передают секрет явно. `PHILOGRAPH_INTERNAL_TOKEN` (`platform/web.py`) и `PHILOGRAPH_STATE_DIR` (`platform/lifecycle.py`) остаются чтением окружения в общем каркасе: это не настройка сервиса, а общий механизм, и у обоих есть осмысленное «не задано».

Костыли, которых избегаем: значение секрета по умолчанию; сборка приложения при импорте по условию `if os.environ.get(...)`; `KeyError` вместо сообщения.

### 2. Воспроизводимость (1.2, 1.3, 1.15)

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. pip-tools: `requirements.lock` с хешами, `pip install --require-hashes` | Нового инструмента в Docker нет | Lock под одну платформу: Linux в Docker и CI, а владелец работает на Windows — нужен второй lock | Два файла под платформы, extras — отдельными файлами |
| Б. uv: `uv.lock` (универсальный, все платформы и extras), `uv sync --frozen` в Docker и CI | Один файл; установка в CI быстрее pip | `pyproject.toml` остаётся источником диапазонов, lock — точных версий; `uv lock --check` в CI ловит рассинхрон | Dependabot умеет экосистему `uv`. Локально по-прежнему работает `pip install -e ".[dev]"` |

Выбрано: Б. uv закреплён версией (`ghcr.io/astral-sh/uv:0.13.6` в Docker, `astral-sh/setup-uv` с той же версией в CI). `uvicorn[standard]` переехал из команды в Dockerfile в extra `server`, чтобы тоже попасть в lock.

Базовые образы — точный тег и digest (`python:3.13.18-slim@sha256:…`, `node:24.22.3-slim@…`, `postgres:16.15@…`, `caddy:2.8.4@…`, `qdrant/qdrant:v1.12.4@…`). Digest защищает от подмены тега, тег оставлен для читаемости и для Dependabot. Caddy остаётся на 2.8: переход на 2.11 меняет сервер HTTPS и требует отдельной проверки развёртывания; Dependabot предложит его отдельным PR.

Actions — по полному SHA с тегом в комментарии (`actions/checkout@<sha> # v4.4.0`). Мажорные версии не повышаются в этом изменении: их предложит Dependabot. Тег можно перевесить, SHA — нет, а Dependabot обновляет SHA вместе с комментарием.

`.github/dependabot.yml`: `uv` (корень), `npm` (`web/`), `docker` (`Dockerfile`), `docker-compose` (compose-файлы), `github-actions`. Раз в неделю, мелкие обновления группируются.

### 3. CI (1.4, 1.15)

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Перевести фикстуру `tests/web` на `PHILOGRAPH_TEST_DATABASE_URL` | Ещё один прогон браузерных тестов в `checks` (несколько минут) | Браузерные тесты проверяют клиент и шлюз против одного процесса; от базы в них зависит только хранение библиотеки, а оно уже проверено `tests/library` на PostgreSQL | Время CI растёт с каждым браузерным тестом |
| Б. Исключить `tests/web` из прогона на PostgreSQL (`--ignore=tests/web`) | Время падает на длину прогона `tests/web` | Ответственность прогонов ясна: SQLite — всё без e2e, PostgreSQL — поведение хранилищ | Новый браузерный тест не удлиняет второй прогон |

Выбрано: Б. Ещё: шаг `Pytest (SQLite)` запускает `-m "not e2e"` — e2e идут в задании `e2e`; удалён мёртвый шаг «Есть ли Python-проект» и все `if:` по нему; `uv lock --check`. Предел времени `checks` снижен по замеру (в `progress.md`).

### 4. OCR в рабочем образе (1.8)

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Tesseract 5 с языками rus, lat, grc, eng, deu, fra в рабочем образе, `TesseractOcr` в исполнителе | Плюс около 150 МБ к одному образу всех сервисов; распознавание сотен страниц на одноядерном сервере занимает процессор, нужный читателям | Противоречит требованию «Обработка не мешает читателям» без выноса исполнителя на отдельную машину | Каждое обновление образа тянет Tesseract |
| Б. OCR вне сервера: в каталог берутся издания с текстовым слоем; скан без текстового слоя останавливается на шаге извлечения с понятной ошибкой «распознавание не задано» и разбирается оператором локально (extra `ocr`) | Ничего не добавляется | Конвейер уже поддерживает OCR через параметр, решение — где его включать | Пересмотр — когда нужное издание есть только сканом или исполнитель уедет на отдельную машину |

Выбрано: Б. Сейчас в каталоге 317 записей, отбор шёл по наличию текстового слоя (EPUB, PDF с текстом, `djvu.txt`), записи только со сканом не одобряются (пример — запись Гегеля «Наука логики», т. 1). Решение записано в ADR-0001.

### 5. Еженедельная проверка обновлений каталога

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. systemd timer на сервере: `docker compose run --rm worker python -m philograph.library.catalog check-updates` | Ноль кода | Расписание живёт вне репозитория и вне стенда e2e; его надо ставить руками и нечем проверить в CI | Забывается при переезде сервера |
| Б. Отдельный контейнер-планировщик (cron, ofelia) в compose | Новый образ и зависимость | Второй планировщик рядом с уже существующим в `ops` | Две системы расписаний |
| В. Планировщик `ops` раз в неделю ставит задачу `library.catalog.check_updates` в очередь, исполнитель выполняет `check-updates` каталога | Несколько десятков строк | `ops` знает только имя задачи и очередь из `platform`, не импортирует библиотеку. Когда задача ставилась, хранится в журнале запусков `ops.runs`: перезапуск не даёт лишней проверки и не пропускает плановую. Ключ задачи — неделя ISO, повторная постановка не создаёт дубля | Одно место для всех расписаний; проверяется тестом без часов реального времени |

Выбрано: В. Окно — то же, что у копий (`backup_hour`, по умолчанию 03:00 UTC), раз в 7 дней. События: `ops.check_updates.scheduled` (`job_key`) в `ops` и `library.catalog.check_updates.finished` (`checked`, `outcomes`) в исполнителе. Путь к каталогу — настройка исполнителя `PHILOGRAPH_CATALOG_PATH` (в образе `/app/sources/catalog.yaml`).

### 6. Счётчики лимитов шлюза (Критично 7)

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Счётчики в PostgreSQL (таблица в схеме шлюза, атомарный upsert) | Запрос к базе на каждый запрос посетителя, в том числе бесплатный (общий лимит частоты); у шлюза появляется база и миграции | Шлюз становится сервисом с данными | Нужен при нескольких репликах |
| Б. Осознанное ограничение: одна реплика шлюза, счётчики в памяти, перезапуск их сбрасывает | Ноль задержки | Без изменений | Записано в ADR-0004 с условием пересмотра |

Выбрано: Б, ADR-0004. Пересмотр: вторая реплика шлюза, частые перезапуски шлюза или расход по платным операциям, который сброс лимитов делает заметным. Деньги защищает не только лимит посетителя, но и дневной бюджет сервиса LLM, который хранится в базе и перезапуск переживает.

### 7. Прод-образ без отладочных частей (1.14)

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. Не копировать `scripts/` и `demo/` вообще | Минимум | Ломает стенд e2e: `seed` запускает `scripts/seed_demo.py` с `demo/`, проверка перезапуска (`tests/ops/test_deploy.py`) — `scripts/crash_service.py` | — |
| Б. Две цели Dockerfile: `runtime` без `scripts/` и `demo/`, `e2e` поверх `runtime` с `seed_demo.py`, `crash_service.py` и `demo/`; `compose.e2e.yaml` собирает цель `e2e` под своим именем образа | Слои общие, вторая цель — несколько КБ | Прод-образ содержит только код сервисов, конфиги и каталог источников | Новый отладочный скрипт по умолчанию в прод не попадает |

Выбрано: Б. Кто что использует: `scripts/deploy.py` запускается на хосте; `evaluate.py`, `visual_check.py`, `dev_stack.py`, `design_tokens.py`, `check_traceability.py` — машина разработчика и CI; в контейнерах нужны только `seed_demo.py` (сервис `seed` стенда e2e) и `crash_service.py` (`test_deploy.py` на стенде e2e).

### 8. Мелочи (1.12, 1.13, 1.15)

- `philograph.knowledge` добавлен в контракт независимости import-linter; нарушений нет.
- Сетевые сбои с запасным путём пишут событие уровня warning с `error_kind`: `knowledge.portraits.download_failed` (`commons_file`) и `library.catalog.lookup_failed` (`lookup`). Неудачная запись итога резервной копии — `ops.backup.record_failed`.
- Лямбды с `noqa: E731` в `evaluation/runs.py` заменены функциями; `type: ignore[arg-type]` в CLI каталога убран: команды `add` и `harvest` получают сервис без учёта источников через отдельный конструктор.

## Риски

- `uvicorn --factory` ловит `SettingsError` как ошибку запуска: процесс завершается с кодом 1, в журнале — событие `service.settings.invalid`. Контейнер с `restart: unless-stopped` перезапускается по кругу, пока настройку не исправят, — это ожидаемо и видно оператору.
- Dependabot по SHA создаёт больше PR; группировка мелких обновлений их сокращает.
- Если в lock попадёт пакет без колеса под Linux, сборка образа это покажет сразу: `uv sync --frozen` не разрешает зависимости заново.
