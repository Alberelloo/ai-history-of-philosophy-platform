## 4. Покрытие требований тестами и инвариантами

**Цифры:**
- 37 возможностей, 350 требований, 604 сценария;
- 727 тестовых функций, из них 708 с маркером `req`;
- у 222 требований (63%) ровно один тест.

### 4.1. Что на самом деле проверяет прослеживаемость

`scripts/check_traceability.py` сверяет только, есть ли у пары «возможность, требование» хотя бы один маркер:
- `#### Scenario:` не разбирает;
- тело теста не смотрит;
- skip/xfail и сам запуск теста не учитывает;
- маркер с нелитеральным аргументом молча пропускает;
- засчитывает и вложенные функции, которые не являются тестами.

Поэтому «350 из 350» означает «у каждого требования есть маркер», а не «каждый сценарий проверен».

### 4.2. Сценарии

**Оценка сверху.** У 75 требований тестов меньше, чем сценариев; непарных сценариев не меньше 95. Больше всего их в source-library и source-registry (по 13), source-processing (9), llm-gateway (8), chapter-reading (7).

**Ручная выборка: сценарии, чьё THEN не проверено.**

| Возможность | Сценарий | Что не так |
|---|---|---|
| question-routing | Типы вопросов | Фейковая модель сама возвращает тип, тест проверяет только передачу. В примере «Карта» не проверено «в извлечённых именах „эмпиризм“» |
| question-routing | Заданные цепочки шагов | Не проверены «если найдено мало — во всей библиотеке» и «разделяет, что пишет каждый» |
| source-library | Список, Сочетание поиска и фильтров | Из 5 сценариев проверен один; «Оба фильтра» не выполняется |
| source-processing | Продолжение с места сбоя | Вид ошибки `unexpected` и продолжение пакета не проверены |
| regional-access | Регион не сохраняется | Нет теста, что страны нет в базе, метриках и журналах |
| ontology-review | Доступ | Отказ оператору без права «проверять онтологию» не проверен, хотя роли в коде есть |
| knowledge-graph | Ограничение размера | Подсказка «Сузьте окно времени» не проверена |

abuse-protection и llm-gateway проверены глубоко: по журналу и по тому, что провайдер не вызывался.

- **Ожидания по таймеру.** 36 тестов с `req` ждут через `wait_for_timeout`/`sleep`. Проверки отсутствия после фиксированной паузы могут быть ложно зелёными: `tests/web/test_reader_cards.py:369-375`, `tests/web/test_reader_notes.py:328`.
- **Зависимость от скорости машины:** `tests/library/test_processing.py:223` (`elapsed < 0.5`).
- **Условные пропуски.** Пропуск по строке в исходнике `tests/web/test_assistant_dialogs.py:835` молча сработает после переименования хука. Пропуски без node и без Docker: `tests/ops/test_deploy.py` в этой сессии не запускался — в docker нет плагина compose.
- **Снимочные тесты с функциональными маркерами** раздувают покрытие. Пример: `test_answer_states` засчитан за три требования assistant-dialog.
- **E2E.** 6 файлов, 71 тест; журнал проверяют 13 из них. **В 18 из 37 возможностей нет ни одного e2e.** Среди них свежие regional-access и entity-portraits, где поток идёт через CDN и оператора.

### 4.5. Нефункциональные требования

- **Снимки.** Эталоны есть только в `tests/e2e/visual/baselines/win32/`. Без эталона сравнение пропускается (`tests/e2e/visual.py`), а CI работает на Linux, поэтому **снимки в CI не сравниваются**. По DOM проверяются токены, контраст 4.5:1, кольцо фокуса и отсутствие прокрутки.
- **Доступность.** Аудита axe/ARIA нет. Клавиатура проверена на библиотеке и настройках.
- **Задержки.** Числовые границы в спецификациях отложены. Нагрузочных проверок и проверок задержки нет.
- **Стоимость и бюджеты.** Покрыты хорошо: фейковый провайдер, управляемые часы, журнал.
- **Качество LLM.** Тесты quality-evaluation проверяют механику оценки. Прогона оценки с порогами нет ни в CI, ни по расписанию.

## 5. Каркас работы

### 5.1. Скиллы

В репозитории (`.claude/skills/`, `.claude/commands/opsx/`) лежат шесть скиллов OpenSpec и шесть команд `/opsx:*`:
- propose, explore, apply;
- update, sync, archive.

Это стандартный набор, сгенерированный `openspec init`, своих в нём нет. `.dsh/skills/` и `.claude/agents/` нет. Общих настроек `.claude/settings.json` в репозитории нет, только локальный `settings.local.json`.

**Чего не хватает (по убыванию пользы):**

| Скилл | Зачем |
|---|---|
| `verify-invariants` | Пройти по сценариям изменения: для каждого найти тест, проверяющий вывод, и тест, проверяющий журнал; прогнать; собрать события одного `request_id` с живого стенда; доложить пробелы. Сейчас это делается вручную и зависит от памяти сессии |
| `review-change` (судья) | Независимая вычитка изменения по спецификации, без доступа к рассуждениям автора: spec ↔ код ↔ тесты, мутационные проверки ключевых правил. Требование CLAUDE.md «код вычитываем» сейчас ничем не обеспечено |
| `visual-check` | Скриншоты на 1024/1366/1920 в обеих темах, проверка прокрутки и пересечений; сейчас временные тестовые файлы пишутся и удаляются каждой сессией заново |
| `run-stack` | Поднять `dev_stack`, задать вопрос, прочитать журналы всех сервисов по `request_id` |
| `pr-ship` | Ветка, коммит, PR по шаблону, слежение за CI, перезапуск по таймауту, перебазирование после слияния |

### 5.2. AGENTS.md

**AGENTS.md нет**, есть только `CLAUDE.md` на 19 строк. В нём:
- описание продукта;
- правила веток, PR и автослияния;
- «код вычитываем».

Чего в нём нет:
- команд проекта (venv, `pytest`, `ruff`, `lint-imports`, `check_traceability.py`, `npm run build`, `dev_stack.py`);
- карты сервисов и границ;
- правил тестов и журнала, ролей агентов;
- известных ловушек окружения: нет CLI `openspec` и плагина docker compose; эталоны снимков только Windows; рендер для визуальных проверок.

К тому же в нём устаревшая строка «Стек не выбран».

**Как должно быть.** AGENTS.md — общий для любых агентов файл с командами, картой кода и правилами. CLAUDE.md ссылается на него и хранит только особенности Claude Code. Сюда же ссылки на документ принципов (5.3) и на скиллы.

### 5.3. Документ принципов работы

| Принцип | Где записан | Оценка |
|---|---|---|
| OpenSpec: сначала спецификация, потом код; контрольные точки `progress.md`; архив в том же PR | `docs/process/openspec-workflow.md`, CLAUDE.md | **Есть**. Но в нём устаревшая строка про синтаксис MODIFIED/REMOVED: изменения существующих спецификаций давно делаются. И не сказано, что CLI в облачных сессиях нет и перенос дельт выполняет скилл |
| Каждое требование покрыто тестами, инварианты проверяются **и по журналу, и по выводу** | Нигде. Есть маркер `req` и скрипт прослеживаемости (только требования); правило «журнал + вывод» существует лишь как устная договорённость с владельцем | **Нет — недочёт** |
| Несколько ролей агентов: разработчик, тестировщик, судья-верификатор | Упоминания мельком: «роль» субагента в `progress.md`, «раунды тестировщика» в `docs/process/reader-handoff.md` | **Нет — недочёт** |
| Ревью перед слиянием | `docs/process/git-workflow.md`: ревью не обязательно, PR сливается сам по зелёным проверкам | **Расходится** с «сгенерированное без проверки в `main` не попадает»: проверку делает та же сессия, что писала код |

**Как должно быть.** Нужен документ `docs/process/working-principles.md` (и скилл, который его применяет). В нём:

1. **Цикл изменения.**
   1. Спецификация: сценарии WHEN/THEN, каждый THEN наблюдаем — в выводе (ответ API, интерфейс) и в журнале (событие с полями).
   2. Реализация.
   3. Тесты на каждый сценарий: проверка вывода и проверка события. Исключения (чисто визуальные требования) перечислены явно.
   4. Проверка на живом стенде: вывод и журнал по одному `request_id`.
   5. Мутационная проверка ключевых правил.
   6. Архив.
2. **Роли и передача.**
   - **Разработчик:** пишет спецификацию и код, свои тесты.
   - **Тестировщик:** независимо от разработчика пишет и дополняет тесты по сценариям, ищет непокрытые THEN, проверяет журнал; кода не правит.
   - **Судья-верификатор:** получает спецификацию, дифф и результаты, но не рассуждения разработчика. Выносит вердикт по каждому сценарию: подтверждено выводом, подтверждено журналом, не подтверждено. Без его вердикта PR не переводится из draft.
   
   Каждая роль пишет в `progress.md` своё имя и итог.
3. **Критерии готовности.**
   - Прослеживаемость до сценариев.
   - Доля требований с проверкой журнала не снижается.
   - Снимки сравниваются в CI.
   - Предел вызовов модели и стоимость указаны.
4. **Когда спрашивать владельца.** Спорные решения — draft-PR. Что считается спорным: изменение поведения вне спецификации, новые внешние сервисы, деньги, юридические вопросы источников.
