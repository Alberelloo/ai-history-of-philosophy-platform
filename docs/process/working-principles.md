# Принципы работы: роли, цикл, тесты, модели, выбор решения

Как команда агентов делает изменение в PhiloGraph от спецификации до слияния. Документ общий для людей и агентов. Краткая выжимка — в [AGENTS.md](../../AGENTS.md), инструкции ролей — в скиллах `.claude/skills/role-*`, определения субагентов с моделями — в `.claude/agents/`.

Три правила, из которых выводится остальное:

1. **Сначала спецификация, потом код.** Любое изменение поведения идёт через OpenSpec ([openspec-workflow.md](openspec-workflow.md)).
2. **Каждое требование подтверждено дважды.** Подтверждение — тестом, который видно в журнале тестировщика, и в итоговом выводе системы, который судья получает сам. Совпадение двух источников — защита от подгонки результата (reward hacking).
3. **Решение выбирается по трём критериям** (раздел 5) и записывается до реализации.

## 1. Роли

| Роль | Что делает | Чего не делает | Модель | Скилл / субагент |
|---|---|---|---|---|
| **Ведущий** (основная сессия) | Ведёт цикл: заводит изменение, передаёт работу ролям, держит `progress.md`, открывает PR | Не пишет вердикт за судью и тесты за тестировщика | Opus | `change-loop` |
| **Разработчик** (coder) | Пишет предложение, дизайн с выбором решения (раздел 5) и код; юнит-тесты своих модулей | Не ослабляет и не переписывает тесты тестировщика; не меняет спецификацию молча | Opus | `role-coder` / `coder` |
| **Тестировщик** (tester) | По спецификации, не по коду, пишет сценарные и нормативные тесты (раздел 3), прогоняет, ведёт журнал проверки `verification.md` | Не правит продуктовый код; не подгоняет ожидания под фактический вывод | Sonnet | `role-tester` / `tester` |
| **Исполнитель прогонов** | Механически запускает заданные команды и собирает вывод и журналы по `request_id` | Не делает выводов и не правит файлы | Haiku | `test-runner` |
| **Ревьювер** (reviewer) | Читает дифф: соответствие спецификации, архитектура, критерии выбора решения, костыли, безопасность | Не правит код сам: замечания уходят разработчику | Opus | `role-reviewer` / `reviewer` |
| **Судья** (judge) | Независимо проверяет итог: всё ли из `tasks.md` сделано, каждый сценарий подтверждён, журнал тестировщика совпадает с собственным прогоном, нет подгонки | Не видит рассуждений разработчика, только спецификацию, дифф, журнал проверки и систему; не чинит | Opus | `role-judge` / `judge` |

Роли разделены, чтобы один агент не проверял сам себя:
- тестировщик пишет тесты по спецификации, не заглядывая в код;
- судья получает результат, а не рассказ о нём.

Если субагенты недоступны, роли выполняет одна сессия по очереди. Тогда каждую роль она начинает с чистого чтения артефактов (спецификации, диффа, журнала), а не из памяти о том, как писала код, и в `progress.md` пишет, что роли совмещены.

## 2. Цикл изменения

```
  предложение ─► решение владельца (если спорно) ─► разработчик ─► тестировщик ─► ревьювер ─► судья ─► PR
                                                         ▲             │              │           │
                                                         └─────────────┴──────────────┴───────────┘
                                                           замечания возвращаются разработчику
                                                           (тесту — тестировщику)
```

1. **Предложение** (разработчик, `/opsx:propose`): `proposal.md`, `design.md` с разделом «Выбор решения», дельты спецификаций и `tasks.md`. В `tasks.md` всегда есть задачи тестировщика и судьи. Если меняется поведение вне исходного запроса, есть деньги, внешний сервис или юридический вопрос источников, ведущий спрашивает владельца до реализации.
2. **Реализация** (разработчик, `/opsx:apply`): код и юнит-тесты; после каждого пункта отметка в `tasks.md`, запись в `progress.md`, коммит `wip(<имя>): …`.
3. **Тесты** (тестировщик): сценарные и нормативные тесты по каждому требованию дельты, прогон, журнал `verification.md`. Мутационная проверка ключевых правил (раздел 3.5). Найденные дефекты — разработчику, тест не ослабляется.
4. **Ревью** (ревьювер): замечания по уровням «блокирует» / «желательно». Блокирующие возвращаются разработчику, после правки — снова тестировщик (прогон) и ревьювер.
5. **Вердикт** (судья): по каждому сценарию «подтверждено» или «не подтверждено» с доказательствами, отметка о подгонке. Вердикт «не принято» возвращает работу нужной роли.
6. **Архив и PR** (ведущий): перенос дельт и архив в том же PR (`/opsx:archive`), PR по шаблону. PR открывается как draft и переводится в «Ready for review» только после вердикта «принято». Тогда автослияние его сливает.

**Предел кругов.** Если один этап возвращается больше трёх раз, ведущий останавливается: оставляет PR в draft и описывает владельцу, где застряли и какие есть варианты.

**Мелкие правки** (опечатка, ссылка, документ без изменения поведения) идут без OpenSpec и без судьи: разработчик и самопроверка. Если правка задела поведение, она уже не мелкая.

## 3. Тесты

### 3.1. Каждое требование

Каждое требование в `openspec/specs/` проверяется тестом с маркером, по которому `scripts/check_traceability.py` строит отчёт:

```python
@pytest.mark.req("question-routing", "Цепочка «карта»", scenario="Нет кандидатов")
def test_no_candidates_falls_back(...): ...

@pytest.mark.req("question-routing", "Цепочка «карта»", invariant="не больше 3 вызовов модели")
def test_map_chain_call_budget(...): ...
```

Два первых аргумента — возможность и заголовок требования, их считает скрипт прослеживаемости. Именованный аргумент говорит, какой у теста вид:
- `scenario=` — заголовок сценария из спецификации;
- `invariant=` — правило нормативного теста.

Скрипт пока считает только требования. Пока проверку сценариев не автоматизировали, полноту по сценариям сверяют тестировщик и судья.

### 3.2. Два вида тестов

| Вид | Что проверяет | Как устроен |
|---|---|---|
| **Сценарный** | Один сценарий WHEN/THEN из спецификации | Ставит условия WHEN, выполняет действие, проверяет каждое утверждение THEN. Одно утверждение THEN без проверки — сценарий не покрыт |
| **Нормативный** | Инвариант: правило, которое держится при любых входах. Например, вызовов модели не больше предела; текст модели не попадает в адрес; связи без проверки помечены; нет прокрутки страницы на 1024×576; событие журнала без личных данных | Проверяет правило на наборе входов: параметризация, граничные значения, испорченные и враждебные входы, несколько размеров экрана. Имя инварианта — в `invariant=` |

Инварианты берутся из нормативных формулировок спецификаций (SHALL, MUST, «не», «всегда», «только») и из разделов «Риски» и «Безопасность» дизайна. Если инвариант нельзя проверить тестом (задержка под нагрузкой, качество ответа модели), это записывается в `verification.md` с тем, как он проверяется вместо теста: замер, оценка, ручная проверка.

### 3.3. Вывод и журнал

Каждый тест проверяет и **вывод**, и **журнал**:

- **вывод** — ответ API, поток событий, состояние интерфейса, файл;
- **журнал** — событие с ожидаемыми полями: `events.one(...)`/`events.of(...)` в юнит- и сервисных тестах (`tests/conftest.py`), `wait_logs(stack, service, ...)` в e2e (`tests/e2e/conftest.py`). События одного запроса сводятся по `request_id`.

Исключения:
- чисто визуальные требования (токены, шрифты, раскладка) — у них журнала нет, проверка по DOM и снимкам;
- требования, у которых события нет по природе.

Исключение пишется в `verification.md` с причиной. Если поведение важно, а события для него нет, это дефект спецификации или кода: событие добавляется в каталог.

### 3.4. Два подтверждения: журнал тестировщика и итоговый вывод

Чтобы агент не мог подогнать результат, каждое требование подтверждается из двух независимых источников.

1. **Журнал тестировщика** — `openspec/changes/<имя>/verification.md`, раздел «Тестировщик». Это сырые данные, а не пересказ:
   - для каждого сценария и инварианта — идентификатор теста;
   - команда и строка итога pytest;
   - выдержка события журнала (`event`, ключевые поля, `request_id`);
   - для e2e — что увидел пользователь.
2. **Итоговый вывод** — судья сам, в своём контексте, прогоняет тесты изменения и полный набор. Затем поднимает стенд (`scripts/dev_stack.py` или e2e) и проходит главные сценарии, собирая вывод и события по `request_id`. Результат судья пишет в раздел «Судья» того же файла.

Судья сравнивает два источника. **Расхождение — признак подгонки**, пока не объяснено:
- разные числа прошедших тестов;
- тест в журнале есть, а в коде его нет;
- событие в журнале есть, а на стенде его нет;
- вывод не тот.

**Признаки подгонки, которые ищут ревьювер и судья** (`git diff origin/main -- tests openspec`):

- ожидаемое значение в тесте поменяли так, чтобы оно совпало с фактическим выводом, без изменения спецификации;
- проверка удалена или ослаблена: меньше полей, `in` вместо `==`, шире допуск, `>= 0`;
- добавлены `skip`, `xfail`, `skipif`, `try/except` вокруг проверки, условный выход;
- заглушка подменяет сам проверяемый модуль; проверка повторяет то, что заглушка сама вернула (тавтология);
- проверка отсутствия после фиксированной паузы (`wait_for_timeout`, `sleep`) вместо точки синхронизации;
- маркер `req` на тесте, который не проверяет THEN этого требования;
- спецификацию подправили под реализацию без записи в `progress.md` и без согласия владельца;
- разработчик правил тест тестировщика.

### 3.5. Мутационная проверка

Для ключевых правил изменения тестировщик временно ломает код и убеждается, что падает нужный тест, а потом возвращает код. Ключевые правила — это инварианты и ветви отказа: порядок, граница, отсечение, запасной путь. Результат («сломал X — упал `test_y`») пишется в `verification.md`. Судья повторяет хотя бы одну мутацию сам. Тест, который не падает на поломке своего правила, не считается покрытием.

### 3.6. Что запускать

| Когда | Команда |
|---|---|
| После каждого пункта | тесты затронутых модулей: `pytest -q tests/<пакет>/test_<модуль>.py` |
| Перед передачей ревьюверу | `ruff check . && ruff format --check .`, `lint-imports`, `python scripts/check_traceability.py`, `cd web && npm run build` |
| Тестировщик и судья | тесты изменения, затем полный `pytest -q` (около 25 минут; e2e требуют собранного `web/dist`) |
| Визуальные изменения | `python scripts/visual_check.py` или снимки нужных размеров в обеих темах; страница без прокрутки на 1024×576, 1366×768, 1920×1080 |

## 4. Модели

Модель каждой роли задана в `model:` определения субагента в `.claude/agents/`. Правило: сложное рассуждение — Opus, механическая и объёмная работа — лёгкие модели.

| Роль | Модель | Почему |
|---|---|---|
| Ведущий, разработчик, ревьювер, судья | **Opus** | Архитектурные решения, поиск тонких дефектов и подгонки, итоговая ответственность |
| Тестировщик | **Sonnet** | Тесты пишутся по готовой спецификации и образцам из `tests/`; объём большой, рассуждение умеренное |
| Исполнитель прогонов | **Haiku** | Запустить команды, собрать вывод и журналы, ничего не решать |

Тестировщик поднимается до Opus, только если тест требует новой тестовой инфраструктуры (стенд, фикстура, заглушка сервиса). В `progress.md` это отмечается.

Судья всегда отличается от разработчика по контексту, даже если модель одна: это новый субагент без истории разработки.

## 5. Выбор решения

Перед реализацией разработчик записывает в `design.md` раздел «Выбор решения». В нём не меньше двух вариантов, включая самый простой, и оценка каждого по трём критериям.

| Критерий | Что оценивается |
|---|---|
| **1. Оптимальность** | Минимально достаточное решение. Цена на пути пользователя: вызовы модели, деньги, задержка, запросы между сервисами. Объём кода и новых зависимостей |
| **2. Архитектурная правильность** | Правило живёт в одном месте и в правильном сервисе. Границы сервисов не нарушены (`lint-imports`). Совместимость с ADR и спецификациями. Данные идут через API сервиса-владельца, а не в обход. Модель предлагает, код проверяет: ничто из ответа модели не применяется без проверки сервером |
| **3. Поддерживаемость и масштабируемость** | Нет дублирования правил. Настройка данными, а не ветвлением кода (как цепочки ассистента). Тестируемость без живой модели. Что будет при 10× источников, пользователей, сущностей. Насколько легко изменить или удалить |

Формат в `design.md`:

```markdown
## Выбор решения

| Вариант | Оптимальность | Архитектура | Поддержка и масштаб |
|---|---|---|---|
| А. … | … | … | … |
| Б. … | … | … | … |

Выбрано: Б, потому что … Чем платим: … Костыли, которых избегаем: …
```

**Признаки костыля** — повод вернуться к выбору:
- особый случай по идентификатору или строке;
- `sleep` вместо синхронизации;
- копия логики в двух местах без общего теста;
- `except Exception` без события;
- флаг ради одного теста;
- правка теста под код;
- обход сервиса через его базу;
- «временное» без задачи на удаление.

Если без такого решения не обойтись, это записывается в «Чем платим», а задача на исправление — в `tasks.md` или в открытое изменение.

Ревьювер проверяет, что код соответствует выбранному варианту. Если реализация ушла к другому варианту, раздел обновляется, а не остаётся устаревшим.
