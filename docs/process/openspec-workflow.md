# Работа по OpenSpec

Фичи и изменения ведём по spec-driven подходу фреймворка [OpenSpec](https://github.com/Fission-AI/OpenSpec): сначала спецификация, потом реализация. В репозитории уже выполнен `openspec init`: конфиг в `openspec/config.yaml`, команды и навыки для Claude Code в `.claude/`. Артефакты пишем на русском, служебные заголовки и слова SHALL/MUST оставляем английскими.

CLI ставится отдельно на каждой машине. На Windows: `irm https://openspec.dev/cli/install.ps1 | iex` (Node.js не нужен). Либо через npm при Node.js 22.12 или выше: `npm install -g @fission-ai/openspec@latest`.

## Где что лежит

| Путь | Что внутри |
|---|---|
| `openspec/specs/` | Актуальные спецификации: как система должна работать сейчас. Источник правды по поведению |
| `openspec/changes/<имя>/` | Предложение об изменении: `proposal.md` (зачем и что), `design.md` (как, если нужно), `tasks.md` (задачи), `specs/` (изменения к спецификациям) |
| `openspec/changes/archive/` | Завершённые изменения с датой в имени, например `2026-11-20-add-ontology` |
| [docs/product/](../product/vision.md) | Продуктовый контекст: видение и system design. Объясняют, почему система такая, но не заменяют спецификации |

## Цикл изменения

1. **Предложение.** Описываем изменение в `openspec/changes/<имя>/`: `proposal.md`, при необходимости `design.md`, спецификации изменений и `tasks.md`. Неясности закрываем обсуждением до реализации.
2. **Реализация.** Идём по `tasks.md` и сверяемся со спецификациями.
3. **Архив.** Когда изменение готово, оно архивируется, и его спецификации вливаются в `openspec/specs/`. Архивируем в том же PR, где завершена реализация: `openspec archive <имя> --yes`. Задачи, которые ждут внешнего (данных, ключей, доступов владельца), не держат изменение открытым: они переносятся в отдельное изменение с пометкой «перенесено в …», а готовое архивируется. Изменение без спецификаций (данные, замеры, эксплуатация) помечается `skip_specs: true` в `.openspec.yaml`.

В Claude Code эти шаги вызываются командами `/opsx:propose`, `/opsx:apply`, `/opsx:archive`. Для обсуждения перед предложением есть `/opsx:explore`, для правки уже созданного изменения `/opsx:update`, для переноса спецификаций изменения в `openspec/specs/` без архивации `/opsx:sync`.

## Контрольные точки

Работа может оборваться в любой момент: кончились лимиты, закрылась сессия, упал субагент. Чтобы её можно было продолжить с того же места:

- Задача заводится до начала работы: изменение в `openspec/changes/<имя>/` с `tasks.md`.
- Рядом ведётся журнал `progress.md`: кто ведёт (сессия или субагент и его роль), статус каждого пункта `tasks.md` (сделан, в работе, не начат), что сделано в текущем пункте, следующий шаг, известные проблемы, как проверить.
- После каждого завершённого пункта: пункт отмечается в `tasks.md`, журнал обновляется, изменения коммитятся (`wip(<имя>): …`) и ветка пушится. При слиянии PR коммиты сжимаются в один.
- Возобновление: прочитать `progress.md` и `git log` ветки, продолжить с первого незакрытого пункта.

## Формат спецификации

Обычный Markdown. Требование описывается нормативной формулировкой со словом SHALL, у каждого требования есть сценарии в виде WHEN и THEN:

```markdown
## ADDED Requirements

### Requirement: Выбор учебника
Система SHALL позволять пользователю выбрать основной учебник из библиотеки.

#### Scenario: Пользователь меняет учебник
- **WHEN** пользователь выбирает другой учебник
- **THEN** страница главы показывает текст выбранного учебника
```

В папке изменения такие блоки группируются под заголовками `## ADDED Requirements`, `## MODIFIED Requirements` и `## REMOVED Requirements`. Точный синтаксис последних двух сверяем с документацией OpenSpec, когда будет первое изменение существующей спецификации.

## Как это сочетается с остальным процессом

Ветки и PR идут как раньше, см. [git-workflow.md](git-workflow.md). Спецификации и код одного изменения лежат в одном PR, чтобы PR показывал, как поведение изменилось.
