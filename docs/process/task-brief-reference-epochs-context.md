# ТЗ для Claude: справочник, эпохи, контекст + интерактивный географический таймлайн

Выдаёт Lead (DSH, ноутбук). Исполнитель — Claude (отдельный сервер, VS Code).

## 1. Контекст

- Локальный стенд PhiloGraph поднят на ноутбуке Lead'а: онтология извлекается в фоне
  (≈700+ сущностей, 360+ утверждений), карта раздела `/graph` работает, web-клиент собран.
- Данные `.stack` (SQLite: библиотека, онтология, поиск) — **локальны у Lead'а**, в git их нет.
  Claude их не видит; он пишет код/спеки/скрипты, Lead прогоняет на своих данных.
- Базовая ветка для отталкивания — **`claude/embedding-docker`** (запушена в origin, коммит
  `ec97eb8`). В ней: рабочий прогон (бюджет/токены в `config/llm.yaml`, strong-извлечение
  в `filling.py`, явный промпт `ontology.extract`, атомарный захват очереди `queue.py`,
  пилот arxiv в каталоге).

## 2. Что нужно сделать (4 задачи)

### 2.1 Справочник
Страница-каталог сущностей онтологии: персоны, понятия, труды, эпохи, события.
Поиск, фильтры по типу/эпохе/разделу, переход в карточку, счётчики по типам.
Питание — `GET /api/knowledge/v1/entities` и связанные эндпоинты.

### 2.2 Эпохи
Сущности типа `epoch` с датами (`primary.dates`), отображение на таймлайне,
связь «относится к эпохе» (`relates_to_epoch` / аналог из реестра).
Даты эпох — из Wikidata (отдельное обогащение), UI — отображение и фильтрация.

### 2.3 Контекст
Исторический контекст эпохи: политические/экономические/религиозные/научные события и
явления, стимулировавшие идеи. Связи `стимулировало` / `возникло в контексте` (с механизмом,
уточнитель). Источник части связей — текст (извлечение), части — Wikidata/генерация.

### 2.4 (Личное пожелание владельца) Интерактивный географический таймлайн
Отдельная фича: 3D-земля, прокрутка времени, развитие и связи во времени и **пространстве**.
Референс: https://mpjuhasz.com/posts/influenced-by/ (3D Earth, можно крутить время и видеть развитие).
Нужно «сделать конфетку», но **сперва детально продумать с разных сторон** (варианты, trade-off,
производительность, доступность, что из этого реально в рамках текущего стека).

## 3. Процесс (обязательно)

1. **Сначала архитектура и требования — полностью самостоятельно, без владельца.**
   Владелец в обсуждении НЕ участвует. Все архитектурные и продуктовые вопросы решаешь сам,
   организуя **внутреннее обсуждение с субагентами в разных ролях** (по `CLAUDE.md`:
   `coder`/разработчик, `tester`/тестировщик, `reviewer`/ревьювер, `judge`/судья;
   `test-runner` — для прогонов). Роли спорят и находят решение, ты ведёшь и фиксируешь итог.
   Вопросов владельцу не задавать.
2. **Документировать явно и детально.** Каждое решение и его альтернативы — в `design.md`
   (раздел «Выбор решения» по трём критериям), ход работы — в `progress.md`, выводы ролей и
   судьи (сырые результаты, вердикт) — там же. Ничего не оставлять «только в чате»: всё, что
   решили, — текстом в OpenSpec-артефактах.
3. **Концепты UI и функциональные** — макеты/вайрфреймы/описания сценариев до реализации.

4. **OpenSpec-цикл** (по `docs/process/openspec-workflow.md`):
   `openspec new change "<kebab-name>"` → `proposal.md` (Why / What Changes / Capabilities /
   Impact), `specs/<capability>/spec.md` (дельта: `## ADDED|MODIFIED` + `### Requirement:` SHALL
   + `#### Scenario:` WHEN/THEN), `design.md` (с разделом «Выбор решения» по трём критериям),
   `tasks.md`. **Планирование и код не смешивать.**
5. **Реализация** по `tasks.md`, контрольные точки: отметка в `tasks.md` → `progress.md` →
   `wip(<change>): …` → push.
6. **Проверка готовности по инвариантам и всем якорям**:
   - traceability (`@pytest.mark.req` у каждого требования из `openspec/traceability.yaml`);
   - сценарные тесты (`scenario=`) и нормативные (`invariant=`);
   - e2e и визуальные — если затронут UI (`scripts/visual_check.py`, эталоны только win32);
   - дизайн-якоря графа/карты: линии жизни, узлы, маршруты связей (`anchorOn`), без регрессий.

## 4. Ограничения

- Работать в **своих ветках** от `claude/embedding-docker` (или от `main` — согласовать с Lead'ом).
- **Не трогать runtime-файлы Lead'а** без согласования: `config/llm.yaml`,
  `scripts/dev_stack.py`, `src/philograph/platform/queue.py`,
  `src/philograph/knowledge/filling.py`, `src/philograph/prompts/__init__.py`,
  `sources/catalog.yaml`. Если нужно — писать в задачи/PR отдельным пунктом.
- Данные `.stack` не коммитить. Секреты — только в `.env`.
- Соблюдать `docs/process/working-principles.md`, `openspec-workflow.md`, `git-workflow.md`,
  `AGENTS.md`, роли и вердикт судьи.
- Новые фичи не должны ломать границы сервисов (`lint-imports`) и текущий прогон онтологии.
