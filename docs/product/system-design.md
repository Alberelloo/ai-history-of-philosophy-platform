# System design

Пересобран по блокам в формате интервью 02–03.11.2026 на основе [видения](vision.md). Подробная модель онтологии в [ontology.md](ontology.md). Стек выбран в [ADR-0001](../architecture/adr/0001-stack.md).

## 1. Требования

### Функциональные

Берутся из возможностей первой версии (vision, блок 6).

| Возможность | Система должна |
|---|---|
| Библиотека | хранить источники с названием, автором, языком и лицензией; показывать список; давать выбрать основной |
| Чтение | показывать главы выбранного учебника; выделять в тексте термины, имена и события как кликабельные; позволять выделить любой фрагмент |
| Карточки | для понятия: описание, происхождение слова, связи; для философа: биография, основные работы, связи; для события: описание и связь с идеями. Везде ссылки на источники. Открываются рядом с текстом (П-6) |
| Граф | строить по запросу (сущность, направление, глубина); различать проверенные и сгенерированные связи; у каждой связи показывать источники. Сохранённые связи показываются сразу, достроенные LLM добавляются на экран по мере появления |
| Ассистент по месту | принимать вопрос, выделенный фрагмент и источник; отвечать потоком со ссылками на источники |
| Ассистент как база знаний | отвечать без привязки к тексту по нескольким источникам; рассказывать о трактовках других авторов |
| Прозрачность | помечать сгенерированное (значок и рамка); показывать при первом входе уведомление и переключатели; отключать ответы без опоры на источники |
| Сквозное | логировать вызовы LLM и использование функций |

### Нефункциональные

| Свойство | Требование |
|---|---|
| Нагрузка | порядка сотен одновременных пользователей в худшем случае |
| Скорость чтения и карточек | открываются быстро: данные подготовлены заранее, LLM не участвует |
| Скорость ассистента | ответ потоком, первое слово появляется быстро; скорость на уровне быстрых моделей класса Flash; числа фиксируем после замера на прототипе |
| Стоимость | не более 50 долларов в месяц на вызовы LLM в первой версии; тяжёлые расчёты (наполнение онтологии) выполняются заранее и кэшируются |
| Доверие | каждая ссылка в ответе проверяется кодом на существование в найденных источниках; пометка сгенерированного обязательна и не теряется при ошибке |
| Устойчивость | чтение, карточки и сохранённые связи работают, даже если LLM недоступна; ошибки LLM показываются понятным сообщением |
| Приватность | без аккаунтов; вопросы пользователей уходят провайдеру LLM, пользователь об этом уведомлён; логи без персональных данных |
| Платформа | веб-приложение для современных браузеров на компьютере, интерфейс на русском |
| Развёртывание | публичный сайт, доступный участникам исследования |
| Данные | лицензия хранится у каждого источника; показываем только разрешённое |
| Расширяемость | другой раздел философии добавляется данными, а не переделкой архитектуры |
| Воспроизводимость | подготовка данных запускается одной командой и повторима |

## 2. Ограничения и допущения

| Что | Значение |
|---|---|
| Команда | один разработчик с AI-ассистентом: архитектура должна быть минимальной и понятной одному человеку |
| Бюджет на LLM | до 50 долларов в месяц |
| Бюджет на хостинг | выделен отдельно |
| Модели | только по API, собственную LLM не поднимаем. Основной провайдер: DeepSeek |
| Развёртывание | публичный сайт |
| Стек | не выбран, определяем после архитектуры |
| Языки | интерфейс на русском, источники могут быть на разных языках |
| Состояние пользователя | в первой версии (v0) хранится в браузере; аккаунты появятся в следующих версиях вместе с шерингом и загрузкой материалов |

### Оценка объёма данных

| Данные | Порядок |
|---|---|
| Источники | около сотни |
| Абзацы | десятки тысяч |
| Сущности онтологии | сотни или тысячи |
| Связи онтологии | тысячи или десятки тысяч |

Данных немного: хватает одной базы и одного небольшого сервера, распределённые и специализированные хранилища не нужны. Принцип проектирования: простая архитектура, пока нагрузка не требует сложной.

## 3. Архитектура верхнего уровня

Микросервисы на общем сервере, подготовка данных вынесена в отдельные офлайн-задачи. Принцип: сервисов немного, один репозиторий, одна команда запуска.

```
Браузер ──▶ Веб-клиент
              │
              ▼
          API-шлюз
              │
   ┌──────────┼───────────────┬──────────────────┐
   ▼          ▼               ▼                  ▼
Библиотека  Знания         Ассистент           Поиск
   │          │                │                  │
   │          └────────────▶ Сервис LLM ──▶ DeepSeek
   │                            ▲
   ▼                            │
Реляционная БД      Векторная БД        Очередь задач
(тексты,            (эмбеддинги         ▲
 онтология)          абзацев)           │
                                 Офлайн-задачи (запуск вручную и по расписанию):
                                 • обновление источников
                                 • индексация
                                 • наполнение онтологии
```

### Сервисы

| Сервис | Ответственность | Данные |
|---|---|---|
| Веб-клиент | чтение, всплывающие окна, граф, панель ассистента, первое включение и настройки | состояние в браузере |
| API-шлюз | единая точка входа, потоковая передача, лимиты; позже аккаунты | нет |
| Библиотека | список источников, главы, абзацы, подсветка терминов в тексте | реляционная БД |
| Знания | сущности, связи, карточки, обход для графа, достройка недостающих связей | реляционная БД |
| Ассистент | определить тип вопроса (маршрутизация), пройти заданную цепочку шагов, собрать ответ, проверить ссылки | нет своего хранилища |
| Поиск | найти абзацы по смыслу и по словам, фильтровать по источнику | векторная и реляционная БД |
| Сервис LLM | единственное место вызовов моделей: журнал, подсчёт стоимости, кэш, замена провайдера | журнал и кэш |

### Офлайн-задачи

Не работают постоянно: запускаются вручную или по расписанию, выполняют работу и завершаются.

| Задача | Что делает |
|---|---|
| Обновление источников | находит и загружает источники, разбирает на главы и абзацы, записывает метаданные и лицензию |
| Индексация | считает эмбеддинги абзацев, обновляет векторную базу и текстовый индекс |
| Наполнение онтологии | извлекает и обновляет сущности и связи, помечает происхождение каждой |

### Правила взаимодействия

| Правило | Суть |
|---|---|
| Путь пользователя синхронный | чтение, карточки, граф, ассистент: вызовы между сервисами синхронные, ответ ассистента идёт потоком по всей цепочке |
| Очередь только там, где никто не ждёт | офлайн-задачи, отложенная запись (достроенные связи, журналы) |
| Граф | сохранённые связи отдаются сразу, достроенные LLM связи появляются на экране по мере генерации, пользователь ждёт; сохраняются в онтологию отложенно с пометкой «не проверено» |
| Доступ к чужим данным | сервис читает данные другого только через его API, не лезет в его таблицы |
| Деградация | при недоступности LLM работают чтение, карточки и сохранённые связи; ассистент сообщает, что временно недоступен; на синхронных вызовах заданы таймауты |
| Базы | одна реляционная база с отдельными схемами по сервисам и одна векторная. Реляционная хранит все тексты, онтологию и идентификаторы, векторная только эмбеддинги со ссылкой на идентификатор абзаца |
| Развёртывание | контейнеры на одном сервере, запуск одной командой, без Kubernetes |

### Принятые решения

| # | Решение | Почему | Цена |
|---|---|---|---|
| А1 | Микросервисы | выбор автора | больше сопровождения для одного разработчика; смягчаем малым числом сервисов, одним репозиторием и одним способом запуска |
| А2 | Отдельная векторная база | выбор автора, под RAG | два хранилища, синхронизация идентификаторов |
| А3 | Ассистент: маршрутизация и заданные цепочки шагов, а не агент с циклами | дешевле, быстрее, проще измерять; при бюджете 50 долларов в месяц агент с циклами рискован | менее гибок для неожиданных вопросов |
| А4 | Гибрид: синхронно на пути пользователя, очередь для офлайна и отложенной записи | простота там, где человек ждёт; надёжность там, где работа тяжёлая | брокер или очередь задач в инфраструктуре |
| А5 | Достроенные LLM связи сохраняются в онтологию с пометкой | не платить повторно, накапливать знания | в онтологии появляются непроверенные данные, нужна чёткая метка происхождения |

## 4. Данные и онтология

Подробно в [ontology.md](ontology.md). Здесь только то, что нужно для остальных блоков.

### Два набора данных

| Набор | Что в нём | Где хранится | Сервис |
|---|---|---|---|
| Документы | источник, глава, абзац | реляционная БД; эмбеддинги абзацев в векторной БД | Библиотека, Поиск |
| Знания | онтология: сущности, утверждения, реестр типов, рецепты обхода | реляционная БД, отдельная схема | Знания |

Документы и знания связаны тремя способами:
- **подтверждение:** утверждение онтологии ссылается на абзац и цитату;
- **упоминание:** названия сущностей и терминов находятся в тексте автоматически, с учётом склонений; LLM разрешает только неоднозначные случаи;
- **издание:** источник библиотеки ссылается на произведение в онтологии.

### Устройство онтологии

- **Сущности** пяти слоёв: слова (термин), идеи (понятие, концепция автора, учение, проблема, позиция, аргумент), люди и сообщества (персона, группа), тексты (произведение), история (событие, идейное событие, явление, эпоха, место).
- **Утверждения:** всё, кроме идентификатора, типа и названий, включая даты и определения. У утверждения есть уточнители, атрибуция (кто в мире философии так считает), подтверждения из библиотеки, согласие, ранг, статус из П-4 и происхождение в системе.
- **Идейные события** моделируют возникновение и изменение идей: участники, исходный материал, результат, произведение, обстоятельства. Генезис понятия — цепочка таких событий.
- **Реестр** описывает типы сущностей, связей и уточнителей как данные: допустимые концы, иерархию, обратные названия, правила для LLM. Новый тип добавляется без изменения кода.
- **Рецепты обхода** задают запросы графа (генезис, последствия, полемика, контекст, ответы на проблему, сравнение концепций, путь между двумя сущностями). Маршрутизатор ассистента и кнопки графа выбирают рецепт.
- **Проверки целостности:** типы концов и уточнители проверяются при записи; хронология и пересечение жизней дают предупреждения в очередь проверки.

### Принятые решения

| # | Решение |
|---|---|
| О1 | Онтология — реляционная БД с реестром типов, без отдельной графовой базы; обход рекурсивными запросами |
| О2 | Связи и значения хранятся как утверждения с атрибуцией и подтверждениями |
| О3 | В v0 входят идейные события, ключевые проблемы, позиции и аргументы, концепции по критерию дробности; число сущностей определится по данным |
| О4 | Из Wikidata импортируются только простые факты (даты, места, авторство, учителя) со статусом «по источникам»; связи влияния только из библиотеки или достройкой LLM |
| О5 | В v0 есть внутренняя страница проверки утверждений и переключатель «только выбранный учебник / все источники» |

## 5. Конвейеры

Три офлайн-задачи из блока 3. Главное правило: **конвейеры обрабатывают один источник за раз, а не пересобирают всё.** Добавили источник, обработали только его, онтология дополнилась его утверждениями. На этот же конвейер позже ляжет загрузка своих материалов.

### Конвейер источника

| Шаг | Что делает | Если не получилось |
|---|---|---|
| Регистрация | метаданные, лицензия | без подходящей лицензии дальше не идёт |
| Получение | загрузка файла, отпечаток содержимого для отслеживания изменений | повтор |
| Извлечение текста | текстовые форматы разбираются напрямую, сканы распознаются (OCR) | |
| Проверка качества OCR | автоматические метрики (уверенность распознавания, доля словарных слов, доля мусорных символов) отсеивают явно плохие сканы; по остальным человек просматривает 5–10 случайных страниц и решает | источник откладывается |
| Структура | главы, абзацы, сноски, номера страниц для ссылок, удаление колонтитулов | на ручную правку |
| Публикация | источник появляется в библиотеке | |

Каждая обработка создаёт новую версию источника, и читатели видят опубликованную версию, пока новая не будет готова целиком. У версии есть состояние (создана, файлы получены, текст извлечён, ожидает решения о качестве, отложена, структура разобрана, проверена, опубликована, заменена, снята), поэтому обработку можно продолжить с места сбоя. Подробно в изменении OpenSpec [add-source-pipeline](../../openspec/changes/archive/2026-11-05-add-source-pipeline/proposal.md).

### Конвейер индексации

1. Эмбеддинги абзацев через API провайдера эмбеддингов, запись в векторную базу. У DeepSeek API для эмбеддингов нет (по официальной документации на 03.11.2026), провайдера выберем на этапе стека.
2. Полнотекстовый индекс.
3. Упоминания сущностей с учётом склонений. Неоднозначные случаи разрешает LLM.

Когда в онтологии появляются новые сущности, упоминания пересчитываются только для их названий во всех источниках.

### Конвейер наполнения онтологии

1. **Ядро** вручную с подсказками LLM и импорт простых фактов из Wikidata. Делается один раз и дополняется по мере надобности.
2. **Извлечение из нового источника:** в LLM отправляется фрагмент главы из нескольких абзацев, чтобы модель видела контекст. Цитаты в утверждениях привязываются к конкретным абзацам. Вывод структурированный, по схеме из реестра.
3. **Нормализация:** привязка к существующим сущностям, слияние дублей, проверки целостности.
4. **Сведение:** объединение одинаковых утверждений, пересчёт согласия у затронутых утверждений.
5. **Очередь проверки** на странице проверки.
6. **Повышение статуса:** в новом источнике ищутся подтверждения для сгенерированных утверждений.

### Запуск и стоимость

- Запуск вручную командой, по расписанию и по событию: опубликованный источник ставится в очередь на индексацию, затем на извлечение.
- Первичное наполнение оплачивается отдельным разовым бюджетом, лимит 50 долларов в месяц относится к работе сайта. Грубая оценка одного прохода извлечения по ценам `deepseek-flash`: порядка 15–25 долларов на 30 тысяч абзацев. Точную сумму посчитаем на пробной выборке.
- Библиотека пополняется не чаще раза в несколько недель.

### Видимость данных

В v0 все источники и утверждения общие. В будущем загруженный источник принадлежит области видимости: пользователю или группе, например преподавателю и его студентам. Утверждения, извлечённые из него, видны только в этой области. Общим для всех источник и его утверждения становятся только после официальной проверки и верификации. Поле «область видимости» у источников и утверждений закладываем уже в v0, все значения в нём пока общие.

## 6. Потоки

### Чтение главы

Клиент → шлюз → библиотека: текст главы и упоминания сущностей в ней. LLM не участвует.

### Карточка

Клиент → шлюз → знания: утверждения о сущности с учётом переключателя «только выбранный учебник / все источники». LLM вызывается, только если нет описания и генерация включена в настройках; сгенерированное описание помечается и сохраняется.

### Граф

1. Клиент → шлюз → знания: выбирается рецепт обхода, сохранённые связи отдаются сразу.
2. Если связей мало и генерация включена, сервис знаний вызывает сервис LLM для достройки. Новые связи проходят проверки целостности и приходят на экран потоком с пометкой.
3. Достроенные связи сохраняются отложенно через очередь со статусом «сгенерировано».

### Ассистент

1. Шлюз получает вопрос, выделенный фрагмент (если есть), источник, историю диалога и настройку «только по источникам».
2. **Маршрутизация:** быстрый и дешёвый вызов LLM определяет тип вопроса.

| Тип | Пример | Цепочка |
|---|---|---|
| По месту | «Что здесь значит „впечатление“?» | сущности фрагмента, их окружение в онтологии, поиск в основном источнике |
| База знаний | «Что считал Юм о причинности?» | сущности вопроса, утверждения онтологии, поиск по всей библиотеке |
| Другие авторы | «Как это объясняют другие?» | концепции и атрибуции, поиск в других источниках |
| Генезис и контекст | «Откуда взялась эта идея?» | рецепт графа «генезис» или «контекст», утверждения и подтверждающие абзацы |

3. **Поиск:** сервис поиска с запросом, расширенным через онтологию.
4. **Генерация** через сервис LLM потоком. Модель получает абзацы и утверждения с идентификаторами и размечает, на что опирается каждый фрагмент ответа.
5. **Проверка:** код сверяет ссылки с переданными абзацами и утверждениями. Фрагменты без опоры на источники помечаются по отдельности (значок и рамка у фрагмента, а не у всего ответа).
6. Если включён режим «только по источникам», фрагменты без опоры не показываются, а при отсутствии опоры совсем ассистент говорит, что в источниках ответа нет.

**Память диалога:** ассистент помнит предыдущие вопросы и ответы в пределах одного окна ассистента, чтобы понимать уточнения вроде «а у Канта?». История хранится в браузере и передаётся с каждым запросом.

### Страница проверки

Сервис знаний отдаёт очередь утверждений по приоритету: часто показываемые, спорные, с предупреждениями целостности. Человек подтверждает, правит или отклоняет утверждение, статус меняется.

## 7. Качество системы

Общей метрики качества нет: у каждого компонента своя. Пороги не ставим до работающего прототипа.

### Метрики по компонентам

| Компонент | Что измеряем | На чём |
|---|---|---|
| OCR и структура | доля ошибок распознавания по символам и словам; правильность разбиения на главы и абзацы | страницы с эталонной расшифровкой |
| Упоминания в тексте | точность и полнота найденных упоминаний; доля неоднозначных | абзацы с ручной разметкой упоминаний |
| Извлечение онтологии | доля верных утверждений, отдельно по типам связей; цитата есть в абзаце и подтверждает утверждение; доля дублей сущностей; доля нарушений целостности | выборка утверждений, проверенная человеком |
| Покрытие онтологии | на сколько контрольных вопросов из [ontology.md](ontology.md) онтология даёт ожидаемый ответ | контрольные вопросы с эталонными ответами |
| Достройка LLM | доля верных среди сгенерированных; доля, позже подтверждённых источниками | выборка сгенерированных утверждений |
| Поиск | recall@k и MRR; то же без онтологии, чтобы увидеть её вклад | вопросы с размеченными релевантными абзацами |
| Маршрутизатор | точность определения типа вопроса | вопросы с размеченным типом |
| Ассистент | верность ответа источникам; корректность ссылок; точность пофрагментной пометки; правильность отказов в режиме «только по источникам»; доля использованных из подходящих источников; качество ответа | вопросы с эталонными ответами, включая вопросы без ответа в источниках |
| Система целиком | время до первого слова и до полного ответа; стоимость запроса; доля ошибок | журналы и нагрузочный прогон |

### Наборы для оценки

1. Вопросы: тип, релевантные абзацы, эталонный ответ, ожидаемые сущности. Отдельно вопросы, на которые в источниках ответа нет.
2. Абзацы с размеченными упоминаниями.
3. Выборка утверждений онтологии (даёт страница проверки).
4. Страницы сканов с эталонной расшифровкой.
5. Контрольные вопросы онтологии с ожидаемыми ответами.

Размер наборов определим, когда появится прототип. Разметку делает автор проекта: LLM готовит черновую разметку, автор её правит.

### Как оцениваем

- Автоматически: корректность ссылок, recall@k, MRR, маршрутизатор, проверки целостности, задержка, стоимость.
- LLM-оценщик (сильная модель, например `deepseek-v4-pro`): верность ответа источникам, качество ответа, подтверждает ли цитата утверждение. Согласие оценщика с человеком проверяется на небольшой выборке, размеченной вручную.
- Человек: выборки утверждений онтологии и достроенных связей, эталоны OCR.

## 8. Надёжность, безопасность, стоимость

Сайт публичный, аккаунтов нет, а каждый вопрос ассистенту стоит денег. Поэтому главная угроза — не взлом, а то, что кто-то израсходует бюджет на LLM.

### Надёжность

| Что | Как |
|---|---|
| Сбой LLM или поиска | таймауты, ограниченные повторы; чтение, карточки и сохранённые связи работают без LLM |
| Потеря данных | ежедневная резервная копия реляционной базы. Векторная база производная: пересобирается из абзацев (стоит денег на эмбеддинги, но данные не теряются) |
| Отказы сервисов | проверки состояния каждого сервиса, автоматический перезапуск контейнера |
| Наблюдение | журналы, метрики (задержка, ошибки, расходы), оповещения при сбоях и при приближении к лимиту бюджета |

### Безопасность

| Угроза | Защита |
|---|---|
| Злоупотребление ассистентом и расход бюджета | лимит запросов на посетителя; дневной лимит расходов на LLM около 1/30 месячного бюджета (1,5–2 доллара). При исчерпании ассистент и достройка графа отключаются до следующего дня с понятным сообщением, остальное работает |
| Чужой доступ к странице проверки | вход по паролю только для автора; страница не видна посетителям |
| Внедрение инструкций через вопрос или текст источника | текст пользователя и источников передаётся модели как данные; у ассистента нет действий, меняющих систему; ответ проходит проверку ссылок и пометку |
| Утечка ключей | ключи только в переменных окружения сервера; секреты в истории ищет gitleaks в CI |
| Перехват трафика | только HTTPS |

### Приватность

- Вопросы пользователей обрабатывает DeepSeek по своим правилам. Об этом прямо сказано в уведомлении при первом входе; участникам исследования об этом сообщаем отдельно.
- Журналы без персональных данных. Журналы вызовов LLM хранятся 90 дней.

### Стоимость

| Мера | Эффект |
|---|---|
| Маршрутизатор на дешёвой модели | основной расход только там, где нужен ответ |
| Достроенные связи сохраняются | повторный запрос того же графа ничего не стоит |
| Офлайн-задачи в ночные часы DeepSeek | ночью цены вдвое ниже |
| Кэш одинаковых запросов к LLM | повторный вопрос по тому же месту не оплачивается дважды |
| Дневной лимит | месячный бюджет не уходит за один день |

## 10. Риски и открытые вопросы

### Технические риски

| Риск | Чем грозит | Что делаем |
|---|---|---|
| Цепочка ассистента медленная: маршрутизатор, поиск, генерация, проверка | не выполняем требование к скорости | замер на прототипе; поток с первого слова; маршрутизатор на самой быстрой модели |
| Плохое качество OCR старых изданий | меньше источников | проверка качества, отложенные источники, приоритет текстовым форматам |
| Ошибки извлечения онтологии | неверные связи в графе и карточках | статусы, страница проверки, метрики по типам связей |
| Зависимость от DeepSeek: цены, доступность, правила | рост расходов или остановка | весь доступ к моделям через сервис LLM, смена провайдера в одном месте |
| Микросервисы для одного разработчика | время уходит на инфраструктуру | мало сервисов, один репозиторий, один способ запуска |
| Проверка человеком становится узким местом | статус «проверено» растёт медленно | очередь по приоритету, для метрик проверяется выборка |

### Открытые вопросы

1. Провайдер эмбеддингов.
2. Хостинг (стек выбран в [ADR-0001](../architecture/adr/0001-stack.md)).
3. Войдёт ли Википедия в библиотеку.
4. Числовые пороги скорости и качества: после замеров на прототипе.
5. Модель доступа к загруженным материалам (пользователь, группа, верификация): при проектировании загрузки, после v0.
