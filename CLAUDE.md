# CLAUDE.md

Контекст проекта для Claude Code (в VS Code и в облачных сессиях). Общие правила для любых агентов: стек, карта кода, команды, договорённости — в [AGENTS.md](AGENTS.md). Прочитай его первым. Процесс целиком — в [docs/process/working-principles.md](docs/process/working-principles.md).

## О проекте

Интерактивный AI-учебник по истории философии. Пользователь выбирает учебник и читает главу, открывает карточки понятий, философов и событий, смотрит синхронологическую карту раздела и спрашивает LLM-ассистента о выделенном месте текста.
- Знания хранит онтология (сущности и связи), тексты ищет RAG, онтология расширяет поиск.
- Связи, которые достроила модель и не проверил человек, в интерфейсе помечены.
- Ассистент отвечает со ссылками на источники.

Проблема: учебник задаёт одну авторскую парадигму, материал разрознен, а связи между учениями и контекст эпохи читателю приходится восстанавливать самому.

Рабочее название: PhiloGraph. Пилотный раздел: теория познания. Стек выбран ([ADR-0001](docs/architecture/adr/0001-stack.md)): Python 3.13 и FastAPI, PostgreSQL и Qdrant, React и Vite, Docker Compose. Подробнее:
- что в первой версии и что отложено — [docs/product/vision.md](docs/product/vision.md);
- устройство — [docs/product/system-design.md](docs/product/system-design.md);
- этапы — [docs/product/roadmap.md](docs/product/roadmap.md).

## Договорённости

- Источник правды по продукту и плану лежит в `docs/`. Если план меняется, обновляем документы там же, чтобы локальная работа и облачные сессии видели одну версию.
- Фичи ведём по spec-driven подходу OpenSpec: сначала спецификация в `openspec/`, потом реализация. Правила в [docs/process/openspec-workflow.md](docs/process/openspec-workflow.md). Спецификации описывают поведение, продуктовое обоснование остаётся в `docs/product/`.
- Изменения идут через ветки и PR в `main`, процесс описан в [docs/process/git-workflow.md](docs/process/git-workflow.md). Готовый PR сливается сам (squash), когда проходят проверки `checks` и `pr-format`.
- Claude не пушит в `main` напрямую. Ветки называет `claude/<кратко>`. Заголовок PR пишет по формату `<тип>: <что сделано>`, описание заполняет по шаблону (что изменилось, зачем, как проверить). Если изменение спорное и требует решения человека, PR открывается как draft.
- Код вычитываем: сгенерированное без проверки в `main` не попадает. Проверка — это цикл ролей с вердиктом судьи (ниже), а не самопроверка автора.

## Роли и цикл в Claude Code

Изменение поведения ведёт основная сессия по скиллу `change-loop`. Ролям она передаёт работу через субагентов из `.claude/agents/`, у каждого своя модель:

| Субагент | Скилл с инструкцией | Модель |
|---|---|---|
| `coder` | `role-coder` | opus |
| `tester` | `role-tester` | sonnet |
| `test-runner` | — (только прогоны и сбор журналов) | haiku |
| `reviewer` | `role-reviewer` | opus |
| `judge` | `role-judge` | opus |

Правила, которые легко нарушить:
- Судья — всегда новый субагент. Ему передаются путь к изменению, ветка и `verification.md`, но не рассуждения разработчика и не выводы ведущего.
- Тестировщику передаётся спецификация, а не код. Тесты он пишет от сценариев.
- PR остаётся в draft до вердикта судьи «принято».
- Если субагенты недоступны, роли проходятся по очереди в одной сессии, каждая с чистого чтения артефактов. Это отмечается в `progress.md`.

Команды OpenSpec: `/opsx:propose`, `/opsx:apply`, `/opsx:archive`, а также `/opsx:explore`, `/opsx:update`, `/opsx:sync`.

## Окружение

- Python и инструменты — в виртуальном окружении проекта (`.venv`). Если его нет: `pip install -e ".[dev]"`.
- Браузерные тесты и визуальные проверки идут через Playwright с Chromium.
- Ловушки окружения: CLI `openspec`, эталоны снимков только для Windows, `docker compose` для `tests/ops`. Подробно — в разделе «Известные ловушки» [AGENTS.md](AGENTS.md).
